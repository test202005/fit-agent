## 1. 从真实问题开始

用户输入：“我是进阶，来个 40 分钟背部训练”。动作库返回 1 条单臂哑铃划船，真实模型给出 4 组 × 8 次、休息 60 秒，同时返回 `total_min=40`，并称“已通过增加组数将总时长补足至约 40 分钟”。当前评测 PASS。

证据见 [pl-004 闭环复验](../eval/reports/真实BadCase闭环-pl-004.md)，原始批次为 `20260916T032017Z`。

可以确认：计划缺少支持时长声明的计算依据。不能仅凭上述字段认定实际训练一定是多少分钟；单次动作耗时、单侧计数、休息计法均未定义。

## 2. 当前链路与缺口

| 环节 | 当前实现 | 缺口及影响 |
|---|---|---|
| Planner | 从输入解析 `duration_min`；未提时默认 30；代码接收 5～300 的整数 | 它表示用户目标，不是计算出的计划耗时 |
| 动作库 | 按肌群与难度筛选；每个非空组合目前只有 1 个动作；字段为名称、肌群、难度、风险提示 | 没有动作计时方式、单次或单组耗时，无法直接重算计划时长 |
| Generator | 模型生成 `total_min`、动作、组数、次数、休息和 note | `total_min` 是模型声明值，没有独立计算 |
| Prompt v2 | 第 3 条要求时长贴近目标 ±20%；第 4 条要求动作不足时加组数；第 5 条固定简单/中等 3 组、中高 4 组，休息 60 秒 | “加组数”和固定处方之间缺少优先级；不能靠继续加一句指令解决口径冲突 |
| Parser | 检查 `total_min` 和动作数值为正整数 | 未检查计划内容与总时长一致；空计划也要求正的 `total_min` |
| Evaluator | `abs(total_min - expected.duration_min) <= target * 0.2` | 只比两个声明值；把目标原样抄回也能通过 |
| Stub | 直接设置 `total_min = duration_min` | 适合验证运行和断言，不能证明真实模型会合理估时 |
| Trace | 保存用户输入、解析结果、工具名称与参数、返回动作名、模型原始输出 | Generator 最终拼装输入与完整动作观察未直接落入事件；需要时补最小证据即可 |

代码入口：[plan.py](../backend/plan.py)、[动作库](../backend/action_lib.py)、[生成器 v2](../backend/prompts/workout_generator_v2.txt)、[评测 Runner](../eval/run_plan_eval.py)。现有 [PRD §9](prd-iter5-plan-generation.md) 的 ±20% 是初始默认值，没有估时方法或校准证据，不能解释成实际运动时长误差标准。

## 3. 业务口径建议

先区分三个概念：

| 概念 | 定义 | 依据 |
|---|---|---|
| 用户目标时长 | 用户希望训练多久 | 输入或明确的默认规则 |
| 计划预计时长 | 根据计划与已约定计时规则计算的估计 | 动作计时依据、组数、休息及包含项 |
| 实际训练时长 | 用户实际执行耗时 | 真实执行记录；本期没有这类数据 |

**建议本期先采用“有依据才报预计时长，无法估计就明确说明”的口径。** 用户目标保留，动作不足时可以给出可用动作并说明无法保证满足目标；不凭空补动作、不复制条目，不通过无依据地增加训练量来凑分钟数。允许部分满足的产品行为尚需确认。

此方向需要调整原来的 `total_min` 必填正整数及“总时长达标”要求。具体是字段更名、允许未知，还是增加状态，留到规则确认后的设计阶段；此稿不直接指定实现。

如果本期要求“必须输出可核算且接近目标的完整计划”，则需先补计时依据、可用动作/训练量约束及目标不可满足时的行为，范围会大于单纯校正声明。不要默认一个每次动作耗时，把工程假设当成训练事实。

### 需要确认的三个决定

1. **目标是尽量满足还是必须达标？** 推荐允许部分满足并明确说明；无法满足时不声称已完成时长安排。
2. **没有计时依据时怎样输出？** 推荐预计时长允许未知；空计划明确无可执行训练，不再用目标时长冒充计划时长。
3. **如果需要数值估时，本期由谁提供计时口径？** 需明确按次/按秒、单侧动作计数、组间休息是否含最后一组之后、动作切换、热身与整理是否计入。目标容差与计算舍入误差分别定义；±20% 是否沿用要有理由。

## 5. 实施前如何接上评测

- 需求层：先确认上述三个决定，再修改 PRD/输出协议，固定场景预期。未确认的新时长语义记待评审，不追改历史 PASS 为 FAIL。
- 代码断言：目标提取、空结果、动作来源与重复继续覆盖；有独立计算依据后再增加数值一致性。每个新增检查配正常对照和应失败反例。
- 语义复核：先人工检查 note 的满足声明与事实是否一致，保留原文和理由；不靠关键词匹配替代完整语义，也不为这几条 Case 引入 LLM Judge。
- 指标：分别报告原有结构/过程结果、时长可验证状态、满足目标情况。未知估时不能被总体 PASS 掩盖；新通过门槛在正式执行前确定。
- 数据：Stub 或工具返回替换验证的是对应组件与编排，不证明真实检索和模型行为；模型效果需另跑同批真实模型 Case。
- 开发对接：需要可固定的动作返回、实际拼装模型输入、完整计划与 note，以及贯穿的 trace_id；若选择估时，再要求计算依据与明细。现阶段不增加平台或整套 Observation 字段。

评审通过后再进入最小实现、Stub 反例与回归、同批 Live 验证。本轮完成标准为：现状能追溯，缺口清楚，场景与待确认决定可以一起讨论。
