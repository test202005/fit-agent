# iter-4 专项 PRD — 工具调用（Tool Use）

> 状态：v1 待评审
> 上游：[Agent 能力与评测全景](Agent能力与评测全景.md)、[何时该用 Agent](何时该用Agent.md)
> 前置：iter-1 意图识别、iter-2 抽取写入、iter-3 查询
> 范围：单轮工具调用 + trajectory 评测 + 双架构对比实验。**不含多步 ReAct 循环、不含 MCP。**

---

## 1. 为什么做这一轮

**这是 workflow 与 Agent 的分界线。**

前三轮里，模型只回答「这句话是什么」，**接下来干什么由代码写死**。加上工具调用后，模型第一次拥有「决定做什么」的权力——选哪个工具、传什么参数、要不要连着做几件事。

选它排第一的三条理由：

1. **JD 任职要求里明确列出**（Tool Use、Agent Framework 生态）
2. **失败模式大部分能确定性断言**，性价比最高（见 [能力全景](Agent能力与评测全景.md) 第二节）
3. **trajectory 评测到这一轮才真正成立**——前三轮没有决策空间，trace 只能用来排查，现在它变成被断言的对象

**交付**：工具调用链路 + trajectory 断言 + 工具评测集 + **双架构对比报告**。

---

## 2. 链路变化

**现在（固定链路）**

```
一句话 → 判意图 → 代码 if/else → 抽取写入 或 查询
```

**改为（工具调用）**

```
一句话 + 工具清单 → 模型选工具与参数 → 执行 → 结果回灌 → 模型给答复
```

**最大的变化：路由层没了。** 以前靠 `intent` 决定走哪条分支，现在模型直接说「我要调 create_record」——它自己完成了路由。

**下游三个节点的业务逻辑一行不改**，只是被包装成工具。这是刻意的：保证对比实验里两种架构的执行层完全相同，差异只来自决策方式。

---

## 3. 工具定义

三个工具，都是现成能力包一层：

| 工具 | 参数 | 底层 |
|---|---|---|
| `create_record` | exercise, weight_kg, sets, reps, duration_min, distance_km | iter-2 的 storage |
| `query_records` | date | iter-3 的 QueryExecutor |
| `count_exercise` | exercise, from, to | iter-3 的 QueryExecutor |

**决策 1：抽取节点在这条链路里不再需要。**
function calling 天然产出结构化参数，「模型抽字段 → 代码解析」这一步被工具参数取代。iter-2 的 extractor 保留在固定链路上，作为对比实验的一方。

**决策 2：工具参数沿用既有校验。**
`create_record` 的参数校验复用 extractor 的 `parse_extractor_output` 规则（类型、正数、字段集合），不重写一套。

---

## 4. 三条口径（评审重点）

| # | 决策 | 说明 |
|---|---|---|
| 1 | **保留意图识别，降级为兜底** | 模型一个工具都不选时，走原意图链路给出回应。同时它是对比实验的对照组，不能删 |
| 2 | **支持复合请求** | 「查一下今天练了什么，顺便记录我跑了3公里」→ 允许一次调多个工具。这正是固定链路做不到的部分，是本轮的核心价值 |
| 3 | **单轮，最多 3 个工具调用** | 不做多步 ReAct 循环。超过 3 个调用视为异常并终止。多轮推理留给 iter-5——一次只跨一个台阶 |

---

## 5. 失败模式与断言设计

本轮要覆盖的四类失败，**全部可确定性断言**：

| 失败模式 | 例子 | 断言方式 |
|---|---|---|
| **选错工具** | 该查记录却调了写记录 | 实际调用工具名 vs 期望 |
| **该调不调** | 问「今天练了什么」却不调工具、凭空编答案 | 断言必须出现该工具调用 |
| **参数幻觉** | 用户没说重量，参数里却填了 60 | 参数值必须能在用户输入中找到依据 |
| **工具报错不处理** | 工具返回错误，模型仍给出成功答复 | 注入工具故障，断言回应体现失败 |

**新增断言层 · trajectory 断言**

前三轮断言的是「结果对不对」，本轮新增「**过程对不对**」：

```
tool_sequence_equals     调用序列与期望一致（工具名 + 顺序）
tool_args_match          参数逐字段比对
no_extra_tool_calls      没有多余调用
first_divergence_step    失败时定位到第一个出错的调用
```

> **为什么要定位第一个出错的步骤**：早期错误会级联放大——第一步选错工具，后面全废。只报「最终结果错」等于没有归因信息。

**沿用不变**：四问结构、四态 Verdict、双口径报告、副作用快照。

---

## 6. 双架构对比实验（本轮最有价值的产出）

用**同一套评测集**，在两种架构上各跑一遍：

| 维度 | 记录什么 |
|---|---|
| 准确率 | Case 级 + 断言级通过率 |
| Token 成本 | 每条 Case 的输入/输出 token 数 |
| 响应耗时 | 端到端毫秒数 |
| 失败可定位性 | 失败时能否归因到具体步骤 |
| 复合请求 | 固定链路结构性做不到的部分，工具调用完成度 |

**不预设结论方向，以实测为准。** 预期形态见 [何时该用 Agent](何时该用Agent.md) 第六节。

**这个实验的意义**：市面上讲「Agent 怎么写」的很多，讲「**什么时候不该用 Agent**」的很少。做完之后，「该不该上模型」这件事就从口头判断变成了带数据的结论。

## 7. 评测集

新增 `eval/datasets/tool-dataset.jsonl`，约 25–30 条：

```json
{"case_id":"t-001",
 "input":"今天卧推60kg做了4组每组8次",
 "expected_tools":[{"name":"create_record",
                    "args":{"exercise":"卧推","weight_kg":60,"sets":4,"reps":8}}],
 "expected_tool_count":1,
 "assertion":"tool_sequence_equals",
 "category":"single-write","risk":"normal",
 "source":"prd-iter4-tooluse#3","views":["discovery"]}
```

覆盖：单工具写入 / 单工具查询 / **复合请求多工具** / 不该调工具（闲聊）/ 参数幻觉诱导（「练了3年的卧推」）/ 工具故障注入 / 超出能力范围。

**stub 模式**：按 `expected_tools` 生成模型的工具调用响应，验证编排与断言；**live 模式**才验证模型的真实选择能力。

---

## 8. 退出标准

1. Runner 一条命令跑完，stub 全绿
2. Live 三视图各连跑 3 轮，报告含工具选择混淆矩阵
3. **参数幻觉为 0**（三轮全部）——参数值必须能追溯到用户输入
4. **不该调工具的场景零调用**，尤其零写入
5. 工具故障注入时，回应必须体现失败，不得伪装成功
6. 任一失败 Case 能定位到**第一个出错的调用步骤**
7. **双架构对比报告产出**，五个维度均有实测数据

---

## 9. 定死决策清单

1. 保留意图识别链路，降级为兜底，同时充当对比实验对照组
2. 支持复合请求，一次可调多个工具
3. 单轮，最多 3 个工具调用，超出视为异常终止
4. 下游业务逻辑一行不改，仅包装为工具（保证对比实验只有决策方式一个变量）
5. 工具参数校验复用 extractor 既有规则，不重写
6. 新增 trajectory 断言层：序列、参数、无多余调用、首个分歧步骤
7. 同一 trace_id 贯穿全链路，工具调用作为独立 node 记录
8. 双架构对比是本轮硬性交付，不是可选项

## 10. 非目标

多步 ReAct 循环、Reflection 自我修正、Planning 任务拆解、MCP 协议、并行工具调用、多 Agent 协作、工具权限控制。
