# Agent 评测能力与项目实践总纲

> 更新：2026-09-21。本文承接传统测试经验，组织完整学习地图，并指导 fit-agent 与 PaiCLI 的分阶段练习。能力方向完整，每次实施只推进已确认范围。
> 状态：方法框架与实践候选；不代表全部能力已实现或本人已掌握。项目实现、运行结果和练习完成情况分别核查，不用功能清单替代学习证据。

## 一、总：要形成什么能力

接到一个 Agent 需求，能够定义任务成功，设计有覆盖的数据与实验，可靠执行验证，解释失败和不确定性，并支持修复、版本选择与持续改进。

```text
传统基础：需求分析、测试设计、自动化、接口、SQL、Linux、性能与排障
                                 ↓
           评测设计          评测工程          Agent 理解
        Task Definition    Eval Harness      ReAct / Planning
        Dataset / Golden   Batch Runner      Tool Calling / MCP
        Metrics / Criteria Fixture / 隔离     Context / Memory / RAG
        Human / LLM Judge  Trace / Grader     Multi-Agent / Computer Use
                          回归 / 版本 / CI   Long Horizon / Recovery
                                 ↑
                统计与实验：控制变量、抽样、波动、可信度
                                 ↓
                    Failure Analysis / Attribution
                                 ↓
             修复与版本决策 → 回归验证 → 数据和方法回流
```

能力树回答需要懂什么，工作流程回答拿到需求怎么开展，系统架构回答如何用程序执行。三者共同构成学习路线。

### 1. 传统测试经验如何承接

| 已有基础 | 在 Agent 评测中的用途 | 需要扩展的认识 |
|---|---|---|
| 需求分析、风险分析 | 定义任务、约束、范围和准出条件 | 允许多种正确答案，行为边界仍需明确 |
| 等价类、边界、组合 | 按意图、数据、上下文与权限设计覆盖 | 同义表达、模糊输入和多轮状态会改变行为 |
| 异常测试、故障注入 | 模拟超时、空结果、坏 JSON、工具错误 | 检查恢复、重复副作用和假完成 |
| 接口、SQL、数据库测试 | 验证工具参数、记录和最终状态 | “已保存”的回复要与实际写入核对 |
| Python、自动化、Linux | Runner、数据准备、结果归档、环境排查 | 记录模型和输入版本，管理概率性结果 |
| 性能测试 | 并发、吞吐、延迟、资源和成本 | 区分排队、模型、工具、重试及长任务开销 |
| 回归与缺陷管理 | 复现、影响分析、修复验证 | 区分随机波动、输入变化和真实退化 |

不必重学整套基础课；遇到工程缺口再补对应知识。传统测试同样关注过程、统计与反馈闭环，避免把它描述成只看最终 PASS。

### 2. 算法基础怎样落到 Agent 工程

Agent 系统里经常用到的基础算法，大多不是偏门知识，而是熟悉的数据结构和复杂度在具体工程问题里的落地。复习 LeetCode 的价值，不是为了背题，而是重新认识：上下文、记忆、工具和任务调度都有容量、时间和状态管理问题。

#### 已经在代码里出现的基础结构

| 算法或结构 | Agent 工程场景 | 需要真正理解的点 |
|---|---|---|
| 哈希表／字典 | 工具名到工具实现、Case ID 到结果、Trace ID 到事件 | 用空间换查找速度；同时要处理重复注册、缺失键和命名冲突 |
| 固定窗口 | 保留最近 N 条消息、限制事件或日志数量 | 窗口大小不是上下文理解；截断前要保护系统规则、任务目标和必要工具结果 |
| 队列 | 工具请求、异步任务、批量执行和事件消费 | 先进先出只是基础，真实系统还要处理优先级、取消、超时和幂等 |
| 栈／快照 | 计划状态、嵌套解析、最近一次可恢复状态 | 回退依赖完整快照或事件记录，不能只保存一个“上一步”引用 |

对应的经典练习可以从“两数之和、有效括号、队列、滑动窗口”开始，但要把题目改写成项目问题：工具注册冲突如何发现，上下文截断后哪些信息不能丢，失败重试如何不重复写入。

#### 记忆和检索优化会遇到的结构

| 算法或结构 | 可能的工程场景 | 边界与注意点 |
|---|---|---|
| 优先队列／小顶堆 | 从候选记忆或检索结果中取相似度 Top K | 适合维护候选集合；数据量大时还要理解向量索引、召回率和重排，不能把堆等同于完整 RAG |
| 二分查找 | 在按时间或分数排序的数据中定位范围；为 Token 预算寻找最大可放入前缀 | 必须满足有序和边界单调；Token 估算不是简单字符长度，需以实际 tokenizer 或保守预算为准 |
| 双指针／归并 | 合并两段已排序历史、去重相邻记录、扫描时间区间 | 只有数据有序且问题满足单调条件时适用；普通记忆去重不能默认套双指针 |
| 哈希集合 | 去重工具调用、动作、已处理事件和 Case | 需要先定义“相同”的键，不能只按文本完全相等去重 |

相似度检索的基本练习可以从 Top K 和排序开始；进入真实系统后，还要继续学习过滤条件、时间衰减、召回与精度的取舍，以及记忆作用域和隐私边界。

#### 复杂任务和多 Agent 中的搜索思想

复杂任务拆解、多 Agent 调度和工具依赖会出现图与搜索问题：任务可以表示成节点和依赖边，独立节点可以并行，依赖节点要等待前置结果。BFS、DFS、拓扑排序、优先队列等知识有助于读懂调度器和 DAG。

但不能把“有任务树”直接等同于“用了 BFS／DFS”。许多 Agent 的计划来自模型，执行过程还会动态改计划；这时更重要的是依赖校验、状态机、步数上限、取消和失败恢复。ReAct 死循环也不能简单用快慢指针判断，因为每次模型输出可能不同；工程上通常使用最大步数、重复动作或重复状态签名、进展检测和超时门禁。

学习顺序可以这样安排：先用哈希表、窗口、队列和堆解释现有代码，再用栈、图、拓扑排序和搜索理解 Plan、异步调度与 Multi-Agent。每学一种算法，都回答四个问题：数据是否有序或可哈希，资源约束是什么，异常如何恢复，怎样写一个能证明它有效的测试。

这部分与评测直接相连。算法实现错误会变成工具查找错、上下文丢失、任务重复、调度死锁或记忆污染；评测需要针对数据结构的前置条件、边界和失败状态设计 Case，而不是只测模型最终回复。

### 3. Agent 机制与质量目标

功能正确、过程合规、稳定性、性能、成本、安全、体验是质量维度；规划、工具、记忆等是系统机制。每个机制都可以从多个质量维度检查。

| 机制与关键词 | 要读懂的业务流 | 新增失败与验证对象 |
|---|---|---|
| Tool Calling / MCP | 工具发现、参数、执行、结果回灌 | 选错工具、参数幻觉、Schema 不兼容、结果误用、副作用 |
| ReAct | 行动、观察、下一步选择与停止 | 提前结束、无效循环、重复操作、结果回灌丢失 |
| Planning / Reflection | 拆解、依赖、执行、反馈修正 | 漏约束、依赖错、计划执行脱节、越修越错 |
| Context / Memory | 注入、压缩、检索、更新、作用域 | 关键事实丢失、旧约束覆盖新要求、跨用户污染 |
| RAG | 检索、排序、证据拼装与生成 | 没找到、找错、找到没用、引用不支持结论 |
| Multi-Agent | 分工、交接、并行、合并与审查 | 信息损失、重复工作、冲突、错误级联 |
| Long Horizon / Recovery | 长任务状态、检查点、中断和恢复 | 目标漂移、丢进度、重复写入、虚假完成 |
| Computer Use / Safety | 页面观察、操作、权限与外部内容 | 页面状态误判、越权、提示注入、误拦合法任务 |

历史材料使用 L0–L6 作为教学编号，可以继续理解旧文章；这些能力不是行业统一等级，也不要求按线性顺序实现。是否需要模型裁判，取决于可验证证据，不能由“到了哪一层”决定。任务完成可以通过测试、数据库和文件状态验证。

### 4. 当前阶段最应该强化的五项能力

这五项能力把上面的能力地图连到实际工作。看到一个 AI 需求，第一反应不应是“测哪些 Case”，而应先问：**这个 Agent 的任务成功，到底怎么定义？**

#### ① Task Definition：先定义任务成功

以运动计划为例，用户说：“一周三练，目标减脂，有膝伤。”最差的评测方式是“看生成计划好不好”。可执行的定义应拆成一组可检查的结果：

```text
Goal constraint satisfied?
frequency = 3?
injury constraint respected?
course/tool selection valid?
intensity valid?
plan executable?
final task completed?
```

每一项都可以留下 `0 / 1`、分数、理由和失败类型。这样才从“看起来不错”进入 Evaluation。评测人员不能自行把“膝伤”扩写成未经产品或专业人员确认的动作禁忌；缺少依据的部分应保留待确认或人工评审。

#### ② Golden Dataset：把数据变成评测资产

下一阶段不要停留在“准备 100 条测试数据”。数据集应按用途和风险组织，例如：

```text
dataset/
├── basic.jsonl
├── boundary.jsonl
├── adversarial.jsonl
├── long_horizon.jsonl
├── regression.jsonl
└── production_badcase.jsonl
```

这些可以是标签或视图，不要求一定拆成互斥文件。每条 Case 也不只是 `input`，还要能说明它为什么存在、怎样判断成功：

```json
{
  "case_id": "injury_001",
  "source": "confirmed_requirement",
  "user_input": "...",
  "expected_constraints": {
    "frequency": 3,
    "goal": "fat_loss",
    "avoid": ["high_knee_impact"]
  },
  "expected_tools": ["course_search"],
  "critical": true
}
```

Golden 的价值不在文件名，而在于预期经过核查、来源可追溯、前置条件可执行。它也不自动等于独立盲测集。调试集、回归集、生产 Bad Case 和独立验收集的用途要分开，避免用调优材料给自己验收。

#### ③ Judge：不同问题使用不同判定方式

不要把 Judge 简化成“用 GPT 给答案打分”。至少要能区分四种判定：

```text
Rule Judge
Executable Judge
LLM Judge
Human Judge
```

例如：

```text
Rule Judge：训练频率 == 用户指定的 3 天

Executable Judge：course_id = 123，查课程真实存在，且满足用户约束

LLM-as-a-Judge：训练计划是否符合已经确认的目标和规则

Human Judge：体验、表达和需要专业判断的内容
```

真正成熟的做法是不同问题使用不同 Judge，而不是所有结果一股脑交给大模型。代码能确定的字段、状态、调用参数和副作用，优先由程序判断；语义裁判需要 Rubric、人工样本、盲化或位置偏差检查；人工评审也要记录规则和分歧。

#### ④ Trace / Trajectory Evaluation：不能只看最终答案

普通文本评测常见的结构是：

```text
Input → Output
```

Agent 执行更接近：

```text
User → Intent → Plan → Tool A → Observation → Re-plan → Tool B → Final
```

一个典型结果可能是：

```text
最终答案：正确
Plan：错
Tool：调用了 3 次冗余工具
第 2 次参数错误
模型碰巧恢复
```

这时不能只记一个 PASS。应分别记录：

```text
Task Success = PASS
Planning Accuracy = FAIL
Tool Efficiency = FAIL
Recovery = PASS
Latency = HIGH
Cost = HIGH
```

发生恢复不自动等于规划失败，调用次数多也不自动等于质量失败；是否违反约束、是否超过预算、是否产生副作用，要按任务预期和对照实验判断。Trace 用来观察可验证的执行证据，不要求暴露模型内部思维过程。

#### ⑤ Failure Taxonomy：从“失败多少”走到“该改什么”

只报告“总共 100 条，通过 82，失败 18，成功率 82%”，研发仍不知道改哪里。应继续按失败类型拆解：

```text
18 failures

Intent          2
Planning        5
Tool Selection  2
Tool Params     3
Retrieval       2
Model           1
Data            1
Timeout         1
Judge Error     1
```

还可以继续向下分解：

```text
Planning Failure
    ├── 约束未继承：3
    ├── 训练日冲突：1
    └── 错误拆解：1
```

分类是排查入口，不等于已经证明根因。每条失败还要关联原始输入、实际输出、Trace、断言和环境；通过复现、控制变量或修复后回归，才能把“现象”“出错位置”和“根因”区分开。

这五项能力共同回答一条工作链：任务成功如何定义，数据如何证明，结果如何判定，过程如何观察，失败如何转成改动。后面的“拿到需求后怎样评”和“评测系统怎样运行”，分别展开这条链的工作步骤和工程实现。

## 二、分：拿到需求后怎样评

用“用户希望一周三练、目标减脂、提到膝伤”作为任务定义示例。它不是 fit-agent 当前功能承诺；业务与专业规则需另行确认。

### 1. Task Definition：先定义成功

先确认用户目标、明确约束、交付物、禁止行为和必要前置。要的是生成建议，还是还要保存计划并关联课程？频率如何计算？膝伤信息是否足够，哪些判断需要补充信息或专业依据？评测人员不自行编造医疗规则。

| 待验证事项 | 成功证据或待确认内容 |
|---|---|
| 一周三练 | 已确认的一周口径下，训练日数量为三 |
| 课程可用 | ID 在约定目录存在，状态与参数满足契约 |
| 约束被继承 | 规划、工具参数和最终产物使用同一组已确认约束 |
| 任务实际完成 | 若要求保存，检查持久化状态；仅生成时检查产物 |
| 专业适宜性 | 根据产品与专业规则评审，依据不足时不写成自动 PASS |

产出是任务定义、行为预期和待确认项。先分清哪些可以评，哪些暂时缺判断依据。

### 2. 链路、风险与可测试性

沿真实代码还原输入到结果：路由 → 数据获取 → 规划 → 工具 → 生成／写入；循环、异步和多个 Agent 按实际情况补上。

把规则计算交给单元测试，把工具协议与状态变化交给集成验证，再用端到端任务确认整体完成。检查五项条件：能准备并确认前置、能触发目标节点、能观察必要证据、能判定、能恢复或隔离。

开发未定接口时先约定能力，接口确定后再补字段。前置条件失败记 BLOCKED／ERROR，不算产品失败。黑盒评测可以先开展，过程不可见时限制归因结论。

### 3. Dataset / Golden：从覆盖到资产

| 分类维度 | 内容 | 用途 |
|---|---|---|
| 业务与输入 | 正常、边界、缺失、冲突、模糊表达、组合意图 | 检查需求覆盖 |
| 难度与干扰 | 多步、长上下文、对抗、工具故障 | 暴露能力边界 |
| 来源 | 需求、生产 Bad Case、人工构造、合成样本 | 解释存在理由与可信度 |
| 使用目的 | discovery／调试、regression／回归、独立验收 | 防止调优与验收混用 |

分类用标签或视图组织，不必一类一个互斥文件。一个边界 Case 也可以来自生产并用于回归。Golden 表示预期经核查、来源可追溯、条件可执行；不自动表示独立盲测。

以下是学习用结构示例，实际沿用项目已有 Schema：

```json
{
  "case_id": "weekly-plan-001",
  "source": "confirmed_requirement",
  "tags": ["basic", "frequency"],
  "fixture_ref": "profile-and-catalog-v1",
  "user_input": "每周安排三次训练",
  "expected_constraints": {"training_days": 3},
  "forbidden_behavior": ["write_without_confirmation"],
  "verifiers": ["training_days", "catalog_references", "write_audit"],
  "critical": false
}
```

工具预期只在业务或接口确实要求时固定，避免把合法替代路径判错。数据量由覆盖与实验目的决定，不用“凑够 100 条”替代设计。合成样本需要预期审核、去重及代表性检查；Bad Case 回流前先复现和归因。

### 4. Grader：选择并验证判定方式

| 方式 | 例子 | 需要练习的细节 |
|---|---|---|
| Rule Judge | 频次、字段、集合、调用参数与禁止行为 | 四问：承诺、该发生、不该发生、说做一致；配应该失败的反例 |
| Executable Judge | 查课程是否存在、查真实写入、执行产物测试 | 对照原始状态，验证执行成功不只看响应码 |
| LLM-as-a-Judge | 依据给定规则判断解释是否支持结论 | Rubric、盲化、位置偏差、冗长偏好、输出注入、校准 |
| Human Judge | 含糊需求、体验、专业判断与裁判分歧 | 统一规则、记录理由、复核分歧 |

Rule 与 Executable 都可以由程序实现，区分是为了理解证据来源，不要求四套框架。适用时输出 PASS／FAIL；语义待复核保留 REVIEW；运行异常单列。分数必须有定义，不用加权总分掩盖关键违规。

Judge 校准使用人工核查样本，覆盖正确、部分正确、看似流畅但错误和关键违规。分别看漏判、误判和分歧；Pairwise 可交换 A／B 位置检查偏差。阈值先定义理由和适用范围，不把 80% 或 90% 当通用标准。

## 三、分：评测系统怎样运行

### 1. Fitness Agent Eval 架构

下面是目标职责图，映射已有实现并逐步补缺口，不代表所有组件已经交付。

```text
需求 / 任务成功定义
        ↓
Dataset + Fixture + 版本与运行配置
        ↓
Eval Runner：准备与核查、隔离、执行、超时与清理
        ├───────────────┐
        ↓               ↓
     Agent v1        Agent v2
        ↓               ↓
   Response / Trace / 工具结果 / 文件与业务状态
        └───────┬───────┘
                ↓
           Judge Layer
      Rule / Executable / LLM / Human
                ↓
           逐 Case 判定结果
        ┌───────┴────────┐
        ↓                ↓
 Metrics + 统计分析   Failure Analyzer ← 原始运行证据
        └───────┬────────┘
                ↓
      Regression Report / 版本与修复决策
                ↓
        修复验证、Case 与经验回流
```

比较版本可顺序执行，关键是条件可比、状态隔离。Agent 执行环境与 Eval Harness 分工不同：前者完成任务，后者准备试验、收集证据并判定。

| 模块 | 输入 → 输出 | 验证重点 |
|---|---|---|
| Runner | Case、配置 → 各次运行产物 | 前置生效、终态确认、超时分类、重试记录 |
| Trace / Artifact Storage | 运行事件和业务结果 → 可关联证据 | case_id、run_id、trial、版本对应；脱敏与留存 |
| Judge Layer | 预期、产物 → 判定、理由、证据引用 | 判定器自身反例；语义与环境错误分开 |
| Metrics | 逐条结果 → 分项统计 | 分母、缺失值、异常比例、重复运行口径 |
| Failure Analyzer | 失败与轨迹 → 分类、假设、验证结论 | 先定位再归因，可先人工完成 |
| Report | 指标、失败、限制 → 对比与行动建议 | 不隐藏退化、费用和不确定性 |

执行结果保存后可重新评审。历史输出重评分、固定工具返回重跑模型、固定模型输出验证执行代码，证明的对象不同；回放不是开测前提。

### 2. 结果和过程分别看

一个任务最终成功，但经历了错误参数、工具报错和恢复，报告可以同时呈现任务成功、参数违规、恢复成功及实际耗时。调用次数多或发生恢复本身不等于失败，应对照明确预算、约束和故障条件。

Trace 记录可观察的执行，不要求内部思维链。检查最早可观察的异常及传播路径；定位到工具参数，不代表已经证明根因在模型，也可能是上下文、Schema 或数据问题。

### 3. 失败分类与验证

分类可从 Intent、Planning、Tool Selection、Tool Params、Retrieval、Data、Model、Infra、Judge 开始；按真实问题细分，不预建庞大字典。

每条问题记录：现象 → 失败断言 → 证据位置 → 原因假设 → 复现或对照 → 修法 → 同 Case 回归 → 证据边界。一个 Case 可以有多个症状，统计时说明是在数失败 Case 还是错误事件。

已有参考：[pl-004 闭环](../eval/reports/真实BadCase闭环-pl-004.md)、[问题清单](../eval/reports/问题清单.md)。

## 四、分：统计、性能与成本

### 1. 指标先回答具体问题

| 指标方向 | 先明确的口径 |
|---|---|
| Task Success / Constraint Pass | 完整任务还是单条断言；关键约束是否单列 |
| Intent / Tool Correctness | 任务级、调用级或参数级；合法替代工具如何处理 |
| Recovery Rate | 发生可恢复故障的试验数作为分母，不能拿所有任务算 |
| Reliability | 每个 Case 的重复运行、flaky、至少一次与全部成功 |
| Latency / Throughput | 墙钟时间、首输出与完成时间、并发、超时、P50／P95 |
| Cost | 输入／输出／缓存 Token、工具费用、重试及每任务费用 |

Token 不是费用；价格未知就报用量。少量任务的 P95 只作描述，不包装成稳定性能承诺。业务失败、REVIEW、基础设施错误与覆盖率分开呈现，展示有效分母。

### 2. 统计与实验学习清单

| 知识点 | 要能回答的问题 | 练习与验收 |
|---|---|---|
| 统计单位、分母 | 一条 Case 跑十次是否等于十个独立任务？ | 区分 Case、trial、断言，给同一结果写三种口径 |
| mean / variance / 分位数 | 平均值是否掩盖失败集中和长尾？ | 分任务类型计算、解释波动与超时 |
| 抽样、代表性、sample size | 数据覆盖什么分布？需要多少样本？ | 从覆盖、风险及估计精度说明取样理由 |
| confidence interval | 成功率估计有多大不确定性？ | 对二项成功率理解并应用 Wilson 区间；先检查独立性与样本范围 |
| 配对实验、效应大小 | V1 82%、V2 84%，哪些任务改善或退化？ | 冻结同批 Case，列配对结果与实际收益 |
| significance | 差异是否可能来自波动？ | 根据试验设计选择检验；二元配对可学习 McNemar，保留适用条件 |
| 重采样与相关性 | 重复轮次怎样影响区间？ | 学习按 Case 分组的 bootstrap，不把所有重复运行当独立样本 |
| inter-rater agreement | 人与人、人与 Judge 一致是否可靠？ | 一致率、混淆表、关键错误漏判；进一步理解 kappa 及类别分布影响 |

统计从已有实验学起，不以背公式为验收。覆盖有偏、预期错误、断言无效时，显著性无法补救。有限内部集合上的结论不能直接外推真实用户分布。

### 3. 怎样写版本对比报告

固定 Case、Fixture、代码或被控制的变更项、Prompt、模型参数和判定器版本；不一致项显式记录。先确定实验目的，再选择重复次数与预算，不默认三轮足以证明稳定。

报告应保留以下结构，数值必须来自运行：

```text
运行条件、计划任务数、有效执行与异常覆盖
任务成功 / 约束满足 / 工具正确性 / 恢复（适用才报）
逐 Case：改善、退化、持平、无法比较
稳定性与不确定性
调用数、Token、费用、延迟及测量边界
主要失败及证据
推荐选择、遗留风险、下一次实验
```

参考已有[两模型受控对比](../eval/reports/两模型受控对比评测报告.md)：输出长度兼容问题与模型语义能力分开解释；历史报告不含可靠延迟比较，不能补写不存在的结论。

### 2. 阶段目标，不设机械期限

1. **可信闭环**：从需求写出预期，准备并核查数据，执行、断言、保存证据；能解释一次失败与评测器错误的区别。
2. **差异与代价**：分析过程、恢复和级联影响，做受控版本比较，说明稳定性、成本与统计边界。
3. **持续改进**：数据与判定版本化、Judge 校准、变更回归、Bad Case 回流；反复手工作业成为瓶颈时再接 CI、聚合或 Dashboard。

已有证据可以直接作为起点。每轮从真实问题选两三项能力，不为了填满技能树重做已验证内容，也不删去暂未实施的学习方向。

### 3. 学习记录的最小单位

在对应迭代报告中记录：想弄清什么、理解的业务链路、设计的实验、实际结果、被推翻的判断、下一步。区分“读懂”“跟做”“独立完成”“已回归验证”，不要把项目现成功能直接算作个人掌握。

成果应能讲清：需求 → 成功标准 → 数据与判定依据 → 执行证据 → 原因验证 → 修复／版本选择 → 结论边界。这也是文章、面试和迁移到新公司的证据基础，不靠术语数量证明能力。

### 4. 原开发练手路线并入：四个可选练习

保留原路线的独立练习分支约定：动手改代码前选用隔离的练习分支，正式主线改动走项目迭代流程；未在本次创建分支或启动实验。旧练习没有完成记录，以下不标成已完成。先检查当前实现，已有故障支持就直接复用。

| 练习 | 怎么做 | 验收问题 |
|---|---|---|
| 读通一条请求 | `eval/run_intent_eval.py --views discovery --run-mode stub`；对照 router.py 与 trace.jsonl 的五类事件 | bad_request 为什么在模型之前结束？怎样证明没有调模型？ |
| 注入空响应 | 在 Stub 层复用或构造空字符串，检查解析错误和单测 | 为什么是 parse error 而非 API error？断言能否检出错误？ |
| 单轮 Tool Use | 对照 agent.py、tools.py、run_tool_eval.py，加入未知工具反例 | Schema、参数校验、执行各负责什么？与多步循环有什么区别？ |
| 抽取、查询与副作用 | 跟 pipeline.py、extractor.py、query.py，检查 complete／incomplete／invalid 和 Planner／Executor | 哪些输入不应写入？错误来自理解还是执行？ |

使用项目 `.venv/bin/python` 执行，凭证沿本地配置管理，不写入练习笔记。练习日志直接进入当次报告，不新增一份长期重复路线。

### 5. 学习取舍

模型原理优先理解 Transformer 基本工作方式、Inference、Sampling、Context、Embedding 如何影响质量；SFT、RLHF／RLAIF、DPO／GRPO 先建立概念与行为变化的联系，遇到训练评测任务再深入。LangChain、Ragas 等工具按具体用途学，不以熟记 API 为目标；新增 Demo 应服务尚未理解的问题。

独立验收集、人工盲评和统计深度由结论用途决定。用于版本决策也可能需要独立数据，不只有公开发数字时才需要。是否引入平台由协作、数据规模、检索和运行成本决定，不把“第二个人加入”设成唯一开关。
