# Agent 能力形态与评测方法全景

> **用途**：本项目后续迭代的规划依据。先铺开 Agent 的能力阶梯与各自的失败模式，再倒推「先做哪块、做到什么程度停」。
> **三个输入来源**：① Agent/LLM 评测岗 JD 的职责要求 ② 学界与工业界的能力分类与评测基准 ③ 本项目已有的方法论沉淀。
> **一句话原则**：**先立靶子，再倒推能力**——迭代顺序由「市场要什么 + 哪块是空白」决定，不由「链路还差什么功能」决定。

---

## 一、能力阶梯：从 workflow 到 Agent

行业对 Agent 能力的划分基本收敛为四块：**工具使用、规划与推理、记忆与上下文、多 Agent 协作**。代表范式是 ReAct（推理与行动交替）和 Reflexion（自我批评 + 记忆修正）。

按「模型的自主程度」排成阶梯：

| 层 | 形态 | 模型有多少决策权 | 本项目现状 |
|---|---|---|---|
| L0 | **固定 workflow** | 无。链路写死，模型只做单点判断 | ✅ 已完成（iter-1~3） |
| L1 | **Tool Use** | 选哪个工具、传什么参数 | ❌ 空白 |
| L2 | **ReAct 循环** | 做几步、每步做什么、什么时候停 | ❌ 空白 |
| L3 | **Reflection / 自我修正** | 判断自己错没错、要不要重来 | ❌ 空白 |
| L4 | **Planning** | 先拆解任务再执行 | ❌ 空白 |
| L5 | **Memory / 多轮上下文** | 跨轮次记住什么、怎么用 | ❌ 空白 |
| L6 | **多 Agent 协作** | 分派给谁、怎么交接 | ❌ 空白 |

**关键分界线在 L0 → L1**：有了工具选择，模型才第一次拥有「决定做什么」的权力。在此之前叫 workflow，之后才配叫 Agent。本项目目前是一个**做透了评测闭环的 L0**。

## 二、每层引入什么新的失败模式（测试人的核心关注）

**能力越强，失败模式越多，且越难用确定性断言覆盖。** 这是评测难度上升的根本原因。

### L1 · Tool Use

| 失败模式 | 说明 | 能否确定性断言 |
|---|---|---|
| 选错工具 | 该查记录却去写记录 | ✅ 可以 |
| 该调不调 / 不该调却调 | 明明要查数据却凭记忆编答案 | ✅ 可以 |
| 参数幻觉 | 工具参数编造出用户没提供的值 | ✅ 可以 |
| 参数类型/格式错 | 日期格式、单位错 | ✅ 可以 |
| 工具报错后不处理 | 拿到错误仍继续往下走 | ✅ 可以 |
| 调用顺序错 | 依赖关系没满足就调用 | ⚠️ 部分 |

> **一个关键判断**：早期的错误会**级联放大**——「弱计划、错工具、早期错误假设不会被局限在原地」，它会污染后面每一步。所以 Tool Use 的断言必须能定位到**第一个出错的步骤**，而不只是看最终结果。

### L2 · ReAct 循环

| 失败模式 | 能否确定性断言 |
|---|---|
| 循环失控（不停调工具，不收敛） | ✅ 可以（步数上限） |
| 提前停止（没做完就给结论） | ⚠️ 部分 |
| 推理与行动不一致（想的是 A，做的是 B） | ❌ 需要裁判 |
| 中间步骤都对，最终结论错 | ❌ 需要裁判 |

### L3 · Reflection

| 失败模式 | 能否确定性断言 |
|---|---|
| 该反思不反思（错了还往下走） | ⚠️ 部分 |
| 过度反思（对的也推翻，反复横跳） | ⚠️ 部分 |
| 反思后改得更错 | ❌ 需要裁判 |

### L5 · Memory / 多轮

| 失败模式 | 能否确定性断言 |
|---|---|
| 该记不记 / 该忘不忘 | ✅ 可以 |
| 指代消解错（"那就改成周三" 指向错对象） | ✅ 可以 |
| 上下文污染（旧信息干扰新判断） | ⚠️ 部分 |

### L6 · 多 Agent

| 失败模式 | 能否确定性断言 |
|---|---|
| 交接时信息丢失 | ✅ 可以 |
| 责任归属不清（错了不知道是谁的锅） | ⚠️ 靠 trace 分层 |
| 一个子 Agent 错导致全盘错 | ⚠️ 部分 |

**规律**：**L1 和 L5 的失败模式大部分能确定性断言，L2/L3 开始必须引入裁判。** 这决定了性价比——**先做能用代码断死的层**。

## 三、评测方法与指标对照

行业目前的四类核心指标，以及各自的判定方式：

| 指标 | 测什么 | 怎么判 | 本项目对应 |
|---|---|---|---|
| **Tool Calling Correctness** | 是否调了正确的工具、参数对不对 | **确定性**：实际调用 vs 期望调用，工具选择/参数/输出可分开评 | ❌ 无 |
| **Task Completion** | 整条轨迹下来有没有真的达成用户目标 | **LLM 裁判**：综合推理步骤、工具调用、最终回复 | ❌ 无 |
| **Reasoning Quality** | 推理相关性 + 推理连贯性 | **LLM 裁判** | ❌ 无 |
| **Trace-Based Evaluation** | 逐组件表现（检索、工具、规划、子 Agent 交接） | **确定性 + 裁判混合**，失败归因到具体组件 | ✅ **已有**（三层 trace + 事件断言 + 一致性断言） |

> **Trace-based evaluation 是本项目已有的最强项**，它的价值在于——**没有 trace，性能下降时你不知道是哪个组件坏了**。这一条已经做透，后续每加一层能力，trace 只需扩展节点，方法不变。

**一个诚实的区分**：本项目的 trace 断言目前只覆盖「事件完整性 + 结论一致性」，**不包括评估决策序列本身是否合理**——因为 L0 没有决策空间。到 L1 才会真正有 trajectory 可评。

## 五、倒推出的迭代顺序

排序依据三条：**① 补 JD 空白的价值 ② 失败模式能否确定性断言 ③ 实现成本**。

### iter-4 · Tool Use（最高优先）

**为什么排第一**：它是 L0→L1 的分界线，是「workflow」和「Agent」的分水岭；JD 任职要求里明确列出；失败模式**大部分能用确定性断言覆盖**，性价比最高。

一次带来三样 JD 要的东西：Tool Use 本身、真正的 trajectory 评测、execution-based evaluation 的深化。

**做到什么程度停**：2–3 个工具（查记录 / 写记录 / 算统计），覆盖「选错工具、参数幻觉、该调不调、工具报错不处理」四类失败。**不做复杂工具链、不做 MCP**。

### iter-5 · 多模型对比（低成本高回报）

同一套评测集跑两个模型，出对比报告。直接对上 JD 的「模型对比分析」，且**几乎不需要新方法**——现有 Runner 加一个模型维度即可。

**做到什么程度停**：两个模型、一份对比报告。**不做 leaderboard 系统**。

### iter-6 · ReAct 循环 + LLM 裁判首次实施

有了工具，自然进入多步循环。这一层开始出现**代码断不了的失败模式**（推理与行动不一致），正好是启用三级漏斗里第二级的时机——**方法论早就写好了，缺一次实施**。

**做到什么程度停**：步数上限、循环失控检测、一个最小 Rubric 的裁判（三态输出，不评分）。

### iter-7 · 多轮 Memory（原 Phase 2）

指代消解、追问补全。失败模式**大部分可确定性断言**，且是产品上真实需要的（iter-2 的 `incomplete` 状态本来就等着追问补全）。

### 明确不做 / 留口子

| 项 | 决定 | 理由 |
|---|---|---|
| **评测平台**（Web 界面） | **不做，只留口子** | 现在做是自嗨。触发条件：有第二个人需要用这套评测 |
| **多 Agent 协作** | **远期锚点** | 单 Agent 的评测都没做透，上多 Agent 是跳级 |
| **Planning / Reflection** | **远期锚点** | 依赖 L2 成熟 |
| **多模态评测** | 不在本项目 | 另有 CV 项目承载 |

## 六、这份文档怎么用

1. **规划迭代时**：先看第五节的顺序，再看该层「做到什么程度停」，避免过度设计
2. **写 PRD 时**：从第二节挑该层的失败模式，逐条转成用例设计的覆盖点
3. **判断要不要上裁判时**：查第二节的「能否确定性断言」列——**能用代码断的绝不上裁判**
4. **对外表达时**：用第三节的指标名称，不用大白话

**贯穿全篇的一条判断**：能力越往上，越依赖裁判，评测成本越高、可信度越低。所以**每一层都要先把能确定性断言的部分榨干**，再考虑裁判。这是本项目从 iter-1 就在执行的纪律，往上走不改。
