# 迭代一代码实现讲解

> 用途：先捋懂开发实现，再去做评测。给主人自己读，也给新会话的 AI 当实现导览。
> 对应代码：iter-1（Router 单节点链路 + 评测 harness）。行号以 2026-07-19 版本为准，代码变更后以实际为准。
> 练习路线（怎么亲手练）见 [Agent开发练手路线](Agent开发练手路线.md)，本文只讲"是什么、为什么"。

## 1. 一条请求的完整生命周期

```
route(text, llm, tracer)                          # router.py:47
  ├─ 生成 trace_id，发 input_received 事件
  ├─ 入参防御：空/纯空白/超500字符 → bad_request   # 不构造 prompt、不调 LLM
  ├─ 加载 prompt 文件 + 计算 sha256               # prompt 是文件不是代码，版本可哈希
  ├─ 发 llm_request 事件（model/prompt_hash/temperature）
  ├─ llm.complete(system_prompt, text)            # 唯一一次模型调用
  │    ├─ 超时 → llm_timeout
  │    └─ API 错 → llm_api_error
  ├─ 发 llm_response 事件（原始输出 + 耗时）
  ├─ parse_router_output(raw)                     # router.py:24 纯函数
  │    └─ 不合 schema → llm_parse_error
  ├─ 发 parse_result / result 事件
  └─ 返回 {ok, trace_id, intent, confidence, source}
```

五种结局对应五种 trace 事件组合——**事件序列本身就是断言目标**：

| 结局 | trace 事件 |
|------|-----------|
| 成功 | input_received → llm_request → llm_response → parse_result → result |
| bad_request | input_received → result（**没有 llm_request = 证明没调模型**） |
| llm_timeout / llm_api_error | input_received → llm_request → result |
| llm_parse_error | input_received → llm_request → llm_response → parse_result(ok=false) → result |

## 2. 逐文件讲解

### backend/llm.py（78 行）——模型抽象层

- `LLMClient` 是 Protocol（接口）：只约定 `complete(system_prompt, user_text) -> LLMResult`。router 只认接口，不知道背后是谁——这就是**依赖注入**，一切可测试性的地基
- `LiveLLM`：OpenAI SDK 指向 DeepSeek（`base_url` 替换），关键参数都是常量：`temperature=0`（分类要确定性）、`response_format={"type":"json_object"}`（官方 JSON Mode，让模型输出合法 JSON）、`max_tokens=100`（分类不需要长输出）、`thinking disabled`（速度优先）、`timeout 30s`、`max_retries=0`（重试会掩盖失败率，评测要看真实失败）
- `StubLLM`：测试替身。构造时注入剧本——固定返回文本，或抛指定异常。**故障注入只在这一层做**，router 对 stub/live 无感知，所以 stub 测的是 router 的真实代码路径
- SDK 异常 → 自家异常（`LLMTimeout`/`LLMApiError`）的翻译也在这层：业务代码永远不 import openai 的异常类型

### backend/router.py（102 行）——决策节点

三段式：**防御 → 调用 → 解析**。

- 防御段（:52）：不合法输入直接拒，省 token 也守边界。500 字符按 `len()`（Unicode 字符数）
- 解析段 `parse_router_output`（:24）是**全项目最重要的 20 行**："模型输出 → 程序数据"的关口。校验链：合法 JSON → 恰好两个字段 → intent 在枚举内 → confidence 是 0~1 数字（0~1 数字字符串归一化，PRD v4 决议，归一化次数计入报告指标）。任何一步不过 = `llm_parse_error`
- 为什么这道关口值得这么严：对照生产项目里常见的三种做法——裸文本 equals（零保护）、路由标记正则匹配（中）、这里的 JSON Mode + 严格校验（强）。关口越松，模型格式问题越会静默变成路由错误
- 统一判别结构：成功失败都带 `trace_id`，失败只有 `{ok, trace_id, error_code}`——响应形状可预测，评测断言才写得干净

### backend/trace.py（47 行）——可观测性

- 每个事件一行 JSON（trace_id / ts / node / event / payload），同时进内存列表和落盘文件——内存给测试断言用，文件给人工排查用
- 写盘失败不抛异常（`write_failed` 标记 + stderr logger）：**可观测性故障不能拖垮业务主链路**，但 Runner 会把 trace 缺失判 FAIL——"不崩"和"不漏"分开保证

### backend/prompts/intent_router_v1.txt（28 行）——Prompt 即代码

- 结构：任务说明 → PRD §3.4 十条规则的自然语言版 → 对比 few-shot（成对出现："改练深蹲5组"=record vs "改成休息"=reject，教模型边界而不是教答案）→ 防注入段 → 输出格式约束
- 两条纪律：①prompt 只许改表达不许改规则，规则变更先回 PRD；②few-shot 用过的句子不得进 locked/blind 评测集（防泄漏）
- 它是文件不是字符串常量：为了独立版本化（文件名带 v1，内容算 sha256 进报告）——**prompt 变更从此可审计**

### eval/run_intent_eval.py（377 行）——评测 harness，全项目最大的文件

评测代码比业务代码多，这是"可测试 Agent"的正常形态。五个机制：

1. **视图过滤**：`--views discovery|locked|regression|all`，故障 Case 只在 stub 模式跑（live 跑不了注入）
2. **stub 剧本生成**（:116）：普通 Case 直接按 expected_intent 生成固定响应——所以 stub 账里 intent 断言必然过，它验的是编排/契约/trace，不是模型质量（报告里有免责声明）
3. **双层断言**（:132）：intent（或 error_code）断言 + trace 事件集合断言，两者都过才算 PASS
4. **副作用快照**（:324/:337）：run 前后对 backend/ 和 datasets/ 做 mtime 快照比对，有意外写入直接报错退出——"评测不污染被测系统"的自证
5. **版本快照**（:349）：model / git_commit / prompt_hash / dataset_hash / 全部采样参数进报告头——每份报告可复现、可对比

指标层（:158）：混淆矩阵、分类别 P/R/F1、macro-F1、parse_error 单列且计入端到端失败、高风险错进 record 单独计数（`risk=high` 字段驱动，数据集加载时校验高风险类必须标记，:76）。

### tests/test_router_unit.py——确定性单测

只测纯逻辑（解析矩阵、防御边界、错误路径、trace 事件），不调真实模型、零 token。它和评测的分工：**单测保证"代码没写错"，评测保证"模型行为没变坏"**——两本账。

## 3. 还没有的三层（也就是"Agent"真正的部分）

| 缺的层 | 是什么 | 什么时候做 |
|--------|--------|-----------|
| 工具调用循环 | 模型选工具 → 代码执行 → 结果回灌 → 模型继续推理的 while 循环 | Backlog（计划生成场景才需要）；各类 Agent 框架的工具回调底下就是它 |
| 多轮 session | incomplete 状态保存、追问补全、跨轮指代 | Phase 2 |
| 多节点编排 | router 之后接 extractor/query 的分支执行 | iter-2/3 |

所以严格说，iter-1 是"带评测闭环的单节点 LLM workflow"——这正是对外表述里承诺的诚实说法，也符合 Anthropic《Building Effective Agents》"先 workflow 后 agent"的路径。

## 4. 开发 ↔ 评测的映射（捋完开发，评测就知道往哪打）

| 实现层 | 会怎么坏 | 对应评测手段 |
|--------|---------|-------------|
| prompt 规则表达 | 模型对边界句错分（负向否定进 record） | 黄金集分类断言 + 高风险零容忍 |
| 解析关口 | 模型格式漂移（confidence 带引号） | parse_error 率单列 + 归一化计数 |
| 错误翻译层 | 超时/API 错被吞或错分类 | stub 故障注入 + error_code 断言 |
| trace | 事件缺失导致失败不可定位 | trace 事件集合断言（缺即 FAIL） |
| 评测自身 | runner 污染数据 / 指标算错 | 副作用快照 + 单测覆盖指标函数 |
| 版本管理 | prompt 改了没人知道 | prompt_hash + git_commit 进报告（P0 教训） |

一句话总结：**每一层实现都有一种典型的坏法，每种坏法都有一个对应的断言**——这就是"可测试 Agent"六个字在代码层的含义。
