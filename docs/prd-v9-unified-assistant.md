## 1. 为什么做

当前三套入口各自独立：`/api/chat` 只认记录、查询、拒识；工具调用链路只有 3 个工具；训练安排、训练计划各有专用链路。调试台只能让用户手动选链路，选错就会出现「我只负责训练安排」这类答非所问（2026-09-25 调试台实测：训练安排链路下输入「今天中午做了一百个俯卧撑」被拒）。

本期回答两个问题：

1. 用户只面对一个聊天框时，助手能否正确分派、办完复合请求、在信息不够时先问？
2. 把专用链路合进一个助手后，工具选择与参数质量是否退化？退化出现在哪？

## 2. 用户能感受到的变化

| 档 | 示例 | 期望 |
|---|---|---|
| 不用选链路 | 今天中午做了一百个俯卧撑 | 记录俯卧撑 100 次 |
| | 把腿日放到最前面 | 调整训练安排 |
| | 给我一个 30 分钟下肢训练，新手 | 生成训练计划 |
| 跨能力复合请求 | 中午做了 100 个俯卧撑，顺便把腿日挪到最前面 | 记录一条 + 调整安排，回复同时说明两件事 |
| | 今天练了什么？再看看我的训练安排 | 查询 + 查看安排 |
| 信息不够先问 | 把那个挪到前面 | 不写入，反问挪哪个 |
| | 帮我记一下今天的训练 | 不写入，反问练了什么 |
| 超出范围 | 我今天吃了多少热量 | 不调工具，说明不支持 |

## 3. 设计

### 3.1 入口

新增 `POST /api/assistant`，`/api/chat` 保持不变，继续作为「固定链路」对照组。

| 字段 | 说明 |
|---|---|
| 请求 `text` | 必填，非空字符串 |
| 请求 `user_id` | 可选，默认 `demo-user` |
| 请求 `request_id` | **本期不接受**。现有存储按 `request_id` 做整请求幂等，同一请求内第二次 `create_record` 会被当成重放而不写入、却返回成功；统一助手每次写入由服务端生成独立 id。客户端重发导致的重复记录本期不防护，写入能力清单的已知限制 |
| 响应 `ok` / `trace_id` / `reply` | 是否正常结束、链路 id、给用户的一句话 |
| 响应 `actions` | 本次实际执行的工具与结果摘要，如 `[{tool, ok}]` |
| 错误 | 非法请求 400 `bad_request`；模型超时或接口错误返回 `ok=false` 与错误码 |

调试台默认链路改为「智能助手」，其余链路保留在下拉框供调试。

### 3.2 工具

| 工具 | 来源 | 说明 |
|---|---|---|
| `create_record` | iter-4 现有执行器 | 参数校验沿用 `validate_create_args` |
| `query_records` | iter-4 | 同上 |
| `count_exercise` | iter-4 | 同上 |
| `get_routine` | V8 | 同 V8 协议 |
| `set_routine_order` | V8 | 同 V8 v1 协议，不在本期修 |
| `generate_workout_plan` | 包装 V7 | 入参为用户原话 `request`，内部运行 V7 三步链路（planner → 动作库 → generator），返回计划或错误；V7 代码与评测基线不变 |

工具定义与执行器复用现有模块，不复制实现。

### 3.3 循环

- 独立实现 `run_assistant`，不修改 V8 的 `run_routine_agent`，V8 复现实验条件保持不变；V8 结束后再评估合并重复的循环代码。
- 单次请求最多 6 轮模型调用、最多 8 次工具调用，超出记 `max_rounds_exceeded` / `too_many_tool_calls`。
- 工具错误（参数校验、协议拒绝、子链路失败）以结构化结果回灌给模型，允许修正重试。
- 用户消息前注入当前时间（同 iter-4），相对日期由模型换算；评测按 Case 的 `now` 冻结时钟。
- 同一请求内以相同参数重复成功调用 `create_record` 视为重复写入，Runner 判 FAIL（硬门禁）。
- 新 Prompt `assistant_v1`，登记进 manifest。要点：只做清单内能力；写操作只在用户明确要求时发生；信息不够时先反问、不写入；复合请求逐项完成；回复如实说明每件事的结果，失败不说成成功。

### 3.4 Trace

沿用 V8 事件结构：`request`、`assistant_request`、`state_before/after`（训练安排全量）、`llm_round`、`tool_attempt`、`result`。`generate_workout_plan` 内部的 V7 事件用同一 `trace_id` 记录，便于展开子链路。子链路收到的是助手转述的 `request`，不是用户原话；Trace 同时保留两者，V7 白盒断言失败时先比对二者，区分「助手转述丢了约束」与「V7 解析错」。

评测视角新增通用「工具循环」视图：结论、执行步骤表、训练安排操作前后（有变化时）、本次写入的记录（有写入时）、子链路计划（调用时）。

## 5. V9.2 对比评测

### 5.1 数据集

| 来源 | 条数 | 用法 |
|---|---|---|
| iter-4 工具调用集 | 23（discovery 21 + regression 2） | 同一输入交给统一助手，按原期望工具与参数判定；locked 5 条不用，见下 |
| V8 训练安排集 | 27 | 同上，沿用 V8 分层判定 |
| V7 训练计划集 | 8（discovery） | 判定是否调用 `generate_workout_plan`，子链路结果沿用 V7 断言；regression 2 条为故障注入自测，不适用 |
| 新增 `assistant-dataset.jsonl` | 15～20 | 跨能力复合、需反问、超出范围、易混淆（如「帮我安排一下」在计划与安排之间） |

**复用规则**：

- **locked 不暴露**：V9.3 会调 `assistant` Prompt，V9.2 若跑 locked，这 5 条即被调优看过。locked 留到 V9.3 冻结后一次性验收。
- **期望随入口变化的 Case 重标**：原数据集按专用链路的职责写期望，换到统一入口后可能不同。例如 V8 `rt-b07`「帮我记一下今天跑了5公里」在训练安排链路期望不写入，在统一助手应调用 `create_record`。这类 Case 在统一数据视图中加 `assistant_expected` 覆盖原期望，原数据集文件不改；重标清单随数据集一起评审。
- **判定口径**：期望的工具须全部出现且参数匹配；多出写工具判 FAIL；多出只读工具（`get_routine`、`query_records`、`count_exercise`）只记观测，不判错。原 iter-4 的 `tool_count_equals`、`no_extra_tool_calls` 在统一助手下按此口径替换。

### 5.2 实验组

| 组 | 说明 | 回答什么 |
|---|---|---|
| 专用链路 | 各能力原有链路（iter-4 / V8 / V7） | 基线 |
| 统一助手 · 全部工具 | 6 个工具 | 合并后的真实表现 |
| 统一助手 · 同源工具 | 只给该 Case 所属链路的工具 | 把「循环方式不同」与「工具变多」两个变量分开 |

「专用 vs 全部工具」的差异里混有循环方式的影响；「同源工具 vs 全部工具」只差工具数量，才能归因到「工具变多」。

### 5.3 指标

- 工具选择准确率与混淆矩阵（期望工具 × 实际工具）
- 参数正确率（沿用各数据集原断言）
- 首次写入协议通过率（接续 V8 口径）
- 复合请求完成率：每件事都执行且结果正确才算完成
- 反问命中率：需反问 Case 未写入且回复为反问；回复语义部分记 REVIEW
- 越界调用：不该写却写、超出范围仍调工具，硬门禁为 0
- 轮数、token、耗时

报告按 `组 × 模型 × 轮次` 分节，沿用 pass@k / pass^k / flaky。

**成本口径**：统一助手每次请求至少多一轮「生成最终回复」的模型调用，专用的 iter-4 链路没有这一步。token 与耗时按「决策轮」和「回复轮」分开报，不直接下「统一更贵」的结论。

**预算与分阶段**：约 78 条 × 3 组。先每组 Live 1 轮探路，估算约 0.4～1.2M token（按单次 2～5k token 推算，未实测）；有差异的类别再补到 3 轮，不对全集盲目跑 3 轮。

### 5.4 验收

报告给出三组对比与退化定位（哪类 Case、哪一层）；硬门禁违规逐条列出 Trace。数字如实报告，不因退化调整数据集。

## 10. 自审修订（v0.2，2026-09-25 12:56）

| # | 问题 | 依据 | 修订 |
|---|---|---|---|
| 1 | **会静默丢记录**：若 `/api/assistant` 接收 `request_id` 并透传给每次写入，同一请求内第二次 `create_record` 被当成重放，不写入却返回成功 | `backend/storage.py` 以 `(user_id, request_id)` 做整请求幂等 | 本期不接受 `request_id`；重复写入列为硬门禁 |
| 2 | 复用 Case 的期望绑定在原链路职责上，换入口后会误判 | V8 `rt-b07` 期望「不写入」，统一助手应记录 | 统一视图加 `assistant_expected` 覆盖，原文件不改 |
| 3 | iter-4 断言要求工具数量相等、不许多调，统一助手多调只读工具会被误判 | `eval/run_tool_eval.py` 的 `tool_count_equals`、`no_extra_tool_calls` | 写工具精确、只读多调记观测 |
| 4 | V9.2 跑 locked 会让 V9.3 的验收集被提前看过 | 项目 locked 使用规则 | V9.2 只用 discovery / regression，locked 留给 V9.3 冻结验收 |
| 5 | 全集 3 组 × 3 轮成本未估 | 约 78 条 × 3 组 × 3 轮 | 先 1 轮探路，按差异补轮；估算标明未实测 |
| 6 | 未写时间注入，相对日期 Case 无法复用 | iter-4 Case 依赖 `now` | 注入当前时间，评测冻结时钟 |
| 7 | 计划子链路收到的是转述，出错时无法归因 | V7 planner 只看到传入文本 | Trace 同时保留原话与转述，先比对再归因 |
| 8 | 成本对比不公平：统一助手多一轮回复 | iter-4 单次决策无回复轮 | 决策轮与回复轮分开报 |

另核对：iter-4 数据集中没有依赖「单轮最多 3 个工具」上限的 Case，统一助手上限设为 8 不影响复用。

## 11. Trace 可读性：每轮输入与决策理由（v0.4，2026-09-25 13:12）

**目标**：在执行步骤表里看出每轮「模型看到了什么 → 为什么 → 决定做什么」。不改为经典文本 ReAct：函数调用已是其原生形态，文本解析更脆弱、更费 token。

**每轮输入**：`llm_round` 增加 `new_inputs`，只记本轮新增的用户消息或上一步工具结果（标注工具名）；系统提示词只在 `assistant_request` 记名称与 hash，不每轮重复。

**决策理由的三次尝试**（Live 冒烟，非评测）：

| Prompt | 做法 | 结果 |
|---|---|---|
| v2 | 要求调工具时在同一条回复里写一句理由 | 理由基本都有；但「帮我记一下今天的训练」这类不调工具的反问，把分析过程写进了给用户的回复 |
| v3 | v2 + 「直接回复用户时不写分析」 | 泄漏消失（3/3）；但简单单步调用多半不写理由，9 次工具调用只有 3 次有 |
| v4 | 改为每个工具必填 `reason` 参数，Prompt 同步说明 | 14/14 次工具调用有理由；4 次直接回复无泄漏；两次训练安排调整最终状态正确 |

**边界**：理由是模型给出的说明，不等于真实推理过程，只用于阅读链路，不作为根因证据。`reason` 只加在助手的工具副本上，iter-4 与 V8 共用的工具定义不变。v2、v3 文件保留作对照。
