## 1. 核心问题与交付

**核心问题**：数据已经写进去了，用户问一句自然语言，能不能拿到正确的答案？

**为什么它比前两轮难测**：前两轮每条用例都是独立的一句话进、一个结果出。查询**依赖前置数据**，而且**答案随时间变化**——这是本项目第一次遇到「测试环境本身要被控制」的问题。

**交付**：查询执行节点 + Clock 注入 + `POST /api/chat` + 查询评测集与报告。

## 2. 查询能力范围（先窄后宽）

只支持两类问题，其余一律返回「暂不支持」：

| 类型 | 例子 | 返回 |
|---|---|---|
| **某天练了什么** | 「今天练了什么」「昨天的训练记录」 | 那天的全部记录 |
| **某范围内某动作练了几次** | 「这周卧推了几次」 | 计数 |

**明确不做**：部位维度聚合（「这周练了几次腿」需要动作→部位映射表）、重量趋势、进步分析、跨用户对比。**不做的理由是它们需要词典或统计口径，属于另一个量级的问题，不是本迭代要验证的东西。**

## 3. 口径定死（本迭代最重要的部分）

> 这几条不定，测试只能猜，用例写不出唯一 expected。

| # | 口径 | 决定 |
|---|---|---|
| 1 | 「今天」的边界 | 自然日，本地时区 00:00:00 到 23:59:59.999 |
| 2 | 「昨天」「前天」 | 同上，按自然日往前推 |
| 3 | 「这周」起点 | **周一 00:00** 到当前时刻（不是往前七天） |
| 4 | 「最近 N 天」 | 含今天在内往前推 N 个自然日 |
| 5 | 返回排序 | **按写入时间倒序**（最新的在前） |
| 6 | `incomplete` 记录 | **计入查询结果**，但返回里带 `state` 标记，让上层能区分 |
| 7 | 查无结果 | 返回**空数组 + `ok: true`**，不是错误 |
| 8 | 动作名匹配 | **精确匹配**原文，不做同义词归一（「卧推」查不到「杠铃卧推」）——已知限制 |

**决策 3 说明**：选「周一起算」是因为用户说「这周」通常指日历周，不是滚动七天。这是产品口径，不是技术选择，写在这里就是为了让用例有唯一答案。

**决策 6 说明**：不完整记录也是用户记的，藏起来他会觉得数据丢了；但要标记出来，否则统计口径会失真。

## 4. 时间必须可注入（本迭代的技术关键）

**问题**：用例写「今天练了什么」，今天跑对了，明天再跑就错了——**用例会自己烂掉**。

**做法**：代码不许直接取系统时间，一律走统一入口，与 LLM、Storage 同样的形状：

```
LLMClient  →  LiveLLM      / StubLLM
Storage    →  JsonlStorage / FakeStorage
Clock      →  SystemClock  / FrozenClock     ← 本迭代新增
```

生产用 `SystemClock`；测试注入 `FrozenClock(冻结在某个时刻)`，于是「今天」永远是同一天，用例明年跑还是同一个答案。

**纪律（沿用全项目）**：任何让测试变慢、变贵或变不确定的依赖，都必须能被替换掉。时间是第三个，不会是最后一个。

## 5. 查询链路与契约

```
text → Router → intent=query → QueryPlanner(LLM) → QueryExecutor(纯代码) → 结果
```

**关键设计：把 LLM 和执行分开。**

- `QueryPlanner`：LLM 负责把自然语言变成结构化查询条件（**唯一的不确定环节**）
- `QueryExecutor`：纯代码按条件过滤记录（**完全确定，可用普通单测覆盖**）

```json
{"type": "list_by_date", "date": "2026-09-03"}
{"type": "count_by_exercise", "exercise": "卧推", "from": "2026-09-01", "to": "2026-09-03"}
{"type": "unsupported"}
```

**为什么这样切**：查询错了要能立刻分清是「没听懂用户」还是「查错了数据」。前者改 Prompt，后者改代码，责任完全不同。这是 iter-2「归因要能定位到层」的延续。

**响应契约**（沿用统一判别结构）：

```json
{"ok": true, "trace_id": "t-xxx", "intent": "query", "query": {...},
 "records": [...], "count": 3}
```

## 6. HTTP 入口（最小）

`POST /api/chat`，请求 `{"text": "..."}`，响应即上面的判别结构。

**只做这些**：一个路由、JSON 解析、异常兜底（不许把堆栈吐给调用方）。
**不做**：鉴权、限流、多用户、会话、并发控制。**理由：本迭代要验证的是链路端到端能通，不是做一个可上线的服务。**

## 7. 测试设计（本迭代的重点）

### 7.1 Fixture 隔离

**企业里的通行做法**：因为用数据库，隔离很贵，通常是「每条用例造数 + 跑完清理」，并行执行时还要给账号分池，避免互相踩。

**本项目怎么做**：因为存的是 JSONL，**每条用例给一个独立的临时文件**，天然隔离、跑完自动消失、并行也不冲突。这是企业想要但通常用不起的方案。

数据集里每条 Case 自带前置数据：

```json
{"case_id":"q-001",
 "fixture":[{"exercise":"卧推","weight_kg":60,"sets":4,"state":"complete","ts":"2026-09-03T10:00:00+08:00"}],
 "now":"2026-09-03T20:00:00+08:00",
 "input":"今天练了什么",
 "expected_count":1,
 "expected_exercises":["卧推"]}
```

`now` 字段就是注入给 `FrozenClock` 的时刻——**Case 自带时间**，所以永远可复现。

### 7.2 断言：集合断言，不比整个返回值

| 断言层 | 查询场景 |
|---|---|
| 第一问 · 契约 | `records` 是数组、`count` 与数组长度一致、`query.type` 在枚举内 |
| 第二问 · 目标 | 条数对；**该出现的记录出现了**；排序符合口径 5 |
| 第三问 · 保护 | **不该出现的没混进来**（边界外的记录、别的动作）；**查询零写入** |
| 第四问 · 一致 | 返回的 `query` 结构与 trace 中记录的一致 |

**第三问在查询场景尤其重要**：查询多返回一条边界外的记录，用户不会发现，但统计就错了。所以「边界外那条不能出现」必须显式断言，不能只断言「该出现的出现了」。

### 7.3 必测的时间边界

| 场景 | 为什么 |
|---|---|
| 记录正好在今天 00:00:00 | 下边界含不含 |
| 记录在昨天 23:59:59 | 差一秒就该被排除 |
| 周一查「这周」 | 只应返回今天的 |
| 周日查「这周」 | 应覆盖整周 |
| 跨月、跨年 | 「最近 7 天」跨月份边界 |

**这些用例只有靠冻结时间才写得出来**——这就是 Clock 注入的直接价值。

### 7.4 查询零写入

查询是只读操作。每条 Case 跑前跑后比对存储快照，**任何写入都算失败**。

## 8. 退出标准

1. Runner 一条命令跑完，stub 全绿
2. Live 三视图各连跑 3 轮，报告含查询类型混淆矩阵
3. **查询写入违规为 0**（三轮全部）
4. **时间边界用例全部通过**，且换一天再跑结果不变（证明时间已解耦）
5. 任一失败 Case 能凭 `trace_id` 定位到 Router / Planner / Executor 哪一层
6. `POST /api/chat` 冒烟：record 写入、query 读回，一条链路端到端跑通

## 9. 定死决策清单

1. 只支持「某天练了什么」「某范围某动作几次」两类，其余返回 unsupported
2. 「这周」= 周一起算，不是滚动七天
3. 返回按写入时间倒序
4. `incomplete` 记录计入结果，但带 `state` 标记
5. 查无结果返回空数组 + `ok:true`，不是错误
6. 动作名精确匹配，不做同义词归一（已知限制）
7. 时间走 `Clock` 注入，测试用 `FrozenClock`
8. LLM 只做 Planner，执行是纯代码
9. HTTP 只做一个路由 + 异常兜底，不做鉴权限流会话
10. 每条 Case 自带 `fixture` 与 `now`，用独立临时文件隔离

## 10. 非目标

多轮对话、上下文指代、部位聚合、趋势分析、鉴权、并发、多用户、前端页面。
