## 1. 为什么做这一轮

工作中观察到一类问题模式：

> 写工具要求提交**整份有序状态**，模型只按它**看得到的那部分**生成参数；协议校验拒绝后，模型重试补齐，最终成功。只统计端到端成功率时，这次首次失败被完全掩盖。

本项目复现的是**模式**，不是任何具体实现：领域、字段、工具名、错误码全部重新设计。

这个模式对应两个本项目尚未覆盖的能力台阶：

1. **有状态的写操作**：现有写工具只有追加式的 `create_record`，没有「读出状态、整体改写」的操作。
2. **工具错误回灌与有界重试**：`backend/agent.py` 目前单次决策、执行即结束，工具错误不回传给模型，因此「首次失败、重试成功」在现有架构里无法发生，也无法被观测。

本轮只回答一个问题：

> 模型调整有序状态时，首次参数在哪一层出错、为什么出错，最终成功是否掩盖了首次失败？

## 2. 产品设计

### 2.1 训练安排

每个用户有一份**训练安排**：按顺序轮换执行的训练单元列表。例如：

| 位置 | unit_id | 名称 | 状态 |
|---|---|---|---|
| 1 | `chest` | 胸日 | active |
| 2 | `back` | 背日 | active |
| 3 | `mobility` | 灵活性恢复 | paused |
| 4 | `legs` | 腿日 | active |
| 5 | `shoulders` | 肩日 | active |
| 6 | `cardio` | 有氧 | paused |
| 7 | `core` | 核心 | active |

- `active`：正在轮换，用户日常看到的就是这部分。
- `paused`：暂时不练（伤病、换阶段），不在默认视图里，但**保留在原顺序中**，恢复时回到原位置。

可见与不可见分离是产品本身的形态，不是为制造漏项而设：用户看到的是 active 视图，系统存的是全量顺序。

### 2.2 本期支持的用户操作

只做**调整顺序**，一次调整一个单元：

| 操作 | 示例输入 |
|---|---|
| 移到最前 | 「把腿日放到最前面」 |
| 移到最后 | 「核心放到最后练」 |
| 移到某项之前 | 「把肩日挪到背日前面」 |
| 移到某项之后 | 「腿日放到胸日后面」 |
| 查看 | 「我现在的训练安排是什么」 |

位置语义在**全量顺序**上计算，规则唯一：

1. 从全量顺序中取出目标单元，其余单元（含 paused）相对顺序不变；
2. 「最前 / 最后」插到全量顺序的首位 / 末位；
3. 「某项之前 / 之后」插到锚点单元紧邻的前 / 后。

因此每条 Case 的期望全量顺序可以由代码唯一算出，不依赖人工判断。

### 2.3 明确不做

- 新增、删除、暂停、恢复训练单元，交换两项，一句话多次移动
- 训练安排与训练计划生成（V7）的联动
- 接入 `/api/chat`：当前 HTTP 入口只走固定链路，工具调用链路仅由 Runner 驱动（iter-4 起如此）。本期沿用这一现状，不改意图路由；是否接入见第 11 节待决项
- 前端、并发写冲突、多用户协作
- 修复方案（属于迭代 B）

## 3. 链路设计

### 3.1 工具（v1 协议）

| 工具 | 入参 | 行为 |
|---|---|---|
| `get_routine` | `include_paused`（可选，默认 false） | 默认返回 active 单元（即用户日常看到的视图）；`include_paused=true` 时返回全部单元及状态 |
| `set_routine_order` | `order: list[unit_id]` | 用提交的顺序整体替换全量顺序 |

`set_routine_order` 的 v1 协议校验：`order` 必须是**全部单元（含 paused）的一个排列**，无缺失、无重复、无未知 id。不满足时拒绝写入，返回错误码 `incomplete_order` 与一句协议说明（「必须提交全部训练单元的完整顺序」），**不列出缺哪几项**。

工具描述如实说明两件事：`get_routine` 默认只返回 active，`set_routine_order` 必须包含全部单元。协议信息是给全了的，模型是否在首次调用时用上，正是要观测的对象。

v1 是一个正常的第一版设计：整体替换协议简单、后端校验直接，很多系统都这样起步。代码和 Prompt 中**不预埋任何错误**；失败率多少就记多少。

### 3.2 执行循环

新建独立入口 `run_routine_agent`（独立 Prompt `routine_agent_v1`），不改动现有 `run_agent`，避免影响 iter-4 的 28 条工具评测基线。

```text
用户输入
  → 第 1 轮：模型决策（通常调 get_routine）
  → 执行，结果回灌
  → 第 2 轮：模型决策（通常调 set_routine_order）
  → 执行；若协议拒绝，错误回灌
  → 第 3 轮起：模型可重试
  → 模型给出最终文字回复，或达到轮数上限
```

- **轮数上限**：单次请求最多 5 轮模型调用，超出记 `max_rounds_exceeded`，不写入。
- LLM 统一入口需新增按消息序列调用的方法（现有 `complete_with_tools` 只支持单轮 system + user），Live 与 Stub 同时实现。
- 写入只在协议校验通过后发生；成功后又重复写入的次数记入 L3 观测，不拦截。

### 3.3 存储

新增训练安排表（字段：`user_id`、`unit_id`、名称、状态、全量位置、`updated_at`、`trace_id`），与训练记录同库。**这是一次 Schema 新增**，实现前需主人单独确认。Fake 实现同步提供，Stub 回归不依赖文件。

Case 的初始安排由 Fixture 写入，Runner 每条 Case 前重置，保证可复跑。

## 4. Trace 记录项

只补本链路需要的字段，不整体重构 Trace 结构。沿用 `backend/trace.py`，同一 `trace_id` 贯穿。

| 事件 | 关键字段 | 用于 |
|---|---|---|
| `routine_request` | 模型、Prompt 名/版本/hash、温度、工具清单、Fixture id、实验组 | 版本证据 |
| `llm_round` | `round`、发送的消息条数、返回的 tool_calls、文字长度、耗时、usage | 每轮决策可见 |
| `tool_attempt` | `round`、`attempt`（该工具第几次调用）、工具名、完整入参、`ok`、错误码、错误信息、输出、耗时 | **首次参数断言的对象** |
| `state_before` / `state_after` | 全量顺序（含状态） | 落盘断言 |
| `result` | 最终状态、总轮数、写入次数、最终回复原文 | 结束状态与回复层 |

`eval/trace_view.py` 需能按轮次还原这条链路，一眼看出「第几轮、调了什么、传了什么、被拒原因、重试后传了什么」。Trace 契约（`eval/trace_contract.py`）增加本链路的节点序列声明。

## 5. 分层判定

每条 Case 按层分别判定，**不合并成一个结论**：

| 层 | 判定内容 | 性质 |
|---|---|---|
| L1 意图 | 需写入的 Case 调用了 `set_routine_order`；不应写入的 Case 未成功写入；「已在目标位置」类 Case 写或不写均可 | 门禁 |
| L2 首次参数 | 第一次 `set_routine_order` 的 `order` 通过协议校验 | **核心观测** |
| L2' 首次语义 | 第一次提交的顺序等于期望全量顺序（协议通过但顺序错也算失败） | 核心观测 |
| L3 执行 | 写工具尝试次数、是否触发重试、是否超出轮数上限 | 观测 |
| L4 最终状态 | 落盘全量顺序等于期望；非目标单元相对顺序不变；paused 单元仍在且状态未变 | 门禁 |
| L5 回复 | 记录最终回复原文，供人工核对是否与最终状态一致；本期不做关键词判定 | 观测 |

Case 级四态沿用项目契约：门禁层（L1、L4、Trace 契约）全部通过且 L2 / L2' 无异常为 PASS；门禁通过但 L2 或 L2' 失败为 REVIEW；门禁失败为 FAIL；模型调用超时、接口异常或 Trace 写入失败为 ERROR。

**关键**：一条「首次协议被拒、重试成功、最终状态正确」的 Case，L4 为 PASS，但 L2 为失败，Case 整体记 REVIEW 并单列，**不得计为干净通过**。

## 6. 指标

报告按 `模型 × 轮次` 分节，并汇总：

| 指标 | 定义 |
|---|---|
| 首次协议通过率 | L2 通过的需写入 Case / 需写入 Case（以下「需写入 Case」均指期望发生写入的 Case） |
| 首次顺序正确率 | L2' 通过 / 需写入 Case |
| 最终状态正确率 | L4 通过 / 需写入 Case |
| 被掩盖失败数 | L2 失败且 L4 通过的 Case 数 |
| 平均写工具尝试次数 | 需写入 Case 的 `set_routine_order` 调用次数均值 |
| 缺失项构成 | 首次被拒时，缺失 id 中 paused 单元的占比 |
| pass@k / pass^k / flaky / token | 沿用 `eval/stability.py` 口径 |

「首次协议通过率」与「最终状态正确率」的差值，就是端到端指标掩盖掉的部分。

## 7. 数据集

新增 `eval/datasets/routine-dataset.jsonl`，视图如下：

| 视图 | 规模 | 内容 |
|---|---|---|

## 8. 复现与归因

### 8.1 复现判据（事先写死）

v1 在 discovery 视图 Live 3 轮（默认模型 `deepseek-v4-flash`，温度沿用默认）：

- **复现成功**：出现至少 1 条「L2 失败、L4 通过」的 Case，且有完整 Trace 可还原。
- **v0.5 调整**：正式复现改由第 14 节基线组承担，温度改为 0.7（温度 0 下重复运行结果基本一致，多轮没有信息量）；判据不变。此前默认温度下的冒烟与手工触发只作线索，不作为正式证据。
- **discovery 未复现**：启用 pressure 视图 Live 3 轮，判据相同。
- **仍未复现**：如实记为「在当前模型与规模下未复现」，作为结论写入报告，不修改 Prompt 或 Fixture 去制造失败。是否继续迭代 B 由主人决定。

### 8.2 归因对照

复现后，用同一批 Case、同一模型做对照，只改一个变量：

| 组 | `get_routine` 返回 |
|---|---|
| A（v1 默认） | 只返回 active 单元 |
| B（对照） | 返回全部单元，并标明状态 |

各 Live 3 轮，比较首次协议通过率与缺失项构成：

- B 组显著改善且 A 组缺失项主要为 paused 单元：原因定位为**上下文未提供全量状态**。
- B 组仍有较多缺失或错序：原因包含**模型维护整份列表本身不稳定**，修复不能只靠补上下文。

对照组只用于归因实验，不作为产品默认行为，也不在本期上线。

## 10. 迭代 B 方向（本期不做）

- **协议改为只传操作**：`move_unit(unit_id, position, anchor)`，全量顺序由代码计算，模型不再维护整份列表。

| 4 | 「成功后再写入记异常」会把确认性重写误判为失败 | 改为 L3 观测计数 |
| 5 | Case 四态中 REVIEW 的触发条件不明确 | 写明：门禁通过但 L2 / L2' 失败为 REVIEW |
| 6 | 指标分母「调整类 Case」含义不清 | 统一为「期望发生写入的 Case」 |

## 14. 漏项自救归因实验计划（v0.5，按评审修订；v0.4 初稿，2026-09-25 22:22，待主人确认）

本节细化并替代 8.2。8.2 只对比「读取是否返回全部单元」一个变量；逐轮拆解后发现还有更具体的因素，改为下面的设计。

### 14.1 要回答的问题（总）

> **什么因素决定了模型能不能第一次就提交对、提交错了能不能自己救回来？**

对应「效果 = 模型能力 × 环境设计」：分清哪些靠模型，哪些靠环境。

**两把尺子**：
- **用户价值**：这类失败对用户不可见，但每次多花约 2 轮和一半以上的 token，偶发时还会把暂停单元挪位（用户看不到、恢复后才发现）。找到关键因素，就能用最小改动减少隐藏失败和成本。
- **AI Native**：实验只改「模型收到的信息」（工具描述、读取结果、报错），不改补救路径，不写死「被拒就重读」；验证的是「环境设计让正确的事容易做」这条原则。

### 14.2 第一条线：逐轮拆解（已完成）

基于主人手工触发的 trace `t-ebfc7878-04d5-4b04-973c-39ab5a00e7c6`，每轮按「手里有什么信息 → 做了什么决定 → 结果」拆开并归类，完整表格见 [ReAct 实例](../eval/reports/ReAct实例-训练安排被拒后自我修正.md)「逐轮拆解」一节。结论：

| 轮 | 归类 | 说明 |
|---|---|---|
| 1 | 信息给了，没用上 | 「默认只返回进行中」与「写入必须包含全部」分别写在两个工具描述里，需要组合推理，模型没连上；理由却写「读取全部」 |
| 2 | 信息没给到 | 读取结果没提示还有 2 个暂停单元未列出，模型把 5 个当成全部 |
| 3 | 用上了，推对了 | 报错与读取结果都没提「暂停」，**自救线索唯一来源是工具描述** |

### 14.3 第二条线：对比实验（待做）

一次只改一个变量，其余与基线一致：

| 组 | 改什么 | 改动位置 | 要回答的问题 | **主指标** |
|---|---|---|---|---|
| 基线 | 不改（v1） | - | 参照；兼作 8.1 正式复现 | 全部指标 |
| A 去线索 | 工具描述去掉「默认只返回进行中；include_paused 返回全部」的说明，参数仍在 | `backend/routine_agent.py` 的 `TOOL_SCHEMAS` | 没有这句说明还能不能救回来？（验证第 3 轮） | **自救率** |
| B 报错具体 | 被拒时列出缺了哪些单元 | `backend/routine.py` 的 `validate_order` | 能不能少走一轮？ | **平均写入次数、平均轮数** |
| C 提示隐藏项 | 默认读取结果附上「另有 N 个已暂停单元未列出」 | `backend/routine_agent.py` 的 `_execute` | 能不能第一次就提交对？（验证第 2 轮） | **首次通过率** |
| D 信息集中 | 写入工具描述直接写明「提交前先用 include_paused=true 读取全部单元」 | `backend/routine_agent.py` 的 `TOOL_SCHEMAS` | 两条线索集中到一处，第 1 轮能否直接读全？（验证第 1 轮） | **首次通过率**、第 1 轮是否带 include_paused |

**主指标以外的指标只作观察，不用来下结论。** 例如 C、D 组若让多数 Case 首次即通过，被拒的只剩一两条，这两组的自救率没有意义。

**A 组的已知干扰**：参数名 `include_paused` 本身就是线索。A 组测的是「去掉描述说明、参数名仍在」，不是「完全没有线索」。若 A 组自救率仍高，只能说明「参数名已足够提示」，不能得出「工具描述不重要」。本期不再加改参数名的组，以免一组同时改两个变量。

D 组改的仍是模型收到的信息，不写死补救路径，符合 AI Native 基调。

**实现方式**：三个变体做成实验开关，只由评测 Runner 通过组名打开；产品默认行为不变。Trace 与报告记录组名。

**不做**：换更弱的模型（目前只有 flash 与更强的 pro）；协议改为只传操作（属迭代 B，等本实验结论）；统一助手链路（用 V8 专用链路，变量更干净）；其他场景。

### 14.4 数据与规模

- 数据：V8 discovery 12 条（Fixture base7，四种移动操作 × 不同位置）。
- **温度 0.7**：温度 0 下同一输入结果基本一致，重复跑没有意义。
- 分两步控制成本：
  1. 每组各跑 1 轮：5 组 × 12 条 = 60 次，按已有实测单次约 3～5k token 估算，约 25 万 token；**基线组在 0.7 下重新跑，不复用此前默认温度的结果**；
  2. 只对「差异不清楚」的组补 2 轮（条件见 14.5），上限再加 35 万。
- **预算上限 60 万 token**，到上限即停，报告已有结果。
- 更正：此前口头估算「15～25 万」只算了单轮，按 3 轮全跑应为约 60 万。

### 14.5 指标与判定（事先写死）

| 指标 | 定义 |
|---|---|
| 首次通过率 | 第一次提交即通过协议校验 |
| 自救率 | 首次被拒的 Case 中，最终状态正确的比例 |
| 平均写入尝试次数、平均轮数、平均 token | 每条 Case |
| 最终状态正确率 | 沿用 V8 L4 口径（含暂停单元相对位置不变） |

判定只看各组**主指标**，与基线相比（事先写死，看到结果后不改）：

| 主指标差距 | 结论 | 动作 |
|---|---|---|
| ≥ 20 个百分点（轮数、写入次数类为差 ≥ 0.5） | 明显差异 | 不补跑 |
| 10～20 个百分点（或差 0.25～0.5） | 差异不清楚 | 该组与基线各补 2 轮，按 3 轮合计重新判定 |
| < 10 个百分点（或差 < 0.25） | 无明显差异 | 不补跑 |

报告一律写**条数**（如「3/12」），不只写百分比：12 条里 20 个百分点约等于 2～3 条，温度 0.7 下的随机波动可能就有这么大。结论只适用于本场景、本模型。
