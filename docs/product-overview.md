## 一句话

一个纯对话的个人健身训练助手——用自然语言跟它说话，它帮你记训练、查历史。**当前聚焦自然语言记录与查询训练历史；远期可能探索档案与计划生成，但不作为当前承诺**。没有表单、没有按钮、不接手环，**对话是主要入口**（交互原则：对话优先，远期即使做前端也不引入表单式主流程）。

对标产品：Keep 卡卡（健身教练 Agent，2025.03 发布，[新浪财经报道](https://finance.sina.com.cn/tech/shenji/2025-03-26/doc-ineqxtzx9234398.shtml)、[OSCHINA](https://www.oschina.net/news/341108)）、Fitbod（基于训练历史生成个性化训练，[官方帮助文档](https://help.fitbod.me/hc/en-us/articles/360004429814-How-Fitbod-Creates-Your-Workout)）、[W8Log](https://www.w8log.app/) / [FitLog AI](https://www.fitlogai.com/)（自然语言记录）。本项目不与成熟健身平台比功能数量，而是聚焦一个更窄的问题：**如何让自然语言训练记录既方便，又不会因为 AI 的不确定性而乱记、漏记或无法追溯。**

## 为什么做

这个项目同时解决两类问题，两层价值不能割裂。

### 1. 面向消费者：降低训练记录成本

规律训练者一次可能完成多个动作，每个动作又包含重量、组数、次数、距离或时长。现有记录方式通常需要逐项填写表单，或者先记在备忘录、训练后再补，容易因为操作麻烦而漏记或放弃记录。

fit-agent 验证一个产品假设：

> 对有训练记录需求、但嫌表单操作麻烦的规律训练者，能否用一句自然语言完成记录，并通过对话快速查回历史？

例如，用户说：

> 今天卧推60kg 4组8次，深蹲80kg 5组5次，跑步20分钟。

系统将它转换为结构化训练记录。之后用户可以直接问“我上次卧推多少”“这周练了几次”，不需要重新翻找备忘录或逐页筛选。

消费者得到的核心价值是：

- 降低训练后补记录的操作成本。
- 将零散自然语言变成可查询的结构化历史。
- 更容易回顾上次训练内容，而不是依赖记忆。
- 对不完整、否定或未来时态的输入不乱写数据。

这个价值目前还是待验证的产品假设。项目不会预设“对话一定比表单好”，而是通过真实用户体验继续验证记录耗时、修正率、重复使用和查询使用情况。

### 2. 面向 AI 测试能力：建立可测试 Agent 参考实现

自然语言入口降低了操作成本，也带来了新的质量风险：

- “今天没练卧推”可能被错误识别为训练记录。
- 缺字段输入可能被模型擅自补全。
- 多条训练可能只写入一部分。
- 多轮追问可能挂接到错误的历史状态。
- 模型更新后，原本正确的边界可能发生回归。

因此，本项目从第一条能力开始内建数据集、expected、Trace、分层断言、Stub 回归和真实模型评测，让失败可以复现、定位和进入长期回归。

这条线同时服务三个目标：

- 复演并验证 Agent 意图识别、结构化抽取和多轮测试方法。
- 将方法和 Bad Case 反哺实际 AI 项目。
- 形成可以公开、复用和面试展示的 AI 测试工程作品。

### 两层价值怎么连接

```text
消费者需要更低摩擦的训练记录
  → 对话减少表单操作
  → 自然语言带来否定、时态、缺字段和多轮歧义
  → 错误记录会直接破坏用户信任
  → 必须建立可评测、可追溯、可回归的质量体系
```

项目最终要证明的不是“做出了一个会聊天的健身 Demo”，而是：

> 如何把方便但不确定的 AI 交互，做成一个结果可信、错误可发现的真实产品能力。

## 目标人群

### 产品用户

主要面向：

- 每周规律训练2～5次的人。
- 有记录习惯或记录需求，但嫌表单操作麻烦的人。
- 习惯在训练后集中复盘，希望一句话完成记录的人。
- 主要需要快速记录和历史查询，不依赖专业教练服务的人。

不重点服务：

- 需要医疗、康复或专业训练处方的人。
- 已深度使用专业训练 App、需要逐组计时和复杂图表的用户。
- 依赖手环自动采集、实时动作指导或社交功能的用户。

### 项目受众

- AI 测试岗位的招聘经理和面试官：关注是否具备从需求到评测闭环的能力。
- AI 项目与测试负责人：关注方法能否用于真实 Agent 质量建设。
- Agent 开发和测试从业者：关注数据集、Runner、Trace 和断言能否复用。
- 正在学习 AI 评测的人：关注能否通过完整案例理解测试方法。

## 核心卖点

### 对消费者

> 一句话记训练，随时查历史；不靠模型自由发挥，重点保证不乱记、能定位。

### 对项目受众

> 一个从第一行代码就内建数据集、Trace、断言和回归能力的可测试 Agent 参考实现。

可证明的四项差异：

1. **可测**：每项 Agent 能力都有数据集、expected、指标和退出门禁。
2. **可追溯**：失败可通过 traceId 定位到输入、Prompt、模型输出、解析和业务节点。
3. **可复跑**：Stub 回归与真实模型评测分账，结果可以重复运行和版本比较。
4. **可学习**：逐迭代展示意图识别、结构化抽取、多轮上下文分别应该怎么测。

## 传播方向

项目不等全部功能做完再推广，而是每完成一个迭代，就用真实评测产物讲清一个质量问题：

| 迭代 | 对外主题 | 可展示证据 |
|------|---------|-----------|
| Iteration 1：意图识别 | 三分类 Agent 为什么不能只看总体准确率 | 边界表、混淆矩阵、重复运行、否定句 Bad Case |
| Iteration 2：结构化抽取 | Agent 抽取错误为什么可能造成错误写入 | 字段级指标、三态、原子写入、Stub 与真实模型分账 |
| Iteration 3：单轮闭环 | 如何给 Agent 建立可复跑、可定位的评测流水线 | Runner、端到端 Trace、分层报告、Bad Case 回归 |
| Phase 2：多轮状态 | 多轮 Agent 的错误挂接和状态污染怎么测 | 多轮数据集、上下文断言、Trace 回放 |

传播渠道按职责区分：

- **GitHub**：代码、数据集、运行方式和评测报告的事实源。
- **小红书/短内容**：用一个真实 Bad Case 解释一个 AI 测试问题。
- **技术文章**：完整呈现问题、官方依据、数据设计、断言、结果和优化过程。
- **简历与面试**：证明从需求评审到 Bad Case 回归的完整 AI 质量建设能力。

项目传播不只看 Star，还关注评测报告、稳定复现并关闭的 Bad Case、方法复用、内容收藏与技术交流，以及是否帮助清晰讲出 AI 测试项目经验。具体选题与发布节奏等产生真实迭代素材后，再单独制定推广计划。

## 终态的一天

```
你：今天卧推 60kg 做了4组每组8次，然后深蹲 80kg 5组5次
它：已记录 2 条：卧推 60kg 4×8、深蹲 80kg 5×5（2026-07-19）

你：今天练了胸
它：具体做了什么动作？重量和组次多少？        ← 多轮补全（Phase 2）
你：上斜卧推 40kg 3组10次
它：已记录：上斜卧推 40kg 3×10

你：这周卧推了几次
它：本周卧推 3 次：周一 60kg 4×8、周三 65kg 3×6、今天 60kg 4×8

你：帮我写周报 ／ 明天打算练腿 ／ 今天没练，休息
它：（拒识，不产生任何记录——只记已发生的训练事实）

―――― 以下是远期 Backlog ――――

你：我 75kg，目标增肌，一周能练 4 天          ← 档案填槽
你：帮我排下个月的训练计划                    ← 计划生成（查历史 → 评估 → 生成）
```

## 数据从哪来

当前业务数据来自用户对话抽取的训练记录；评测数据全部使用合成输入。种子画像在远期探索档案/计划能力时才引入。不接 HealthKit / 穿戴设备——产品交互参考 [Hevy](https://www.hevyapp.com/) 等手动训练记录类应用；对话式记录（自然语言 → 结构化数据）正是本项目要展示的核心链路。

| 阶段 | 用户能干什么 | 状态 |
|------|-------------|------|
| Phase 1（拆三迭代） | 单轮：一句话记录一条或多条训练、按日期/具体动作查询、其余拒识 | iter-1 专项 PRD v3 已确认，进入 architecture |

| Backlog（不承诺） | 档案填槽 → 计划生成 → 记录修改/撤销 → 部位查询 → 前端/导入 | — |

## 双螺旋：业务线 × 测试线

每一层业务能力都绑一层测试能力，两条线在文档和交付里始终并排走：

| 业务能力 | 对应测试能力 |
|---------|-------------|
| 意图路由（record/query/reject） | 意图评测：黄金集、混淆矩阵、高风险边界专项统计（锁定集内错进 record 为 0） |
| 自然语言 → 结构化记录 | 抽取评测：字段级断言、三态协议、副作用零错误写入 |
| 多轮补全与指代 | 上下文断言：错误挂接、状态污染、trace 回放 |
| 计划生成（远期） | 不变量断言：计划真的基于历史，不是模板填空 |

每个迭代从首版实现起内建当前链路的 trace，traceId 随能力扩展逐步贯穿 Router → Extractor → Storage → Query；LLM stub 与评测 runner 从第一个迭代开始建设——失败模式也是交付物。

## 边界与免责

不做：饮食、穿戴设备、社交。不提供医疗、康复或专业教练级建议；远期如探索计划生成，仅作为 Agent 能力与测试方法展示的载体，不构成专业训练建议。对外发布一律注明：本项目是 Agent 测试方法论展示，不构成训练建议。
