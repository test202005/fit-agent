# 存储选型：本项目为什么用 JSONL，企业里为什么用数据库

> 背景：iter-2 起 Agent 开始真正写数据，需要先定存储方案。
> 本文回答两件事：本项目选什么、为什么；以及真实企业怎么做、测试要因此多做什么。

---

## 一、本项目：本地 JSONL 文件

一条记录一行：

```json
{"id":"r-001","ts":"2026-09-02T20:10:00+08:00","exercise":"卧推","weight_kg":60,"sets":4,"reps":8,"trace_id":"t-xxx"}
```

### 为什么不是数据库

| 引入数据库的成本 | 本项目能换来什么 |
|---|---|
| 装服务、建库建表、管连接池 | 用不到 |
| 写迁移脚本、维护 schema 版本 | 用不到 |
| 测试前起服务、测试后清库 | 只会拖慢 |
| CI 里额外配一个服务容器 | 只会变脆 |
| **别人 clone 仓库先装 MySQL** | **直接违背「下载填 key 就能跑」** |

这个项目对存储的全部需求就两条：**追加一条、读回来几条**。没有并发、没有复杂查询、没有多表关联、没有事务。SQL 的能力一条都用不上。

### JSONL 对测试反而更友好

- **跑完 `cat` 就能看写了什么**，不用连库查
- **文件快照比对**天然可行——iter-1 那个「跑前跑后比对 mtime，有意外写入就报错」的机制直接复用
- **用例隔离便宜**：每条用例给一个临时文件，天然不互相污染，不用清库
- **落盘内容可进版本库**作为测试证据（脱敏后）

### 什么时候才该换

出现下面任何一条：并发写入、需要按条件查询历史、数据量大到不能全量读。

**现在一条都不沾。** 真到那天也不伤筋动骨——因为写入走统一入口（和 LLM 客户端同样的形状），换实现不影响上层：

```
StorageClient (Protocol)
├── JsonlStorage    真实落盘
└── FakeStorage     内存实现，测试用
```

> 技术选型跟着**测试需求**走，不跟着「正式项目该有数据库」的惯例走。
> 这是 CLAUDE.md「范围红线」的直接应用：功能"够测"即停。

## 二、企业里怎么做

企业当然写数据库，而且通常不止一处。以「记录一次训练」为例，一次写入实际会散落到：

```
业务主表         训练记录本身
用户维度表/缓存   最近训练时间、连续打卡天数等派生状态
任务/审计表      这次 Agent 调用的输入、输出、耗时、模型版本
消息队列         触发下游：推送、报表、推荐更新
数据仓库         T+1 同步，供分析和报表使用
```

**一次「写入」在企业里是一组写入，而且往往跨系统。**

### 因此企业里必须处理，而本项目不需要的问题

| 问题 | 企业必须面对 | 本项目 |
|---|---|---|
| **事务与一致性** | 主表写成功、派生状态写失败怎么办 | 单文件追加，不存在 |
| **幂等** | 用户重复点、消息重投，会不会写两条 | 不涉及 |
| **并发** | 同一用户两个请求同时写 | 不涉及 |
| **Schema 演进** | 加字段要迁移，新旧代码要兼容 | 改 JSON 结构即可 |
| **软删除与审计** | 数据不能真删，要留痕、可回溯 | 不涉及 |
| **多环境数据** | 测试环境数据与线上隔离、定期清理 | 本地文件 |
| **隐私合规** | 落库即受管控，涉及加密、脱敏、留存期限 | 无真实用户数据 |

## 三、存储变复杂之后，测试要多做什么

这是这份文档对测试最有价值的部分——**存储一上数据库，断言的难度就上一个台阶**。

### 1. 「写没写对」不能只看接口返回

接口返回 `success: true` 只代表**它声称写成功了**。必须回查落库结果。企业里的标准做法是**执行前后各取一次状态，比对语义 Diff**，而不是只看响应体。

（这正是 [断言方法论](../eval/methodology/断言方法论.md) 第二问「该发生的发生了吗」，以及实例 B 讲的状态变更类断言。）

### 2. 「没多写」比「写对了」更容易漏

目标层查「该写的写了」，**保护层查「不该写的没动」**：

- 有没有多写一条
- 有没有顺带改了同用户的其他记录
- 有没有污染别的用户的数据
- 派生状态（连续打卡天数）有没有被错误推进

企业里这一层最常被跳过，也最容易出事故——**用户看不见的数据被悄悄改了，没人会报 bug，直到对账时才发现**。

### 3. 数据准备与清理成为测试成本大头

单文件时代不存在的问题，全都回来了：

- **测试数据从哪来**：造数脚本、Fixture 管理、跨表关联数据的一致性
- **跑完怎么清**：清不干净会污染下一轮，清过头会误删别人的数据
- **并行执行怎么隔离**：多人同时跑，账号/数据要分池，否则互相踩
- **环境漂移**：测试库 schema 落后于代码，失败原因是环境不是缺陷

> 经验判断：Agent 项目一旦开始写库，**测试时间的大头会从「设计用例」转移到「准备和清理数据」**。这部分投入要在排期时就说清楚，否则会被当成"测试太慢"。

### 4. 一次写入变成多处写入，断言要分层归因

一条记录写进主表，但派生状态没更新、审计表没落、下游消息没发——这些失败表象不同、责任方不同。

断言必须分层，失败要能定位到是**哪一层没写**，而不是笼统报「写入失败」。这与 [断言方法论](../eval/methodology/断言方法论.md) 的「层序即归因序」是同一条原则。

### 5. 可观测性必须能串起整条链路

单机 JSONL 时，一个 `trace_id` 串 5 个事件就够了。跨系统之后：

- `trace_id` 要**贯穿业务写入、异步任务和下游消息**，不能每个系统各生成一个
- 排查时要能回答：这条数据是哪次请求写的、模型当时收到了什么、哪一步开始歪的
- **数据库里的业务记录最好带上 `trace_id`**——出问题时能从一条脏数据反查回那次 Agent 调用

本项目从第一行代码就把 `trace_id` 写进记录里，就是为这一天留的口子。

## 四、结论

| | 本项目 | 企业 |
|---|---|---|
| 存储 | 本地 JSONL | 关系库 + 缓存 + 审计表 + 消息队列 + 数仓 |
| 一次写入 | 追加一行 | 一组跨系统写入 |
| 测试重点 | 抽取准不准、该不该写 | 加上：一致性、幂等、并发、不该改的没改 |
| 数据准备 | 一个临时文件 | 造数、隔离、清理，成本占大头 |
| 归因 | 单节点 | 必须靠贯穿的 trace 分层定位 |

**方法论是同一套，规模不同。** 本项目验证流程能跑通：抽取 → 三态判定 → 受控写入 → 分层断言 → 副作用检查。搬到企业环境，要加的不是新方法，而是**更严的数据隔离**和**更宽的写入覆盖面**。

选 JSONL 不是"简化版"，是**当前需求下的正确选型**；换数据库不是"升级"，是**需求真的变了之后的必然结果**。判断依据始终是：这个复杂度换来了什么。
