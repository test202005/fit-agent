# V6 专项 PRD：SQLite 持久化与数据一致性

> 状态：规划中  
> 目标：在不牺牲一条命令可运行性的前提下，把当前 JSONL 存储升级为可验证的真实持久化实现。

## 1. 为什么做这一轮

当前系统已经能够记录、查询和通过 Tool Use 产生数据，但 JSONL 不能真实暴露数据库场景中的持久化、事务、隔离和重复请求风险。下一轮先补齐这层企业级基础，再决定是否进入多步 Agent。

本轮只回答一个问题：

> Agent 产生的数据，能不能可靠保存、查询、隔离和恢复？

## 2. 实现范围

沿用现有 `Storage Protocol`，增加三种实现的清晰边界：

```text
FakeStorage       单元测试
JsonlStorage      教学与对照
SQLiteStorage     默认完整运行
```

SQLite 使用本地文件，服务启动时自动初始化最小 Schema，默认不依赖远程数据库账号。后续如有真实部署需求，再增加 PostgreSQL/MySQL 适配，不在本轮引入远程数据库。

最小数据模型包含用户标识、训练记录、状态、业务时间、创建时间和追踪标识。具体字段必须复用当前业务契约，不另起一套训练记录协议。

## 3. 质量风险与断言

| 风险 | 期望行为 | 验证方式 |
|---|---|---|
| 重启丢数据 | 重启后记录仍可查询 | 写入 → 重启 → 查询 |
| 用户数据串读 | 用户只能读自己的记录 | A 写入，B 查询 |
| 重复请求 | 按最终确认的幂等规则处理 | 同一请求执行两次 |
| 部分写入 | 多条记录要么全部成功，要么全部回滚 | 中途注入失败 |
| 时间边界 | 查询继续遵守既有 Frozen Clock 规则 | 复用 V3 时间 Case |
| 状态不一致 | Trace、业务返回和数据库最终状态一致 | 三方结果比对 |

“重复写入是否允许”如果产品尚未定义，先标记为待决策，不由测试单方面规定；但必须把当前行为和风险记录下来。

## 4. 评测分层

- 单测：Fake/SQLite Storage 的 Schema、约束、事务和异常路径；
- Stub 回归：确认现有 Intent、Extract、Query、Tool Use 编排不退化；
- 端到端冒烟：真实 HTTP + SQLite，验证写入、查询和重启恢复；
- 评测报告：区分产品失败、数据库失败、环境 ERROR 和待决策 REVIEW。

本轮不重新跑全套双模型对比；只有当 Storage 接入影响模型输入、输出或调用链路时，才扩大真实模型评测范围。

## 5. 易运行要求

默认运行不需要：

- MySQL/PostgreSQL 服务；
- 远程数据库账号；
- 手工建表；
- 额外数据库管理页面。

项目仍保持一条命令启动；高级用户可以通过 Storage 配置切换其他数据库实现。

## 6. 非目标

- 不引入复杂 ORM；
- 不做分库分表、读写分离和数据库中间件；
- 不做高并发性能专项；
- 不做完整迁移平台；
- 不在本轮开发 ReAct、Memory、多 Agent 或评测平台。

## 7. 准出条件

1. SQLite 默认启动并完成初始化；
2. FakeStorage 和 JsonlStorage 原有测试继续通过；
3. 真实 HTTP 链路可以写入、查询和重启恢复；
4. 用户隔离、事务回滚、重复请求有明确结果；
5. 至少有一次持久化故障注入并被断言捕获；
6. 原有 140 条单测和四套 Stub 回归通过；
7. 形成一份记录错误、归因、修复、验证和边界的迭代复盘；
8. 达到以上条件即收口，不顺带扩展其他能力。

## 8. 后续判断

完成本轮后，只有找到真实的“后一步依赖前一步工具结果”的业务需求，才进入 ReAct 多步循环；否则继续补当前 L1 的副作用、权限或恢复风险，不为了能力等级制造复杂度。
