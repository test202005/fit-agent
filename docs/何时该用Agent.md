# 什么时候该把决策权交给模型

> **这份文档回答一个架构问题**：哪些地方该写死，哪些地方该让模型决定。
> 它不是反对用 AI，而是要把「该不该上模型」从口头争论变成带数据的结论。
> 配套产出：iter-4 完成后，同一套评测集在「固定链路」与「工具调用」两种架构上各跑一遍，形成实测对比。

---

## 一、先承认一个偏见

**测试视角天然偏爱确定性。** 看到不确定的东西，第一反应是「这没必要」。

但有些场景确实只有模型做得了，只是我们先感受到的是它带来的麻烦——不好断言、不好复现、出问题不好归因。

所以需要一条能摆到桌面上的标准，否则「该不该用 AI」就变成谁嗓门大谁说了算。

---

## 二、判断标准：分支能不能穷举

```
分支能穷举        → 写死。更快、更便宜、更可控、更好测
分支穷举不完      → 交给模型
```

一句话展开：**模型的价值在于处理「表达方式无穷、但意图有限」的输入；一旦意图已经确定、后续路径可数，就不该继续让模型决定。**

### 落到本项目

| 环节 | 分支情况 | 决定 | 理由 |
|---|---|---|---|
| 「今天卧推60kg做了4组」怎么理解 | 表达方式无穷 | **模型** | 正则写到最后一定是补丁摞补丁 |
| 判成 record 之后走哪个函数 | 就三条路 | **写死** | 能穷举，交给模型只会把 100% 变成 95% |
| 「这周」换算成哪两个日期 | 表达无穷，结果确定 | **模型翻译 + 代码执行** | 见下方「切开」一节 |
| 按日期过滤记录 | 纯逻辑 | **写死** | 没有任何理解成分 |
| 一句话要做几件事、什么顺序 | 组合穷举不完 | **模型**（iter-4 引入工具调用的理由） | 固定链路只能做一件事 |

---

## 三、把「理解」和「执行」切开

这是本项目从 iter-3 就在执行的做法，也是控制混乱的关键：

```
QueryPlanner（LLM）    自然语言 → 结构化条件      ← 唯一的不确定环节
QueryExecutor（代码）  结构化条件 → 结果          ← 完全确定，可单测
```

**好处有两个，都跟「乱」直接相关：**

1. **责任面清晰**：查错了，立刻知道是「没听懂用户」（改 Prompt）还是「查错了数据」（改代码）。混在一起时，一个 bug 要同时怀疑两个地方。
2. **可测性**：执行那一半是纯函数，普通单测就能覆盖，不花 token、不看运气。

**反过来说**——如果一个模块里既有理解又有执行，且没有中间的结构化产物，那它几乎必然难测、难归因。这是判断「架构乱不乱」的一个实用信号。

---

## 四、常见的「为了 AI 而 AI」

以下模式在真实项目里反复出现，共同特征是：**把本来确定的事变成了不确定的事，却没换来任何理解能力上的收益。**

| 反模式 | 后果 |
|---|---|
| 用模型做**格式转换**（日期格式化、单位换算、JSON 重排） | 代码一行的事，模型有概率出错 |
| 用模型做**能穷举的分支路由** | 100% 变成 95%，且失败不可复现 |
| 用模型做**数值计算与统计** | 算错了没人发现，因为看起来很合理 |
| 用模型**校验数据合法性** | 校验规则本来就是确定的，写成代码还能复用 |
| 模型输出**直接落库，中间没有结构化校验层** | 脏数据进库，且不可追溯 |

**共同的代价**：确定性没了、成本上去了、出问题不知道改哪。

---

## 五、决策权阶梯与代价

每往下一层，能力更强，**可控性与可测性同时下降**：

| 层 | 模型决定什么 | 测试重心 |
|---|---|---|
| 写死 if-else | 什么都不定 | 结果对不对 |
| 意图路由 | 「这是什么」 | 分类准不准 |
| **工具调用** | 「用什么工具、传什么参数」 | 加上：**决策过程合不合理** |
| 多步循环 | 还包括「做几步、何时停」 | 加上：收敛性、推理与行动一致性 |
| 自主规划 | 连「任务怎么拆」都自己定 | 大部分只能靠裁判 |

**关键的一条**：决策权在我时，只需测结果；决策权交给模型后，**必须同时测过程**——这就是 trajectory 评测存在的原因。**每上一层，评测成本是台阶式上涨，不是线性。**

---

## 六、iter-4 的架构对比实验

工具调用做完之后，用**同一套评测集**在两种架构上各跑一遍，形成实测对比：

| 对比维度 | 为什么要测 |
|---|---|
| **准确率** | 工具调用是否真的更准，还是只是更灵活 |
| **Token 成本** | 工具描述会进 prompt，成本上升多少 |
| **响应耗时** | 多一轮回灌意味着多一次往返 |
| **失败可定位性** | 出错时能不能归因到具体步骤 |
| **复合请求处理** | 固定链路做不到的那部分，工具调用能做到多少 |

**预期结论的形态**（不预设方向，以实测为准）：

> 在意图单一、分支有限的场景，固定链路在准确率、成本、耗时上都不劣于工具调用，且更好测；
> 在一句话包含多个诉求的场景，固定链路结构性做不到，工具调用是唯一选项。

### 为什么这个实验比功能本身更有价值

市面上讲「Agent 怎么写」的内容很多，讲「**什么时候不该用 Agent**」的很少。

而对测试工程师而言，这份对比的意义是：**在架构决策上说话时，不是凭感觉反对，而是能说清代价。**

> 不是「我觉得这块不该上模型」，
> 而是「同构场景我实测过，固定链路准确率高 X、成本低 Y、失败可定位到步骤」。

**这才是测试人在架构决策上的话语权来源——不是反对 AI，是能说清代价。**

---

## 七、一句话总结

**能穷举的分支写死，穷举不完的交给模型；理解与执行必须切开，中间留一层结构化产物。**

判断一个 Agent 项目乱不乱，看两点：有没有能穷举却交给模型的地方，以及理解和执行有没有搅在一起。
