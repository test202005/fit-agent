# 意图识别评测数据集：现状判断与建设方法

> 状态：Iteration 1 复盘与下一版数据集设计依据
> 更新：2026-07-19
> 范围：只讨论意图识别数据集和指标口径，不扩展 Iteration 1 产品能力

## 1. 先说结论

fit-agent 当前的 100% 是真实运行结果，但不能解释为“意图识别真实准确率达到 100%”。准确表述是：

> `deepseek-v4-flash` 在当前 16 条小规模 locked 合成种子集上连续三轮全部通过；它证明当前实现、Prompt 和已覆盖边界达到 Iteration 1 工程退出门槛，不证明真实用户分布下的泛化准确率为 100%。

原因不是指标算错，而是数据集还处于早期阶段：意图只有 3 类、locked 只有 16 条、全部是合成单轮输入，且开发过程中看过 locked 失败结果并针对同类问题调过 Prompt。暴露 Case 虽然已转入 regression，但评测过程已经对 locked 分布产生间接适配。

因此应同时保留两个判断：

- **工程闭环成立**：Router、Trace、Stub、Live Eval、错误归因和回归链路已经跑通；
- **模型质量证据不足**：当前数据量和来源不足以支撑“真实准确率 100%”，也不足以与生产级评测横向比较。

## 2. 种子集与生产级评测集的差距在哪

fit-agent 当前这套数据属于**种子集**：规则驱动、人工合成、单轮短句、样本量在几十条量级。成熟产品线上的意图评测集是另一个物种，差距集中在六个维度：

| 维度 | 种子集（fit-agent 现状） | 生产级评测集 |
|---|---|---|
| 意图空间 | 3 类：`record / query / reject` | 十个以上业务意图，且彼此边界互相挤压 |
| 数据规模 | 37 条（分类 34 + 故障 3），locked 16 条 | 数百条起步，并按风险类型分批维护 |
| 数据来源 | PRD 规则驱动的人工合成 | 脱敏线上真实 Query、用户反馈、已复现 Bad Case |
| 输入复杂度 | 中文单轮短句为主 | 口语、错别字、多语言、混合意图、用户历史与账号状态干扰 |
| 链路复杂度 | 函数级 Router，不执行下游业务 | 意图之后还有灰度、路由、下游 Agent、工具与业务结果 |
| 指标用途 | 首版工程闭环与种子能力验收 | 质量画像、发布回归、风险发现、线上问题归因 |

一个反直觉但重要的推论：**小数据集上的高分，信息量低于大数据集上的中等分**。种子集的 100% 只说明「这几十道已定义的题全答对了」；在更大意图空间、更真实语境下测出来的 90%，暴露的是真实质量水位。所以引用任何数字都必须连同数据集版本、样本量和来源一起报，单独一个百分比没有意义。

## 3. 你之前梳理过的数据集方法

知识库中已经有两份直接相关的方法：

- 《AI 数据集设计 SOP》：管数据集如何拆层、如何确认断言、黄金集/标准集/鲁棒集怎么流转；
- 《评测 Query 设计 SOP》：管每条 Query 从哪里来、如何做成真实表达、如何覆盖意图边界。

两份方法合起来的主线是：

```text
先锁定测试层和意图边界
  → 确认稳定断言
  → 从真实来源收集种子
  → 按规则确定性分层
  → 按风险类型补覆盖
  → 小批量试跑与人工归因
  → 修复问题进入回归集
  → 上线后用真实流量持续替换合成数据
```

### 3.1 数据从哪里来

优先级从高到低：

1. 脱敏后的线上真实 Query；
2. 用户反馈和客服/问题群中的真实表达；
3. 已复现的线上或测试 Bad Case；
4. 产品、测试和领域专家基于业务风险构造；
5. LLM 或人工生成的规整合成句。

合成数据适合上线前搭骨架，但不能长期占据黄金集主体。fit-agent 当前基本处在第 4、5 层，后续需要通过试用、dogfooding 或真实用户记录逐步替换。

### 3.2 黄金集怎么来

黄金集不是“模型已经答对的题”，而是“业务上有稳定标准、每次变化都必须守住的题”。准入条件：

- 来源可追溯，优先来自真实核心场景、历史 Bug 和高风险边界；
- expected 有业务依据，两个领域人员能独立得到相同结论；
- 有稳定、自动化的断言；
- 不依赖不可控账号、AB 分组或临时环境；
- 多次运行已达到可靠性要求，适合进入持续回归。

典型流转：

```text
产品规则或真实问题
  → 明确 expected
  → 进入标准/能力集验证
  → 修复并稳定通过
  → 升级为黄金回归 Case
```

注意：真实 Bad Case 修复后进入黄金回归集，不等于它还能留在独立盲测集。回归集用于防止旧问题复发；盲测集用于估计未见数据上的泛化能力，两者职责不同。

### 3.3 三种分类维度不要混用

一条 Case 应同时有三类标签。

#### 维度 A：开发生命周期

| 标签 | 用途 | 是否允许针对结果调 Prompt |
|---|---|:---:|
| `discovery/capability` | 找边界、暴露当前不会的能力 | 是 |
| `blind_holdout` | 估计未见数据泛化质量 | 否 |
| `regression` | 防止已修复问题复发 | 可以修，但 Case 永久保留 |

#### 维度 B：规则确定性和成熟度

| 标签 | 定义 |
|---|---|
| `golden` | expected 唯一、来源可靠、断言稳定、已达到回归可靠性 |
| `standard` | 规则明确且可断言，但尚未达到黄金稳定性 |
| `robust/disputed` | 边界探索、对抗输入或规则仍有争议，不计正式通过率 |

#### 维度 C：风险覆盖类型

| 标签 | 意图识别示例 |
|---|---|
| `positive` | 各意图的清晰正例 |
| `confusion_boundary` | `record` 与 `reject`、`query` 与咨询之间的混淆对 |
| `negative` | 闲聊、越界、无对象、纯否定 |
| `safety` | 提示注入、越权、敏感内容 |
| `language_style` | 口语、错别字、中英混合、长句和噪声 |
| `multi_intent` | 一句话包含多个意图及优先级 |
| `context` | 多轮、省略、指代和历史状态干扰 |

例如，一个“历史提示注入修复 Case”可以同时是：

```json
{
  "lifecycle": "regression",
  "quality_tier": "golden",
  "risk_type": "safety"
}
```

## 4. fit-agent 当前数据集的真实位置

| 当前视图 | 实际作用 | 当前问题 |
|---|---|---|
| discovery | Prompt 开发和格式问题发现 | 部分 Query 与 few-shot 高度接近，只能用于开发 |
| regression | 保存已修复的格式与注入 Bad Case | 方向正确，但样本仍少，且没有 query 类 Case |
| locked | 小型迭代退出验收 | 开发中多次查看失败并替换 Case，不再是严格统计意义的盲测集 |

因此建议保留现有名字和数据作为 Iteration 1 历史资产，但不要再把当前 `locked` 称为独立盲测。更准确的定位是：

```text
当前 locked = iteration acceptance set（迭代验收集）
未来新增 blind_holdout = 一次性独立盲测集
```

## 5. fit-agent 下一版数据集建议

### 5.1 最小可执行结构

| 数据集 | 建议规模 | 来源 | 用途 |
|---|---:|---|---|
| Core Golden | 30–50 | PRD 核心规则 + 已确认真实场景 | 每次改 Prompt 必跑，目标接近 100% |
| Capability/Robust | 50–100 | 边界、噪声、多表达、对抗构造 | 找问题，不设“一定全过”目标 |
| Blind Holdout | 60–100 | 独立生成/独立标注，Prompt 开发者不可见 | 一次性估计真实泛化质量 |
| Regression | 持续增长 | 每个已修复 Bad Case | 防止回归，目标 100% |

Iteration 1 不需要一次补满。下一步最有价值的是先补一批 **60 条 blind holdout**，因为当前最缺的不是更多回归题，而是一个没有被 Prompt 调优污染的质量估计。

### 5.2 Blind Holdout 建设门禁

> **先判断需不需要**：测试集在实际工作中常常直接给开发、由开发照着改，此时它是规格说明书而非统计工具，「被看过」不是污染而是设计意图。真正需要盲测集的只有一种情况——**要对外宣称一个准确率数字**。日常迭代交付不需要，别为它停工。下面这套门禁成本很高，确认需要再启用。

1. 先冻结 PRD 标签决策表；
2. 由不同于 Prompt 调优过程的来源生成 Query；
3. 两人独立标注，分歧 Case 不进入正式分数；
4. 三类基本均衡，高风险边界加权但单独统计；
5. Prompt 开发期间不查看单条结果；
6. 只在版本候选完成后跑一次；
7. 失败 Case 完成归因后移入 regression，下一轮重新补充未见 holdout；
8. 报告置信区间或至少明确样本量，不再只写裸百分比。

### 5.3 Query 应如何变得更真实

围绕每条业务边界，从四个维度轮换表达：

- 领域专业度：新手、普通用户、训练老手；
- 信噪比：极短、省略、冗长、夹杂无关信息；
- 情绪：急躁、疲惫、随意、礼貌；
- 表达风格：陈述、疑问、命令、错别字、中英混合。

重点不是把一条标准句机械改写十次，而是覆盖不同失败机制。例如 `record/reject` 边界至少应包含：

- 纯否定与否定转折；
- 未来计划与已发生事实混合；
- 有训练语气但无训练对象；
- 情绪中夹训练事实；
- 咨询句中包含重量、组数等强关键词；
- 一句话同时要求记录和查询；
- 长上下文和提示注入中夹真实训练事实。

## 6. 指标应该怎么报

不要只报“通过率”。最少同时报告：

- 数据集名称、版本、样本量和来源构成；
- 每个意图 Precision、Recall、F1 和混淆矩阵；
- 高风险错进有副作用意图的数量；
- 单次通过率与多次运行稳定性；
- parse error、timeout 与业务误判分账；
- discovery、blind holdout、regression 分账；
- 失败归因：规则、标注、Prompt、模型、解析、上下文、环境。

对于用户每次都希望正确的意图路由，多次运行应关注“连续 k 次全部成功”的可靠性，而不是“k 次中至少成功一次”。

## 7. 官方依据与本地事实源

官方方向：

- OpenAI Evaluation Best Practices：先定义明确目标，数据应覆盖真实使用分布，持续用新失败更新评测；
- Anthropic《Demystifying evals for AI agents》：初期 20–50 条可起步，但能力评测和回归评测要分开；任务必须无歧义、正反例平衡，并持续检查 trace；100% 饱和的能力集不再提供改进信号；
- Anthropic 对非确定性评测区分 `pass@k` 与 `pass^k`，面向用户的可靠性更关注多次全部成功。

本项目事实源：

- `docs/prd-iter1-intent.md`：意图边界与标签决策表；
- `eval/datasets/intent-dataset.jsonl`：当前数据集；
- `eval/reports/迭代一意图识别评测报告.md`：Iteration 1 最终结果与口径。

## 8. 当前决策

1. Iteration 1 保持完成，不因为数据集证据不足推翻工程交付；
2. 对外不再说“意图识别准确率 100%”，改说“当前 16 条验收集三轮全过”；
3. 当前 locked 重命名问题先在文档中澄清，不立即机械改代码和数据字段；
4. 下一步先设计独立 blind holdout，再决定是否继续调 Prompt；
5. 与其他项目的数字只做方法与复杂度对比，不做模型优劣排名。
