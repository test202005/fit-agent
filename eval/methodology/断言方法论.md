# Agent 断言方法论：结果回来了，怎么证明它真做对了

> 适用范围：任何有 LLM 参与决策的系统——意图分类、参数抽取、内容生成、状态变更。
> 用法：写每一条断言之前对着这份文档过一遍，回答「这条断什么、断多严、断到哪为止」。
> 本文只讲断言。数据集怎么造见 [意图识别数据集设计方法](意图识别数据集设计方法.md)。

---

## 0. 问题

接口返回 `success: true`，你怎么证明 Agent 真的做对了？

`success` 只能证明**它声称自己成功了**。操作类型正确，也只能说明**它打算这么做**。两者都不能证明最终状态是对的。

这份文档要解决的就是：把「看起来对」变成「可复现地证明对」。

---

## 1. 四问：任何 AI 系统的断言都在回答这四个问题

| # | 问题 | 断什么 |
|---|---|---|
| 一 | **系统承诺了什么？** | 状态码、`success` 字段、响应结构、必填字段、枚举合法性、类型 |
| 二 | **该发生的发生了吗？** | 目标对象、操作类型、目标字段、目标值 |
| 三 | **不该发生的没发生吗？** | 保护字段未变、无越界修改、无意外副作用 |
| 四 | **它说的和做的一致吗？** | 摘要/操作记录/标签，与真实发生的变化是否吻合 |

**顺序即归因顺序。** 从一往四断，哪一问先挂就归因到哪一层。第一问挂了不必看第二问——结构都不对，谈语义没有意义。这是「不允许一步归因到模型能力」的执行方式。

**第三问是最容易漏的一问。** 大多数人只断「该改的改了」，不断「不该改的没动」。用户说「其他内容不变」，这句话本身就是一组断言。

### 四问的最小检查清单

**第一问 · 承诺**
- [ ] HTTP 状态码符合预期
- [ ] 业务成功标志（`ok` / `success`）与错误码互斥，不会同时成立
- [ ] 响应字段集合**精确**符合契约——不多不少
- [ ] 失败响应不泄漏业务字段（例如失败了还带着分类结果）
- [ ] 所有枚举值在定义范围内（错误码尤其容易漏）
- [ ] 关键字段类型与取值范围正确

**第二问 · 目标**
- [ ] 先把自然语言请求转成结构化预期，再比对
- [ ] 目标对象、操作、字段、值，四项同时成立才算通过

**第三问 · 保护**
- [ ] 每条 Case 明确三类字段：允许变化 / 必须保护 / 可以忽略
- [ ] 不做整份 JSON 全等比对——时间戳、traceId 这类噪声会淹没真实变化
- [ ] 该被拒绝的请求，要证明**它真的没执行**（而不只是返回了拒绝）

**第四问 · 一致**
- [ ] 系统自述的操作与真实差异一致
- [ ] 没有声称做了实际没做的事

## 2. 断多严：看这个值是谁规定的

同一个字段，该硬断还是该放过，不靠拍脑袋，靠来源分类：

| 来源 | 尺度 | 说明 |
|---|---|---|
| **契约或用户明确规定的** | **精确硬断，不许放宽** | PRD 写死的枚举、用户原话提的要求 |
| **测试为跑通补的 Mock 值** | **只做一致性检查** | 不能表述为「AI 理解对了用户需求」 |
| **场景没规定的** | **不断，进观察项** | 强行断只会制造误报 |

两条铁律：

1. **响应里出现了具体值，永远不能反向升级成业务要求。** 模型某次输出了一个数，不代表这个数就是标准。
2. **Mock 与业务事实冲突时，以业务事实为准，先修 Mock**，不是改断言去迁就 Mock。

> 「断太严会误报」多半是伪命题。真正让人判不准的，是**没给字段定性就直接写 expected**。分类对了，尺度是推出来的。

## 3. 结论是四态，不是两态

```
PASS    确定性断言全部通过，没有剩余开放问题
FAIL    已发现明确的业务错误
REVIEW  结构断言通过，但仍有开放判断需要复核
ERROR   请求、解析或评测程序本身异常
```

**核心通过率只统计 PASS/FAIL，REVIEW 和 ERROR 单独成层。**

分界线不是「规则 vs 语义」，而是：

```
有明确、稳定、可复现的判定标准  →  PASS / FAIL  →  进核心通过率
没有唯一标准、判定随评估者变化  →  REVIEW       →  单独统计
```

注意：涉及语义理解但业务标准明确的（例如「用户要增肌，计划里却没有力量训练」），**该 FAIL 就 FAIL**，不要因为它是语义问题就推给 REVIEW。

如果没有明确标准却强行输出 PASS/FAIL，那是在**制造虚假的确定性**。

## 4. 三级漏斗：能不用模型判就不用

```
① 代码断言   →  客观事实，全部在这拦掉
② 大模型裁判 →  只处理代码断不了的开放文案
③ 人工       →  只看裁判标 FAIL / REVIEW 的那几条
```

**每一级都要尽量把量吃掉，只把剩下的往上抛。** 如果人工那层还剩几十上百条，说明前两级偷懒了。

### 裁判要做浅，这是重点

见过太多方案在裁判上过度设计——五分制、权重、多维度评分表。**没人有时间维护它，也没人有时间校准它，最后整套废掉。**

裁判的正确形态：

- **输出只有三个标签**：`PASS / FAIL / REVIEW`。**不要评分、不要量表、不要权重。**
- **通用 Prompt + Case 声明维度**，不给每个 Case 写一套提示词
- **维度由人声明，模型只执行**——不让模型自己决定「这条该判什么」
- 公共维度控制在三个左右即可，例如：目标有没有被承接、文案有没有自相矛盾、有没有编造用户没提供的事实
- **裁判是观察员，不是法官**：结果作为问题发现和人工复核的证据，**不进正式通过率**

为什么不进通过率：同一批结果，只改裁判提示词的措辞，通过率就能从 72% 跳到 85%。**会随提示词波动的东西，不能当上线门槛。**

**关于校准**：「准不准、稳不稳」的验证，是裁判要**升级为正式断言之前**才做的事。它当观察员用的时候不需要前置校准——否则这一层的启动成本会高到没人做得起。

## 5. 报告：两个口径都要给

```
【核心结果】确定性通过率 92%（100 条断言，PASS 92 / FAIL 8）
【语义质量】裁判 REVIEW 12 项（人工确认：3 真问题 / 7 正常 / 2 待确认）
【执行异常】ERROR 1（接口超时）
```

同时报**断言级**和 **Case 级**通过率：

| 口径 | 回答什么 | 给谁看 |
|---|---|---|
| 断言级 = 通过断言数 / 总断言数 | 业务规则被正确执行的程度 | 开发，估修复工作量 |
| Case 级 = 通过 Case 数 / 总 Case 数 | 用户完整走一遍会不会出错 | 产品，看影响面 |

实测过一批数据：断言级 98.1%，Case 级 77.3%，**差 21 个百分点**。只报前者会掩盖「5 个用户场景确实坏了」，只报后者会让人以为「两成功能坏了」。**任何只给单一数字的报告都在诱导误读。**

还有一层前提：**先分清这是能力评测还是回归评测**。能力评测本来就该低通过率起步（专挑不擅长的任务），回归评测才该接近 100%。判断「能不能上线」看的是回归评测。

## 6. 实例 A：意图分类（最简单的情况）

输入一句话，输出一个标签。四问依然全部适用，只是每问的内容很少：

| 问 | 落到意图分类 |
|---|---|
| 一、承诺 | 响应字段集合精确；成功/失败结构互斥；失败时不带分类结果；`error_code` 在定义的枚举内；置信度是 0~1 数字 |
| 二、目标 | `intent == expected`。边界场景可用 `intent in [...]`；暂时定不了唯一答案但能排除错误路由时，用 `intent != 错误值` |
| 三、保护 | 该被防御拦掉的输入，要证明**没有调用模型**（查执行痕迹里有没有模型调用事件）；评测跑完不产生任何业务写入 |
| 四、一致 | 执行痕迹里记录的结论与最终返回值一致 |

**这一类不需要大模型裁判**，代码断言能吃掉 100%。

一个常见漏洞：断言执行痕迹时用「包含」而不是「等于」——那样多出来的事件不会导致失败，防御路径「没调模型」这条就断不住了。**该用精确集合比对。**

## 7. 实例 B：状态变更（最难的情况）

输入一句指令，改变一份业务数据。这类光比对返回值没用，必须**比对执行前后的状态**。

先生成**语义 Diff**——不要直接 diff 两份 JSON，而是转成业务变化事实：

```json
{
  "modified": [{"target": "动作A", "field": "sets", "before": 4, "after": 3}],
  "added": [],
  "removed": []
}
```

然后照着四问查：预期变化在不在 Diff 里（第二问）→ Diff 里有没有非预期变化（第三问）→ 最终状态是否合法可用（第一问的延伸）→ 系统自述与 Diff 是否吻合（第四问）。

可复用的实现抽象成四个对象：

```
Expected Change  用户要求发生什么变化
Allowed Change   允许、保护、忽略哪些字段
Semantic Diff    系统实际改了什么
Verdict          结论、失败原因、证据
```

换一个业务只需要替换「状态解析」和「合法性规则」，主流程不动。

---

## 8. 最后：怎么描述结论

如果只是现有自动检查没有发现失败，准确的说法是：

> 当前已经实现的确定性检查未发现错误。

而不是：

> Agent 已经正确完成了任务。

这两句看起来只差一点，可信度完全不同。
