# AI 评测数据集实操手册

> 用途：拿到一个 AI 需求后，用 30 分钟完成第一版覆盖矩阵和 Case 骨架。详细原理见[数据集方法论](数据集方法论.md)，本手册只保留执行步骤。

## 一条主线

```text
需求规则 → 等价类 → 风险排序 → 代表 Case
→ expected 与断言 → 分层运行 → Bad Case 回流
```

先回答三问：系统在做什么决策？什么结果算正确？从哪里稳定观察？任何一问答不清，先回需求评审，不批量造数据。

## 第一步：画覆盖矩阵

传统测试的等价类思维仍然有效：把会走相同业务规则、产生相同失败机制的输入归为一类，每类先选代表，不穷举自然语言。

按任务选择矩阵，不套同一模板：

| 任务 | 推荐矩阵 |
|---|---|
| 意图识别 | 意图类别 × 易混淆边界 |
| 参数抽取 | 业务字段 × 完整/缺失/干扰/非法 |
| Tool Use | 用户任务 × 应调用/不应调用/参数边界 |
| 状态修改 | 数据结构 × 操作类型 × 必须保持项 |
| 内容生成 | 业务要求 × 明确冲突 × 可接受变化 |

每个普通格子先放 1 条；高风险、历史易错格子放 2～3 条。只有同一格出现不同失败机制时才继续拆分。

边界不只有数字边界，还包括：肯定/否定、已发生/未来、单意图/多意图、信息完整/缺失、支持/不支持、应调用/不应调用。

## 第二步：从真实种子造 Query

来源优先级：

```text
脱敏真实 Query / 用户反馈
→ 已确认 Bug
→ PRD 核心规则
→ 领域专家风险构造
→ AI 表达扩展
```

真实 Query 只能证明“用户这样问过”，不能自动成为 Golden。AI 可以扩展口语、省略、错别字、噪声和中英混合表达，但不能替人决定业务 expected。

一条正式 Case 最少包含：

```json
{
  "case_id": "稳定唯一 ID",
  "input": "用户输入和必要上下文",
  "expected": "明确结果",
  "assertion": "怎样判定",
  "source": "规则、反馈或 Bug 来源",
  "risk": "normal | high",
  "lifecycle": "discovery | regression | holdout | observation",
  "scenario_type": "standard | boundary | robustness | adversarial",
  "label_status": "golden | candidate | disputed"
}
```

已有项目不必为了字段统一立刻迁移全部 Case；先保证这些语义存在，新需求开始按统一结构写。

## 第三步：判断能不能叫 Golden

Golden 不是“模型已经答对的题”，而是可以长期守住的业务标准。准入检查：

- 来源能追溯，能解释为什么要测；
- expected 有确认过的业务依据；
- 两个领域人员能够独立得出相同结论；
- 输入、Fixture 和环境可复现；
- 自动断言稳定，且用错误结果证明过它会失败；
- 已暴露 Case 不再冒充未见 holdout。

缺业务结论的放 `observation/disputed`，可以执行和观察，但不进入正式通过率。

## 第四步：数量和准出怎么定

数量不从整数倒推：

```text
Case 数 = 覆盖格子需要 × 每格代表样本 × 必要风险加权
```

早期先做 20～50 条高价值任务足够发现明显问题，这是 Anthropic 给出的实操起点；成熟系统要检测更小变化时，再扩大数据和难度。60 条可以支撑人工逐条 Review，但不适合证明 1～2 个百分点的细微差异。[Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

通过率按用途定，不统一拍 90%：

| 类型 | 准出原则 |
|---|---|
| 代码契约、解析和副作用保护 | 100% |
| 高风险 Regression | 每条每轮通过 |
| 普通 Regression | 接近 100%，任何下降都归因 |
| Capability | 允许低分，比较基线和改进幅度 |
| Holdout | 结合历史基线、样本量和业务风险 |
| ERROR / disputed | 单独统计，不混入业务通过率 |

总通过率不能覆盖风险门禁：即使整体 95%，只要出现错误写入、越权调用等高风险失败，仍不准出。模型有波动时同时看单轮结果和 `pass^k`，不能用“多次里成功一次”代替稳定可用。

## 第五步：失败怎样回流

```text
失败 → 核对需求/Case/断言/环境/模型
→ 确认真实缺陷 → 原 Case 进入 Regression
→ 补一个相邻等价类 → 重跑核心集
```

回流不能只保存原句，还要保留 expected、actual、失败断言、风险格子、归因和 `trace_id`。修复后的原题负责防复发，未见题负责验证不是针对单题过拟合。

## 两个项目实例

### 意图识别

决策是 `Query → record/query/reject`。先按三个意图放标准正例，再重点覆盖边界：

```text
“今天没练卧推，改练深蹲5组” → record
“今天没练卧推，改成休息”     → reject
```

这对 Case 复用了相同句式，只改变“是否存在已发生的训练事实”，比再写十条标准句更能证明边界。当前 `fit-agent` 的58条数据都能追溯到 PRD，但主要是规则构造，不应包装成真实用户分布。

### Tool Use

决策是 `Query + 时间/状态 → 工具、参数和副作用`。支持与不支持必须成对：

```text
“这周卧推了几次” → count_exercise
“这周练了几次腿” → 不调用工具
```

除了工具名，还要断言参数、调用次数和没有多余写入。当前28条 Tool Case 共用一个较粗的 PRD 来源，后续新增 Case 应指向具体规则或 Bug，而不是继续堆相同来源。

## 开工与收口检查

开工前：三问有答案、覆盖矩阵已画、每条有 source/expected/assertion，争议项已隔离。

收口时：普通格子有代表、高风险格子有门禁、断言被反例验证、失败完成归因、报告绑定模型/Prompt/数据集/Trace，并写清证据不能外推到什么范围。

做到这里就停。没有新失败机制、真实流量或业务规则变化，不为了增加数量继续造同义 Case。
