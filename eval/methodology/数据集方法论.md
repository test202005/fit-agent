# 评测数据集方法论：从零设计到持续回流

> 执行入口以[数据集实操手册](数据集实操手册.md)为准。本文保留完整原理和历史复盘；若分层名称冲突，以手册中的“生命周期 / 场景类型 / 标注成熟度”三轴定义为准。
>
> 评测只有两块核心：**数据集**和**断言**。数据集决定你测到了什么，断言决定你能证明什么。
> 断言部分见 [断言方法论](断言方法论.md)，本文只讲数据集。
> 本项目的实例见 [意图识别数据集设计方法](意图识别数据集设计方法.md)。

---

## 写在前面：起步阶段，标准够用就行

这份文档列了不少东西，但**不要一上来全做**。做不动的标准等于没有标准。

起步阶段真正必须有的只有三条：

1. **每条 Case 写得出唯一 expected**——写不出就先别进数据集
2. **调优用的和验收用的数据分开**——不然是自己给自己判卷
3. **出了问题的 case 回流进来**——集子自己会长

其余的（source/assertion 字段、对抗桶、blind holdout、脱敏流水线）都是**遇到具体问题再补**，不是开工前的门槛。

### 一个要先说清的现实

实际工作里，**测试集经常是直接给开发的——他们照着测试集和断言改代码**。

这意味着测试集的首要身份是**规格说明书**，不是统计工具。它被开发看见、被针对性优化，**不是污染，是设计意图**。

所以「数据集被看过了怎么办」这个焦虑，多数情况下不成立。真正的问题不是「这批题被看过」，而是「**只有这一批**」——解法是持续补新 case，不是养一个不许碰的盲测集。

**什么时候才真需要 blind holdout？** 只有一种：你要对外宣称一个准确率数字（发论文、给客户报 SLA、做模型选型）。日常迭代交付不需要，别为它停工。

## 速查：六步，照着做就行

| # | 步骤 | 做完的标志 |
|---|---|---|
| 1 | **定决策** | 说得出系统在判什么、什么算对、从哪观察 |
| 2 | **定契约** | 每条 Case 都有 expected、断言、来源、风险标签 |
| 3 | **定覆盖** | 画出等价类矩阵，每个高风险格子有 1–2 条代表 |
| 4 | **定分层** | 调优用的和验收用的数据互斥，分开算分 |
| 5 | **定来源** | 真实数据优先，AI 只扩表达；先判断需不需要脱敏 |
| 6 | **定回流** | Bad Case 先归因再回流，同时更新覆盖矩阵 |

三条卡点，任何一条不满足就别往下走：

- **写不出唯一 expected 的场景，不进数据集**——先回去补规则
- **调优数据和验收数据不能是同一批**——否则是自己给自己判卷
- **不是所有失败都该回流**——先归因，只有确认的真实缺陷才沉淀

下面是每一步的展开。

---

## 0. 先回答三个问题，再造数据

```
系统到底在做什么决策？
什么结果才算正确？
从哪里能稳定观察到这个结果？
```

这三个问题没说清，生成再多 Query 也只是在批量制造无法判定的数据。

**门禁**：写不出明确 expected、或没有稳定观测方式的场景，标为阻塞，不进入用例设计。硬着头皮写出来的 Case，跑完也是 `not_evaluated`，白跑。

## 1. 四层模型

```
Decision Model       系统在做什么决策
Evaluation Contract  每条 Case 如何定义正确并留下证据
Coverage Model       哪些风险维度需要代表样本
Feedback Loop        真实失败如何回流并扩展覆盖
```

不同任务的决策结构不同，数据结构不能套同一个模板：

| 场景 | 决策模型 | 主要覆盖维度 |
|---|---|---|
| 意图识别 | Query → 意图类别 | 意图类别 × 易混淆边界 × 表达方式 |
| RAG | Query + 知识 → 有依据的回答 | 问题类型 × 知识状态 × 引用风险 |
| 工具 Agent | 目标 + 上下文 → 工具调用与结果 | 任务类型 × 工具状态 × 异常路径 |
| 状态修改 | 原始状态 + 指令 → 新状态 | 数据结构 × 操作类型 × 业务约束 |

---

## 2. 一条数据不是一个 Query，是一份评测契约

每条正式数据至少包含：

```
case_id     长期稳定的唯一标识
input       用户输入和必要上下文
expected    明确可判定的预期结果
assertion   自动断言或人工评分规则
tags        所属数据层和风险类型
source      PRD、线上数据、用户反馈或历史 Bug
risk        失败后的业务影响
```

最容易被忽略的是 `source` 和 `assertion`。**没有来源，就不知道这条数据为什么存在、规则变了该找谁确认；没有断言，跑完只能靠人重新理解输入临时判断。**

只有 Query 的文件是测试语料，不是评测数据集。

---

## 3. Golden Case 的准入依据

「什么算 Golden」不能靠感觉。黄金集不是「模型已经答对的题」，而是「业务上有稳定标准、每次变化都必须守住的题」。

**五条准入条件，缺一不可：**

1. **来源可追溯**——优先来自真实核心场景、历史 Bug、高风险边界，能说出这条为什么存在
2. **expected 有业务依据**——两个领域人员独立判断能得到同一结论
3. **有稳定的自动化断言**——不是「人看一眼觉得还行」
4. **不依赖不可控环境**——不绑定临时账号、AB 分组、当天数据
5. **多次运行稳定通过**——已达到可进入持续回归的可靠性

典型流转：

```
产品规则或真实问题 → 明确 expected → 进标准集验证 → 修复并稳定通过 → 升级为 Golden
```

**一个反直觉的点**：真实 Bad Case 修复后进 Golden 回归集，**不等于它还能留在盲测集**。回归集用于防旧问题复发，盲测集用于估计未见数据的泛化能力，两者职责不同，同一条数据不能同时干这两件事。

---

## 4. Query 从哪来：真实优先，AI 只做表达扩展

**来源优先级从高到低：**

```
线上真实 Query（脱敏后）
→ 用户反馈、客服工单
→ 已复现的历史 Bug / Bad Case
→ PRD 和业务规则
→ 领域专家按风险构造
→ AI 批量扩写
```

上线前拿不到真实流量，从需求和领域风险开始是合理的；但上线后**必须持续用脱敏真实数据替换早期构造数据**。合成数据适合搭骨架，不能长期占据黄金集主体。

**起步不要铺全量**：先用 20–50 条**来自真实失败**的任务起步，取材顺序是「你已经在手工测的场景 → 上线前检查项 → 公共用户任务 → Bug 队列 / 支持工单」，按用户影响排优先级。

**AI 该做什么、不该做什么：**

| AI 适合 | AI 不该做 |
|---|---|
| 口语化改写、否定与反问、指代省略、加噪声、专业与非专业表达 | 决定哪些场景重要 |
| 围绕已确认的风险扩展表达 | 决定业务正确答案是什么 |
| | 把自己生成的 expected 直接写进黄金集 |

一句话分工：**人提供业务事实、风险和预期，AI 扩展表达，人最后判断这条能不能进正式集。**

**让 Query 更真实的四个轮换维度**：领域专业度（新手/老手）、信噪比（极短/冗长/夹无关信息）、情绪（急躁/疲惫/礼貌）、表达风格（陈述/疑问/命令/错别字/中英混合）。重点不是把一条标准句机械改写十次，而是**覆盖不同的失败机制**。

## 5. 覆盖靠等价类，不靠穷举

自然语言输入空间无限，Case 永远写不完。解法不是堆数据，是找到**影响系统决策的等价类**。

做法是二维覆盖矩阵，例如「数据结构 × 操作类型」或「意图类别 × 表达方式」。**每个高风险格子先选 1–2 个代表样本**，不围绕每个具体对象复制一批相似 Case。

**同一格里换个说法走同一条解析路径，测一条即可。**

什么时候该拆细：如果同一格子里的样本表现明显不同（例如单动作和多动作在删除操作上失败模式不同），说明等价类太粗，需要拆分。**没有证据时不提前制造大量组合。**

于是「要写多少条」变成一个有用的问题：

> 影响系统决策的核心风险格子，是否都有代表样本？

**别忘了对抗桶**（覆盖不只有典型和边界）：

```
输入变体      非目标语言、非文本格式（XML/JSON/Markdown/CSV）、其他模态
上下文复杂    多意图同请求、错别字、超短/超长上下文、歧义的工具返回、多工具调用
个性化/对抗   越狱尝试、格式操控请求、用户指令与系统指令冲突
```

## 6. 分层是标签，不是五份文件

| 视图 | 作用 | 进入条件 | 通过率目标 |
|---|---|---|---|
| Golden | 核心能力，绝不能退化 | expected 已确认，断言稳定 | 接近 100% |
| Iteration | 本次需求改变的规则和边界 | 能追溯到具体需求 | — |
| Risk | 安全、异常、高风险场景 | 有明确失败影响 | 单独统计 |
| Regression | 历史 Bug 和易复发能力 | 有历史结果或缺陷来源 | 接近 100% |
| Capability | 探索能力边界 | — | **允许低通过率起步** |
| Observation | 暂时无法稳定判分 | — | **不进正式通过率** |

它们是标签不是文件。一条来自历史高风险 Bug 的核心 Case 可以同时是 `Golden + Risk + Regression`。用标签维护比复制多份文件稳——否则改一条 Case 就会出现几个版本不一致。

**两条纪律**：
- 调优用的数据和验收用的数据必须隔离，否则是自己给自己判卷
- 警惕**评测饱和**：全 100% 就只剩回归信号、没有改进信号，分数爬高后要主动加更难的题

## 7. Bad Case 回流：具体怎么做

这是数据集从「一次性造完」变成「活资产」的关键，也是最容易只喊口号的一步。

### 第一步：先归因，不是所有失败都回流

拿到一条失败，先分类，**不允许一步归因到「模型能力不行」**：

| 归因 | 处置 |
|---|---|
| 需求/规则没定义清楚 | 回去补规则表，**Case 先撤出** |
| Case 标注错了 | 修 Case，不算缺陷 |
| 断言写错或太严 | 修断言 |
| 环境/接口异常 | 记为 ERROR，不进通过率 |
| Prompt 表达问题 | 修 Prompt，**回流** |
| 模型能力问题 | 记录并**回流** |

**只有确认的真实缺陷才值得沉淀成长期资产。** 需求没确认、数据错、环境异常的失败先完成归因再说。

### 第二步：回流时不能只存那句话

只保存原始句子，修复的是一句话；要修复的是**一类失败模式**。所以回流一条 Bad Case 至少记：

```
原始输入（脱敏后）
expected 与 actual
它违反了哪条断言
它属于覆盖矩阵的哪个风险格子
失败归因结论
关联的缺陷单号 / trace_id
```

### 第三步：反向更新覆盖模型

这一步最常被跳过。既然这个格子漏出了问题，就要问：

- 这个风险格子的代表样本**够不够**？要不要补同类？
- 这个失败模式是否说明**等价类划粗了**，需要拆分？
- 有没有**相邻格子**存在同样风险但还没覆盖？

### 第四步：处理好视图归属

- 修复后的 Bad Case 进 **Regression**，**永久保留**，目标 100%
- **同一条不能再留在盲测集**——它已经被针对性优化过，留着会高估泛化能力
- 盲测集少掉的那条，要**补一条未见过的新题**

### 第五步：定期体检

Regression 集只增不减会膨胀到跑不动。定期审查：这条对应的失败模式是否还存在？规则是否已经变了？规则变了的 Case 要么更新 expected，要么归档说明原因——**不能默默删掉**。

## 8. 脱敏：真实数据进评测集之前

用线上真实 Query 是对的，但**未经脱敏的真实数据不允许进评测集**，尤其是要开源、要给外部看、要进 CI 的数据集。

### 第 0 步：先判断这份数据需不需要脱敏

不要一上来就执行脱敏流程。先算清楚**风险面**：

```
风险面 = 你取了哪些字段 × 这些字段里可能出现什么
```

三种情况，处置完全不同：

| 情况 | 处置 |
|---|---|
| 取的字段里**不可能**出现个人信息 | **不需要脱敏**，直接用 |
| 只有一个自由文本字段**可能**混入个人信息 | 只对这个字段扫一遍直接标识 |
| 带用户档案、账号、历史记录等结构化上下文 | 走完整脱敏流程 |

**实例 · 意图分类**：判定只需要用户那一句话，不需要账号、不需要档案、不需要设备信息。所以风险面只有一个字段——那句 query 本身。

而「今天卧推 60kg 做了 4 组」这种句子里根本没有个人信息，**这类 Case 不需要任何脱敏动作**。只有当用户在自然语言里自己带出信息时（「我叫张伟，今天练胸」「我住朝阳区，附近健身房…」）才需要处理。

所以意图分类的脱敏工作量，实际上就是：**对 query 文本扫一遍直接标识，命中的替换掉，没命中的原样入库。** 不涉及任何结构化字段处理。

反过来，如果评测的是「带用户历史的多轮对话」或「个性化推荐」，取的字段一多，风险面立刻放大，那就得走完整流程。

**先做这个判断，能让大部分场景的脱敏成本降到接近零。**

### 再按「给谁看」定投入

脱敏强度由**数据流向哪里**决定，不是越严越好：

| 数据去哪 | 做到什么程度 |
|---|---|
| 只在内网跑 CI | **处理直接标识就够了** |
| 团队之间共享 | 直接标识 + 抽检 |
| 对外开源 / 给外部方 | 再加准标识符降精度和残余风险检查 |

大多数团队的真实场景是第一、二档。**上来就套医疗行业那一套，会因为做不动而干脆不做，反而更糟。**

### 最省事的脱敏是不采集

在拿真实数据之前先问：这条 Case 的判定到底需要什么？意图分类需要的只是那句话，不需要用户档案、不需要账号、不需要设备信息。

**能用合成数据搭起骨架的阶段，就别碰真实数据**（本项目 iter-1 全部是合成数据，压根不涉及脱敏）。真实数据只在「合成数据不够真、评不出真问题」的时候才引入。

### 最小可执行版：三步

**第一步 · 只抓直接标识**

```
姓名、手机号、邮箱、身份证、银行卡、账号 ID、设备 ID、IP
URL 里的 token 和 query 参数
```

这几类有固定格式，现成库或几条正则就能覆盖掉绝大部分风险。**先把这一步做完，比纠结准标识符更重要。**

**第二步 · 替换成占位符，别删**

```
原始：我叫张伟，手机 138xxxx1234，今天卧推 60kg
脱敏：我叫[姓名]，手机[手机号]，今天卧推 60kg
```

**第三步 · 抽检**

脱完随机抽 10~20 条自己读一遍，确认两件事：没有漏网的标识信息、句子的语义和口语风格没被洗坏。

三步做完就可以用了。

### 什么时候才需要升级

出现下面任何一条，再往上加：

- **要开源或给外部方** → 补准标识符处理：日期只留到年、地址只到市、罕见特征做泛化
- **涉及健康 / 支付 / 未成年人数据** → 补一次「无实际知识」检查：凭剩下的内容能不能定位到具体某个人
- **数据量大到人工抽检不过来** → 上现成的自动化流水线（见下）

垂直领域要多留个心眼：**一条足够罕见的描述本身就可能是准标识符**——比如某个特定伤病加特定训练方式的组合，全国可能就那么几个人。

### 三条操作原则

**1. 替换，不要删除。**
直接删字段会改变输入的语言分布，模型看到的句子结构就变了，评测结果失真。用占位符保持结构：

```
原始：我叫张伟，手机 138xxxx1234，今天卧推 60kg
脱敏：我叫[姓名]，手机[手机号]，今天卧推 60kg
```

**2. 同一实体一致映射。**
同一条对话里的同一个人必须映射到同一个占位符，否则多轮里的指代关系直接断掉，这条 Case 也就废了。跨 Case 之间则应当**不一致**，避免通过占位符反查真人。

**3. 保留决策相关特征。**
脱敏的目标是去标识，不是把句子洗成标准书面语。**口语、错别字、语序混乱、方言词、情绪——这些恰恰是模型会出错的地方，必须保留。** 把「今儿个练了个胸，累死爹了」洗成「今天进行了胸部训练」，这条 Case 就失去价值了。

### 两条纪律

- **映射表不与数据集同存**：占位符到真实值的对照关系单独存放、单独授权，绝不进版本库
- **脱敏后必须抽样人工复核**：确认没有漏网的标识信息，也确认语义没有被洗坏

### 量大了再上工具

人工加几条正则撑不住的时候，用现成的，别自己造。开源的 Microsoft Presidio 是两段式：先识别（正则抓格式化实体 + NLP 抓人名地名），再处理（replace / mask / redact / hash 等算子）。它默认就是替换成 `<PHONE_NUMBER>` 这类实体占位符，跟上面的做法一致。

选算子只记一条：**评测数据集默认用 replace（占位符），慎用 redact（直接删）**——删会改变文本分布。

### 留个记录

哪些字段处理过、抽检了多少条、结论是什么，写两行就够。**数据集一旦对外分享，这两行就是你的依据。**

## 9. 新项目启动八问

```
1. 系统在做什么决策？
2. 成功、失败和需要澄清分别是什么？
3. 结果从哪里稳定观察？
4. 每条 Case 是否同时有 expected 和 grader？
5. 数据来自真实场景，还是 AI 凭空生成？
6. 覆盖了哪些业务对象、系统行为和高风险语境？
7. 无法稳定判分的数据是否隔离为 Observation？
8. Bad Case 是否回流，并更新了覆盖模型？
```

**前四问回答不了，先别批量造数据；后四问长期没更新，那它只是一个静态样本文件，不是评测资产。**

---

## 一句话总结

> 评测数据集设计，就是先定义系统决策和成功标准，把每条数据做成可判定的评测契约，再用风险矩阵选择代表样本，最后通过真实 Bad Case 持续更新覆盖模型。

AI 可以快速生成表达变体，但**什么值得测、什么叫正确、什么能进正式通过率，仍然由人判断。**

## 实例：对照六步看本项目的数据集

当前数据集 `eval/datasets/intent-dataset.jsonl`，**40 条**：分类 34、故障注入 3、输入防御 3。24 个 category，三视图 discovery 16 / regression 8 / locked 16。

| # | 步骤 | 本项目做到哪一步 |
|---|---|---|
| 1 | 定决策 | ✅ **PRD §3.4 十条标签决策表**是唯一事实源。每条规则就是一个等价类：否定转折含正向事实→record、纯否定→reject、未来+已发生混合→record…… |
| 2 | 定契约 | ⚠️ **有一半**。有 `case_id / input / expected / category / risk / views`，**缺 `source` 和 `assertion`** |
| 3 | 定覆盖 | ✅ 24 个 category 就是等价类清单，每类挑代表不穷举。**对抗桶只覆盖了提示注入** |
| 4 | 定分层 | ✅ 三视图互斥，discovery 与 locked 不重叠。⚠️ 但 locked 调优期被看过，**不是独立盲测集** |
| 5 | 定来源 | ❌ **全部是 PRD 驱动的人工合成数据**，无真实用户 Query。因为不涉及真实数据，**当前不需要脱敏** |
| 6 | 定回流 | ✅ 走通过一次：提示注入 Case 暴露后从 locked 转入 regression 并补新题。⚠️ 但只存了句子，**没记失败模式标签** |

### 一条真实数据长什么样

```json
{"case_id":"intent-record-003","input":"今天没练卧推，改练深蹲5组","expected_intent":"record","category":"record-negative-correction","risk":"high","views":["discovery"]}
```

它能追溯到 PRD 决策表第 3 条「否定/纠正之后含已发生正向事实 → record」。这就是「数据从规则来」的意思——**不是先造句子再猜答案**。

### 明确的缺口（下一步补，不是现在补）

1. **补 `source` 字段** — 现在看不出某条 Case 为什么存在、规则变了该找谁确认
2. **补 `assertion` 字段** — 断言目前隐含在 Runner 代码里，数据本身不声明判定方式，换个执行器就丢了
3. **补对抗桶的输入变体** — 中英混合、错别字、超长噪声、非文本格式（JSON/Markdown 片段），目前一条都没有
4. ~~建独立 blind holdout~~ — **暂不做**。日常迭代不需要，等真要对外报准确率数字时再说
5. **回流时记失败模式** — 不只存句子，还要记违反了哪条断言、属于哪个风险格子
6. **等有真实用户后替换合成数据** — 届时按第 0 步先判断风险面，再决定脱敏强度

**优先级**：1、2 最便宜且立刻提升可维护性；3 能真正发现新问题；4 成本最高，等评测计划 Review 通过再动。
