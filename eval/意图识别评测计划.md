# 意图识别评测计划

> 状态：待 Review
> 适用范围：fit-agent 单轮 `record / query / reject` 意图路由
> 执行原则：每个门禁 Review 通过后，才进入下一步；本文先定义方案，不代表已经开始新一轮正式评测

## 1. 评测目标

本轮要回答：

> 在未针对单条结果调优的输入上，当前模型能否稳定把用户输入路由到 `record / query / reject`，尤其不会把纯否定、未来计划、咨询或提示注入错进有副作用的 `record`？

评测对象是模型与 Router 组成的单轮意图识别链路，包括：

- 模型输出的意图语义；
- JSON 格式与本地解析；
- Router 错误契约；
- Trace 完整性；
- 多次运行稳定性。

本轮不评测：

- extractor 和训练字段抽取；
- 训练记录写入；
- 查询执行；
- HTTP 接口；
- 多轮上下文；
- 前端展示。

业务标签边界以 `docs/prd-iter1-intent.md` 为唯一事实源。写不出唯一 expected 的输入不进入正式分数，先标记 `disputed`。

## 2. Review 门禁

```text
范围与断言 Review
  → 数据集设计 Review
  → Runner 与指标 Review
  → 正式执行与退出 Review
```

### 门禁一：范围与断言

- [ ] 三个意图的定义和易混淆边界已经确认；
- [ ] 每条正式 Case 能写出唯一 expected；
- [ ] 成功、解析失败、超时和 API 错误均有稳定观测字段；
- [ ] 高风险错分和普通错分的阻塞口径已经区分；
- [ ] 非目标没有混入本轮数据集。

### 门禁二：数据集设计

- [ ] 数据来源、分类维度和覆盖矩阵已经 Review；
- [ ] Case 字段足以追溯规则、来源和标注理由；
- [ ] 数据量有覆盖依据，不是为了凑整数；
- [ ] discovery、blind holdout、regression 和 contract 职责互斥；
- [ ] Prompt few-shot 与 blind holdout 完成泄漏检查；
- [ ] 正反例和三类基本平衡；
- [ ] disputed Case 不进入正式通过率。

### 门禁三：Runner 与指标

- [ ] 单测和 Stub 契约全绿；
- [ ] Runner 能按数据视图运行；
- [ ] parse error 和 timeout 不会被剔除美化结果；
- [ ] 报告包含模型、Prompt hash、数据集 hash 和逐 Case trace_id；
- [ ] 指标包含混淆矩阵、分类别 P/R/F1、macro-F1 和高风险错分；
- [ ] 多次运行的稳定性计算口径已经确认；
- [ ] 运行前后零业务写入验证有效。

### 门禁四：正式执行与退出

- [ ] 先完成 discovery 和 regression，再冻结候选版本；
- [ ] blind holdout 在冻结后执行，执行前不查看单条答案；
- [ ] 所有失败完成人工归因；
- [ ] 范围内稳定失败已修复并进入 regression；
- [ ] 修复后使用新的未见 holdout 验证，不复用已暴露题冒充盲测；
- [ ] 正式报告写清样本量、适用范围和不能外推的结论。

## 3. 数据集分类

每条 Case 同时标记三个维度，避免把生命周期、成熟度和风险类型混成一套名字。

### 3.1 生命周期

| lifecycle | 用途 | 是否允许针对结果调 Prompt |
|---|---|:---:|
| `discovery` | 找边界、跑 baseline、开发 Prompt | 是 |
| `blind_holdout` | 估计未见数据上的泛化质量 | 否 |
| `regression` | 防止已修复问题复发 | 可以修，但 Case 永久保留 |
| `contract` | timeout、API error、parse error 等契约 | 不涉及模型语义 |

当前 `locked` 数据保留为 Iteration 1 历史验收集，不再把它当作严格独立盲测。

### 3.2 质量成熟度

| quality_tier | 定义 |
|---|---|
| `golden` | expected 唯一、来源可靠、断言稳定、长期必须守住 |
| `standard` | 规则明确且可断言，但仍需验证稳定性 |
| `robust` | 模糊、对抗或探索性输入，不要求首轮全过 |
| `disputed` | 产品、开发或测试对 expected 有分歧，不计正式分数 |

### 3.3 风险类型

- `standard_positive`：清晰正例；
- `pure_negative`：纯否定、休息陈述；
- `negative_correction`：否定后包含正向事实；
- `future`：纯未来或未来与已发生事实混合；
- `no_object`：有训练语气但无训练对象；
- `consultation_boundary`：训练咨询与本人记录查询的边界；
- `multi_intent`：一句话包含多个意图；
- `prompt_injection`：要求指定分类、输出或忽略规则；
- `noisy_expression`：口语、省略、错别字、中英混合和长噪声；
- `context`：多轮和历史状态，登记但不进入本轮正式范围。

## 4. 数据来源与造数流程

来源优先级：

1. 脱敏后的真实使用 Query；
2. 用户反馈；
3. 已复现的线上或测试 Bad Case；
4. 产品、测试和领域专家构造；
5. LLM 或人工生成的规整合成句。

当前 fit-agent 尚无真实流量，新一轮数据需要明确标注 `source_type`，不能把专家构造或 LLM 合成数据写成真实数据。

造数流程：

```text
从 PRD 提取规则和混淆边界
  → 建覆盖矩阵
  → 为每个格子寻找真实种子
  → 真实不足时由专家构造
  → 用表达维度生成候选
  → 人工去重和筛选
  → 双人独立标注
  → 分歧项进入 disputed
  → 泄漏检查
  → 冻结 blind holdout
```

表达变化至少覆盖：

- 领域专业度：新手、普通用户、训练老手；
- 信噪比：极短、省略、冗长、夹杂无关信息；
- 情绪：急躁、疲惫、随意、礼貌；
- 表达风格：陈述、疑问、命令、错别字、中英混合。

LLM 可以生成候选，但不能同时负责生成、标注和最终审核。

## 5. Case 字段

建议新一版 Case 使用：

```json
{
  "case_id": "intent-reject-001",
  "input": "今天没练卧推，改成休息",
  "expected_intent": "reject",
  "forbidden_intents": ["record"],

  "lifecycle": "blind_holdout",
  "quality_tier": "golden",
  "risk_type": "pure_negative",
  "risk_level": "high",

  "source_type": "expert_constructed",
  "source_ref": "docs/prd-iter1-intent.md#3.4-rule-5",
  "rule_id": "intent-rule-5",
  "label_status": "confirmed",
  "label_reason": "纯否定且没有已发生的正向训练事实",

  "language": "zh-CN",
  "expression_style": ["spoken", "negative"]
}
```

必须字段：

- `case_id`、`input`、`expected_intent`；
- `lifecycle`、`quality_tier`、`risk_type`；
- `source_type`、`rule_id`、`label_status`、`label_reason`。

高风险 Case 必须增加 `forbidden_intents`，用于直接表达“绝不能错到哪里”。

## 6. 数量与覆盖

下一步先建设 60 条独立 blind holdout，不急着扩成几百条：

| 类别 | 数量 | 主要覆盖 |
|---|---:|---|
| record | 20 | 清晰事实、缺字段、否定转折、未来+事实、多记录、噪声 |
| query | 20 | 日期、动作、历史、部位查询、咨询边界、口语省略 |
| reject | 20 | 纯否定、纯未来、无对象、咨询建议、越界、注入、情绪 |

选择 60 条的依据：

- 三类可以基本均衡；
- 每类 20 条能覆盖多个失败机制；
- 仍能逐条人工 Review；
- 单条错误影响总分约 1.67%，比当前 15 条验收集更稳定；
- 定位是首版独立质量估计，不对外称行业 benchmark。

数量门槛不能替代覆盖矩阵。60 条同义改写不等于覆盖 60 个风险场景。

## 7. 执行顺序

```text
1. 单测和 Stub 全量
2. discovery baseline
3. Prompt 修复与 regression 回归
4. 冻结模型、Prompt、数据集和 Runner 版本
5. blind holdout 正式运行
6. 查看单条结果并人工归因
7. 稳定 Bad Case 修复后进入 regression
8. 下一轮补充新的未见 holdout
```

命令入口见 [评测 README](README.md)。

## 8. 失败归因

每条失败必须归入以下一类，不能直接写“模型能力问题”：

| 归因 | 判断 | 后续动作 |
|---|---|---|
| 规则未确认 | PRD 无法给唯一 expected | 转 disputed，找产品确认 |
| 标注错误 | expected 与已确认规则不符 | 修标注，记录原因 |
| Prompt 表达 | 规则明确但模型稳定误判 | 调 Prompt，加入 regression |
| 模型波动 | 相同版本重复运行结果不同 | 报告分布，评估是否阻塞 |
| 解析器 | 语义正确但格式无法解析 | 修解析或 Prompt 格式，契约回归 |
| 上下文污染 | 历史或多轮改变了路由 | 移入 context 专项 |
| Runner/断言 | 结果正确但判分错误 | 修测试工具并复跑 |
| 环境/API | timeout、服务异常、版本不一致 | 与语义指标分账，环境恢复后复验 |

## 9. 候选通过标准

以下标准必须在正式运行前 Review 并冻结：

- 单元测试和 Stub 契约：100%；
- regression：三轮全部通过；
- blind holdout macro-F1：≥ 0.90；
- blind holdout 每类 Recall：≥ 0.85；
- parse error：0；
- `reject → record`：0；
- 纯否定、纯未来、咨询、注入等高风险 Case 错进 `record`：0；
- timeout、API error 与语义错误分账，不允许删除失败样本美化分数；
- disputed Case 不计正式指标，单独列出。

整体分数不能覆盖高风险门禁。即使 macro-F1 达标，只要“今天没练”被判成 `record`，本轮仍不通过。

## 10. 评测交付物

一次完整评测必须交付：

- 已 Review 的评测计划；
- 数据集及覆盖矩阵；
- 数据集 Review 记录；
- 可复跑 Runner；
- 原始逐 Case 结果和 Trace；
- 正式评测报告；
- Bad Case 归因与回归清单；
- 退出结论和适用范围说明。

## 11. 本轮 Review 顺序

当前先 Review 数据集，不立即造数。顺序为：

1. 确认三维分类；
2. 确认 Case 字段；
3. 确认 60 条 blind holdout 的覆盖矩阵；
4. 确认造数人与标注方式；
5. 确认通过标准；
6. 主人明确通过后再生成数据。
