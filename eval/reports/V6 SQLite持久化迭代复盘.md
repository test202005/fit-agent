# V6 SQLite 持久化与数据一致性迭代复盘

> 日期：2026-09-05
> 代码提交：`e6f75b2`
> 设计修订：`446a69c`
> 当前结论：V6 已完成准出，后续不扩展数据库平台能力。

## 1. 为什么做

V4 已经具备 Tool Use，Agent 可以产生真实训练记录。原来的 JSONL 足够支持早期 workflow 和确定性测试，但无法真实验证数据库场景下的持久化、用户隔离、事务回滚、请求重试和应用重启恢复。

本轮只回答一个问题：

> Agent 产生的数据，能不能可靠保存、查询、隔离和恢复？

选择本地 SQLite，是为了增加真实持久化证据，同时保持一条命令可运行；没有提前引入 ORM、远程数据库、连接池或数据库平台。

## 2. 实现内容

- `SQLiteStorage` 成为默认 HTTP 存储实现；
- `FakeStorage` 继续承担单测替身，`JsonlStorage` 保留为教学对照；
- 请求上下文增加 `user_id` 和 `request_id`，`trace_id` 继续只负责执行追踪；
- 记录使用 UUID，业务时间 `ts` 与数据库写入时间 `created_at` 分开保存；
- 同一 `user_id + request_id` 只写入一次，重试返回首次写入的记录 ID；
- 多条记录在同一个 SQLite 事务中写入，任意一条失败则全部回滚；
- 查询必须带用户范围，不能先读取全库再由上层过滤。

## 3. 实现中发现的问题

### 3.1 设计返回值没有闭环

初版设计要求返回 `idempotent_replay`，但 Storage 仍只返回 ID 列表，Pipeline 无法把幂等状态传给 HTTP。修复为 `StorageWriteResult`，并增加 HTTP 重试测试。

### 3.2 时间拼接 ID 会冲突

旧 ID 由业务时间和序号组成。Frozen Clock 下两个请求会生成相同主键，SQLite 将这个隐患直接暴露为完整性错误。修复为 UUID，时间只承担业务语义。

### 3.3 业务时间和写入时间混用

PRD 要求同时保留训练发生时间和创建时间，初版 Schema 只有 `ts`。修复后 `ts` 用于业务查询，`created_at` 用于追踪排障。

### 3.4 数据隔离被误认为鉴权

A/B 用户查询不串数据，只能证明作用域过滤正确。由于本轮 `user_id` 仍由请求传入，因此不能据此宣称完成身份认证和权限控制。该边界被写入设计和验收结论。

## 4. 验证证据

```text
.venv/bin/python -m pytest -q
147 passed
```

新增 SQLite 证据包括：

- 写入后重新创建 `SQLiteStorage`，记录仍可读取；
- HTTP 写入后重新创建 Flask 应用，再通过 HTTP 查询成功；
- A 用户不能读取 B 用户记录；
- 同一请求的多条记录重试不重复写入；
- 相同业务时间下不同请求的记录 ID 仍唯一；
- 批量写入中途失败时，记录和请求登记一起回滚；
- 默认 `create_app()` 自动初始化本地 SQLite 文件。

既有四套 Stub 评测仍保持全绿：Intent、Extract、Query、Tool Use；它们验证的是模型调用编排和业务契约，不替代 SQLite 专项证据。

## 5. 准出与边界

V6 PRD 的 8 条准出条件均已覆盖：默认初始化、旧实现回归、真实 HTTP 重启恢复、隔离/事务/幂等、故障注入、全量回归、问题复盘和范围收口。

本轮没有证明：真实身份鉴权、复杂权限、MySQL/PostgreSQL 兼容、Schema 迁移、高并发性能和连接池表现。这些属于后续有真实需求时再立项的问题。

## 6. 可迁移结论

企业级不等于堆数据库组件。对当前项目，最小但有价值的企业能力是：状态可持久化、数据有作用域、写入可回滚、重试可解释、重启可恢复、证据可复跑。每增加一层状态复杂度，都要同步增加可观测点、失败注入和回归断言。
