## V3.0 · 迭代三（2026-09-03）

### P-001 日期校验接受非零填充，导致范围过滤静默出错

**类型**：正确性 · 静默失真
**严重度**：高（不报错、不崩溃，只是结果悄悄错了）

**现象**
`backend/query.py` 的 `_is_date()` 最初直接用 `datetime.strptime(value, "%Y-%m-%d")` 校验日期，写单测时发现 `2026-9-3` 竟然通过了校验。

**为什么是问题**
Python 的 `strptime` 接受非零填充的月份和日期。而查询的范围过滤用的是**字符串比较**：

```python
plan["from"] <= _row_local_date(row) <= plan["to"]
```

字符串比较下 `"2026-9-3" > "2026-10-01"` 为真——只要模型某次返回了非零填充日期，查询范围就会错，而且**不抛异常、不崩溃，只是返回的记录数不对**。用户不会发现，统计会失真。

**怎么修的**
严格要求长度为 10 且分隔符位置固定，再交给 strptime 校验语义：

```python
if not isinstance(value, str) or len(value) != 10:
    return False
if value[4] != "-" or value[7] != "-":
    return False
```

**其他可选修法（当时未采用）**
- 改用 `date.fromisoformat()`：Python 3.11+ 才严格，3.9 环境行为不同，不选
- 不用字符串比较，转成 date 对象再比：更彻底，但要改动执行层的比较逻辑，超出本轮范围

**怎么验证的**
单测 `test_parse_invalid_plans` 参数化用例中加入 `{"type":"list_by_date","date":"2026-9-3"}`，断言必须抛 `ValueError`。

**出处**：commit `581353d`，`backend/query.py:_is_date`

### P-002 `data/` 未加入 .gitignore，用户数据会被提交

**类型**：配置疏漏
**严重度**：中（一旦发生难以完全撤销）

**现象**
`JsonlStorage` 默认写入 `data/records.jsonl`，但 `.gitignore` 里没有 `data/`。

**为什么是问题**
任何人跑起服务或跑一次真实写入，这个文件就会出现在 `git status` 里，很容易被 `git add -A` 一起提交。里面是用户的训练记录——属于业务数据，不该进版本库；一旦提交，历史里就永远留着。

**怎么修的**
`.gitignore` 增加 `data/`。

**怎么验证的**
`git status --short` 确认跑过服务后 `data/` 不出现在未跟踪列表。

**出处**：commit `581353d`，`.gitignore`

### P-003 每个 HTTP 请求都新建 LiveLLM 实例

**类型**：性能 · 不影响正确性
**严重度**：低

**现象**
`backend/app.py` 中写法为 `client = app.config["LLM"] or LiveLLM()`，`or` 的右侧在每次请求都会执行。

**为什么是问题**
每次请求都新建一个 OpenAI client，意味着重建 HTTP 连接池。功能上正确，但并发一上来就是浪费。**不影响任何测试结果**，属于代码质量问题。

**怎么修的**
改为懒创建但只建一次，创建后写回 `app.config`：

```python
client = app.config["LLM"]
if client is None:
    client = LiveLLM()
    app.config["LLM"] = client
```

**怎么验证的**
现有 HTTP 单测全部通过（注入 LLM 时不受影响）；无新增用例——这一点是缺口，见下方备注。

**备注**：严格说这条应该补一个「同一个 app 多次请求只创建一次 client」的单测，否则以后重构可能改回去。当前未补。

**出处**：commit `581353d`，`backend/app.py`

## V4.0 · 迭代四（2026-09-03）

### P-004 Prompt 规则过度泛化，导致模型拒绝调用本该支持的工具

**类型**：Prompt 表达 · 能力误关闭
**严重度**：高（用户会认为功能缺失，但代码其实是好的）

**现象**
真实模型冒烟时，输入「这周卧推了几次」，模型**没有调用 `count_exercise`**，反而回复「按身体部位统计次数暂不支持」。而 `count_exercise` 正是为这类查询设计的。

**为什么是问题**
Prompt 原文第 8 条写的是：

> 查询按身体部位统计次数（如「这周练了几次腿」）、重量趋势、进步分析都不支持

模型把「按部位统计不支持」**过度泛化成「按次数统计都不支持」**，于是把按动作统计也一并拒绝了。

关键点：**这是 Prompt 表达问题，不是模型能力问题，也不是代码 bug。** 工具本身、参数校验、执行逻辑全部正常。如果归因成「模型能力不行」，就会走向换模型或加 few-shot，方向完全错。

它也说明一件事：**一条否定式规则如果没有划清边界，模型倾向于扩大否定范围。**

**怎么修的**
把第 8 条从单一否定句拆成正反对照，显式给出支持的情况：

```
8. 区分两种统计，不要混淆：
   - 按具体动作统计次数（「这周卧推了几次」）支持，调用 count_exercise
   - 按身体部位统计次数（「这周练了几次腿」）不支持，因为部位和动作没有对应表
   - 重量趋势、进步分析、和别人比较不支持
```

**其他可选修法（当时未采用）**
- 加 few-shot 示例：能修好，但 prompt 变长、token 成本上升，且没有解决"规则表述不清"的根因
- 换模型：方向错误，问题不在模型

**怎么验证的**
修复后重跑冒烟，「这周卧推了几次」正确调用 `count_exercise` 且日期范围正确（`from=2026-08-31` 周一起算）；随后 live 评测 discovery/regression/locked 三视图各三轮全部通过。

**出处**：`backend/prompts/agent_system_v1.txt` 第 8 条

### P-005 工具执行器最初用全局变量传 trace_id

**类型**：设计缺陷 · 并发不安全
**严重度**：中（当前单线程无实际影响，但会在并发时出错）

**现象**
`backend/tools.py` 初版用模块级全局字典 `_CURRENT_TRACE` 传递 trace_id，配一个 `set_current_trace()` 函数。

**为什么是问题**
工具执行器需要 trace_id 才能落库，但工具签名只收 `args`。用全局变量传有三个问题：并发请求会互相覆盖；调用方必须记得先 `set_current_trace`，属于隐式依赖；测试之间会串状态。

**怎么修的**
`make_executors()` 本来就是工厂函数，直接让它多收一个 `trace_id` 参数，由闭包捕获。每次请求各自构造一组执行器，天然隔离。

**怎么验证的**
`test_written_record_carries_trace_id` 断言落库记录带正确 trace_id；全局变量与 setter 已删除。

**出处**：`backend/tools.py:make_executors`

### P-006 架构对比实验缺 token 成本维度

**类型**：交付缺口
**严重度**：低（不影响结论方向，但 PRD 列了这一项）

**现象**
[iter-4 PRD](../../docs/prd-iter4-tooluse.md) 第 6 节列了五个对比维度，其中 **Token 成本**未实测——`run_architecture_compare.py` 只记录了通过率、耗时、写入/查询次数。

**为什么是问题**
「工具描述会进 prompt，成本上升多少」是判断该不该上工具调用的重要依据，尤其在高频调用场景。缺这一项，成本结论只能靠推测。

**当前状态：已修（2026-09-04）。**

**怎么修的**
`run_fixed` / `run_tools` 原先把 `Tracer(TRACE_PATH)` 内联在调用里，事件拿不到。改成持有 tracer 变量，再用 `eval/stability.py` 的 `collect_usages` 从 trace 事件收集 usage，两种架构同口径统计调用次数与 token。

与本条原先设想的补法有一处偏离，需记录：token **走 trace 事件，不透出到业务返回结构**。原因是返回结构受契约断言约束（字段集合必须精确匹配），往里塞可观测数据会让契约断言失去意义。

**怎么验证的**
`.venv/bin/python eval/run_architecture_compare.py --runs 2`，12 场景 × 2 轮真实模型。两轮 token 数字完全一致（温度 0 下 prompt 长度稳定），报告新增「成本」一节。事实源 `eval/results/arch-compare-20260904T015019Z.md`。

**修完之后推翻了本条自己的假设**

本条原文写的是「工具描述会进 prompt，成本上升多少」——预设工具调用更贵。实测相反：

| 架构 | 调用次数/请求 | token/请求 | 平均耗时 |
|---|---:|---:|---:|
| 固定链路 | 1.80 | 1304.5 | 2084ms |
| 工具调用 | 1.00 | 1187.2 | 1371ms |

工具调用每请求便宜 117 token（-9.0%）、快 713ms（-34%）。原因是固定链路每个请求要走**两次**模型（路由一次、抽取或规划再一次），两次调用的 prompt 累加超过了工具 schema 塞进单次 prompt 的开销。

这条推翻只在当前规模成立：3 个工具、schema 很短。工具数量增长后单次 prompt 会变长，交叉点会移动。**不能推广成「工具调用总是更省」。**

**出处**：`eval/run_architecture_compare.py`

## V5.0 · 稳定性与成本口径（2026-09-04）

### P-007 intent Runner 的退出码把 REVIEW 当失败，与四态纪律矛盾

**类型**：口径不一致 · 评测工具自身缺陷
**严重度**：中（不影响结论正确性，但让 CLAUDE.md 里的验证命令永远返回非零）

**现象**
四个 Runner 的退出码逻辑不一致：

```python
# run_tool / run_extract / run_query
return 0 if all(r["verdict"] in {"PASS", "REVIEW"} for r in all_results) else 1
# run_intent
return 0 if all(result["pass"] for result in all_results) else 1
```

`intent-dataset.jsonl` 里 `intent-rb-003`、`intent-rb-004` 是 observation tier，恒判 REVIEW，`pass` 为 False。因此 `run_intent_eval.py --views all --run-mode stub` **永远返回退出码 1**，即便 56 条全 PASS、0 条 FAIL。

**为什么是问题**
项目自己的四态纪律写的是「REVIEW = 规则尚未定义唯一 expected 的探索题，跑但不判分，不污染通过率」。退出码是给 CI 和自动化用的最终判定，把 REVIEW 计为失败等于在退出码这一层推翻了四态纪律。后果是这条验证命令的非零退出码变成噪音——真出现 FAIL 时反而分辨不出来。

**为什么本轮不修**
超出 V5.0（稳定性与成本口径）范围，且退出码是验收契约的一部分，改它会改变 CLAUDE.md 中验证命令的判定行为，属于契约类改动，需要先确认。本轮只登记。

**验证方式**
```bash
.venv/bin/python eval/run_intent_eval.py --views all --run-mode stub --runs 2; echo "exit=$?"
# 现状 exit=1，PASS 56 / FAIL 0 / REVIEW 2 / ERROR 0
```

**溯源**：非本轮引入。`git show 9c0c534:eval/run_intent_eval.py` 显示 V4.0 关账版本即为此逻辑。

**出处**：`eval/run_intent_eval.py:603`
