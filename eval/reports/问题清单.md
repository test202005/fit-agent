### P-013 Prompt 把违规写法写成许可写法

**类型**：Prompt 规则缺陷 · 归因证据链
**严重度**：高

**现象**：`workout_generator_v1.txt` 规则 4 写：

> 动作不够时，**宁可重复同一个动作的多组**，也不要引入库外动作。

而动作库的设计是「一个格子一条动作」。真实模型在 pl-004（背 / 中高，该格子只有 `单臂哑铃划船` 一条）上忠实地照做，把同一条动作抄成 4 行，并在 note 里复述了这条规则：「动作库仅返回单臂哑铃划船一个动作，为满足 40 分钟训练量，重复该动作多组编排。」

**为什么是问题**：这句话把「不要引入库外动作」这个正当约束写成了「重复是保守的、被鼓励的选择」。规则没有错在约束方向，错在**它给出的兜底手段本身就是违规**。计划因此看起来合法：动作名条条来自观察库、时长合规、字段齐全——4 条黑盒断言全绿。

**怎么修的**：出 v2（`workout_generator_v2.txt`），规则 4 改为「动作库返回的条目不够时，就按现有几条输出，靠加大 sets 把 total_min 填到用户要求的时长；同一份计划里动作不允许重复出现」。v1 文件保留，通过 `backend/prompts/manifest.json` 切换版本，不原地覆盖。

**怎么验证的**：

- 当前 `test_duplicated_plan_items_detected_by_uniqueness_and_size` 固定复现缺陷形状，分别验证输出去重与过程数量上界断言失败；历史版本仅有数量上界断言；
- v1 + 新断言 live 跑出 `plan-report-20260915T163912Z.md`：pl-004 黑盒 4/4、白盒 4/5、FAIL；
- v2 live 跑出 `plan-report-20260915T164052Z.md`：Case 级 1.0000、断言级 84/84，`blackbox_blind_spots` 归 0，同一 Case 的计划变成 `1 条 sets=4`，note 改为「已通过增加组数将总时长填充」；
- 报告与 trace 均记录 `generator_prompt_version: v2` 和 `sha256:c181f75d...`。

**经典教训**：写「不要 X」时，给的兜底手段 Y 必须自己也合法。模型会严格按兜底手段执行，并且**在输出里引用它**——这类缺陷靠加断言只能拦住症状，Prompt 不改就换个形状再来。

**出处**：iter-5（`docs/prd-iter5-plan-generation.md`），复盘见 [V7 训练计划生成与可观测性迭代复盘](V7%20训练计划生成与可观测性迭代复盘.md) §3.3。

### P-014 断言集对「复制条目充数」完全盲

**类型**：断言覆盖缺口 · 「全绿」的假象
**严重度**：高

**现象**：v1 生成器在 pl-004 把同一条动作抄成 4 行，**8 条断言（黑盒 4 + 白盒 4）一条都没红**，页面上的结论是 Case 级 1.0000、断言级 77/77。

**为什么是问题**：白盒 4 条断言里最近的 `plan_actions_from_observation` 只检查「动作名是否来自观察」，而复制出来的每一条名字都来自观察，所以它抓不到。**断言不在该红的时候红不了，和没有这条断言等价**，而且更糟——它给出的是「白盒已经看住了」的错觉。

**怎么修的**：新增白盒断言 `plan_size_within_observation`——计划条数不得超过观察条数（`len(plan) <= observation["count"]`）。

校正：按计划内动作名去重不会误伤“观察 5 条、计划取 3 条不同动作”的合法子集。数量上界也不能识别“观察 A、B，计划 A、A”。当前同时保留 `plan_actions_unique` 与 `plan_size_within_observation`，分别检查重复和数量越界。

**怎么验证的**：

- **它在该红的时候红**：v1 + 新断言 live 重跑，pl-004 从 `4/4 4/4 PASS` 变成 `4/4 4/5 FAIL / plan_size_within_observation`，`blackbox_blind_spots` 从 0 变成 1 条；
- **它不是永远红**：`test_plan_size_assertion_stays_green_within_observation` 用正常 case 做对照，白盒 5/5 全绿；
- **红得可归因**：当前 `test_duplicated_plan_items_detected_by_uniqueness_and_size` 分别核对输出和过程的失败集合，避免额外失败被忽略；
- **修复后归零**：v2 live 断言级 84/84，`blackbox_blind_spots` 0 条。

**经典教训**：断言集全绿时，必须能回答「它是真的没发现问题，还是根本没在看」。唯一的区分办法是造一条确定会犯错的 case 看它红不红——这也是本项目 `blackbox_blind_spots` 这个指标存在的理由。

**出处**：iter-5 第 7 步「case 集 + 黑盒/白盒对照」，复盘见 [V7 训练计划生成与可观测性迭代复盘](V7%20训练计划生成与可观测性迭代复盘.md) §3.2。

## V6 · SQLite 持久化与数据一致性（2026-09-04）

### P-009 设计协议要求的返回字段没有落到 Storage 接口

**类型**：接口闭环 · 幂等可观测性
**严重度**：高

**现象**：设计要求业务返回 `idempotent_replay`，但初版 `append()` 仍只返回 `list[str]`，Pipeline 无法知道本次写入是首次执行还是幂等重放。

**怎么修的**：新增 `StorageWriteResult(written_ids, idempotent_replay)`，由 Storage 产生、Pipeline 原样透传；保留 `len()` 和下标兼容旧测试。

**怎么验证的**：`test_http_passes_user_and_request_context_to_sqlite` 验证首次请求为 `false`、重复请求为 `true`，且返回相同 ID。

**经典教训**：设计文档里新增一个业务字段时，必须沿着“存储 → 编排 → HTTP 返回 → 测试断言”走完整条数据流，不能只改最底层接口。

### P-010 基于业务时间生成记录 ID，在冻结时间下会冲突

**类型**：主键设计 · 测试暴露真实风险
**严重度**：高

**现象**：旧实现用业务时间和批次序号拼接 ID。Frozen Clock 或同一时刻的连续请求会生成相同 ID；切换 SQLite 后表现为主键冲突。

**怎么修的**：记录 ID 改为 UUID，业务时间只用于查询，不再承担唯一标识职责。

**怎么验证的**：`test_sqlite_ids_are_unique_with_same_business_time`。

**经典教训**：时间可以是业务字段，不能默认是唯一键；测试中的冻结时钟经常能提前暴露生产并发下的碰撞问题。

### P-011 PRD 的数据字段与数据库 Schema 不一致

**类型**：契约漂移 · 可追溯性缺口
**严重度**：中

**现象**：PRD 要求保存业务时间和创建时间，初版 Schema 只有 `ts`，缺少数据库写入时间 `created_at`。

**怎么修的**：明确 `ts` 是训练发生时间，`created_at` 是实际写入时间，并在 `workout_records` 中补齐字段。

**怎么验证的**：`test_sqlite_roundtrip_and_restart` 断言 `created_at` 存在，且重启后记录可读回。

**经典教训**：同名的“时间”往往承担不同语义；业务时间、写入时间和追踪时间必须分开定义。

### P-012 数据隔离被误写成鉴权能力

**类型**：安全边界 · 测试范围误判
**严重度**：高

**现象**：加入 `user_id` 后可以验证 A/B 用户查询不串数据，但客户端仍可自行传入任意 `user_id`，因此只能证明逻辑作用域，不能证明身份认证和权限控制。

**怎么修的**：查询接口强制显式用户范围；文档明确 `user_id` 只是测试上下文，不进入模型 Tool 参数，也不宣称已完成鉴权。

**怎么验证的**：`test_sqlite_user_isolation` 和 HTTP 上下文测试；未把本轮结果包装成权限安全结论。

**经典教训**：测试隔离、租户隔离和身份鉴权是三层不同能力，验证了前一层不能自动推出后一层。

**出处**：V6 实现提交 `e6f75b2`；设计修订提交 `446a69c`。

## V3.0 · 迭代三（2026-09-03）

### P-001 日期校验接受非零填充，导致范围过滤静默出错

**类型**：正确性 · 静默失真
**严重度**：高（不报错、不崩溃，只是结果悄悄错了）

**现象**
`backend/query.py` 的 `_is_date()` 最初直接用 `datetime.strptime(value, "%Y-%m-%d")` 校验日期，写单测时发现 `2026-9-3` 竟然通过了校验。

**为什么是问题**
Python 的 `strptime` 接受非零填充的月份和日期。而查询的范围过滤用的是**字符串比较**：

```python
plan["from"] <= _row_local_date(row) <= plan["to"]
```

字符串比较下 `"2026-9-3" > "2026-10-01"` 为真——只要模型某次返回了非零填充日期，查询范围就会错，而且**不抛异常、不崩溃，只是返回的记录数不对**。用户不会发现，统计会失真。

**怎么修的**
严格要求长度为 10 且分隔符位置固定，再交给 strptime 校验语义：

```python
if not isinstance(value, str) or len(value) != 10:
    return False
if value[4] != "-" or value[7] != "-":
    return False
```

**其他可选修法（当时未采用）**
- 改用 `date.fromisoformat()`：Python 3.11+ 才严格，3.9 环境行为不同，不选
- 不用字符串比较，转成 date 对象再比：更彻底，但要改动执行层的比较逻辑，超出本轮范围

**怎么验证的**
单测 `test_parse_invalid_plans` 参数化用例中加入 `{"type":"list_by_date","date":"2026-9-3"}`，断言必须抛 `ValueError`。

**出处**：commit `581353d`，`backend/query.py:_is_date`

**类型**：配置疏漏
**严重度**：中（一旦发生难以完全撤销）

### P-003 每个 HTTP 请求都新建 LiveLLM 实例

**类型**：性能 · 不影响正确性
**严重度**：低

**现象**
`backend/app.py` 中写法为 `client = app.config["LLM"] or LiveLLM()`，`or` 的右侧在每次请求都会执行。

**为什么是问题**
每次请求都新建一个 OpenAI client，意味着重建 HTTP 连接池。功能上正确，但并发一上来就是浪费。**不影响任何测试结果**，属于代码质量问题。

**怎么修的**
改为懒创建但只建一次，创建后写回 `app.config`：

```python
client = app.config["LLM"]
if client is None:
    client = LiveLLM()
    app.config["LLM"] = client
```

**怎么验证的**
现有 HTTP 单测全部通过（注入 LLM 时不受影响）；无新增用例——这一点是缺口，见下方备注。

**备注**：严格说这条应该补一个「同一个 app 多次请求只创建一次 client」的单测，否则以后重构可能改回去。当前未补。

**出处**：commit `581353d`，`backend/app.py`

## V4.0 · 迭代四（2026-09-03）

### P-004 Prompt 规则过度泛化，导致模型拒绝调用本该支持的工具

**类型**：Prompt 表达 · 能力误关闭
**严重度**：高（用户会认为功能缺失，但代码其实是好的）

**现象**
真实模型冒烟时，输入「这周卧推了几次」，模型**没有调用 `count_exercise`**，反而回复「按身体部位统计次数暂不支持」。而 `count_exercise` 正是为这类查询设计的。

**为什么是问题**
Prompt 原文第 8 条写的是：

> 查询按身体部位统计次数（如「这周练了几次腿」）、重量趋势、进步分析都不支持

模型把「按部位统计不支持」**过度泛化成「按次数统计都不支持」**，于是把按动作统计也一并拒绝了。

关键点：**这是 Prompt 表达问题，不是模型能力问题，也不是代码 bug。** 工具本身、参数校验、执行逻辑全部正常。如果归因成「模型能力不行」，就会走向换模型或加 few-shot，方向完全错。

它也说明一件事：**一条否定式规则如果没有划清边界，模型倾向于扩大否定范围。**

**怎么修的**
把第 8 条从单一否定句拆成正反对照，显式给出支持的情况：

```
8. 区分两种统计，不要混淆：
   - 按具体动作统计次数（「这周卧推了几次」）支持，调用 count_exercise
   - 按身体部位统计次数（「这周练了几次腿」）不支持，因为部位和动作没有对应表
   - 重量趋势、进步分析、和别人比较不支持
```

**其他可选修法（当时未采用）**
- 加 few-shot 示例：能修好，但 prompt 变长、token 成本上升，且没有解决"规则表述不清"的根因
- 换模型：方向错误，问题不在模型

**怎么验证的**
修复后重跑冒烟，「这周卧推了几次」正确调用 `count_exercise` 且日期范围正确（`from=2026-08-31` 周一起算）；随后 live 评测 discovery/regression/locked 三视图各三轮全部通过。

**出处**：`backend/prompts/agent_system_v1.txt` 第 8 条

### P-005 工具执行器最初用全局变量传 trace_id

**类型**：设计缺陷 · 并发不安全
**严重度**：中（当前单线程无实际影响，但会在并发时出错）

**现象**
`backend/tools.py` 初版用模块级全局字典 `_CURRENT_TRACE` 传递 trace_id，配一个 `set_current_trace()` 函数。

**为什么是问题**
工具执行器需要 trace_id 才能落库，但工具签名只收 `args`。用全局变量传有三个问题：并发请求会互相覆盖；调用方必须记得先 `set_current_trace`，属于隐式依赖；测试之间会串状态。

**怎么修的**
`make_executors()` 本来就是工厂函数，直接让它多收一个 `trace_id` 参数，由闭包捕获。每次请求各自构造一组执行器，天然隔离。

**怎么验证的**
`test_written_record_carries_trace_id` 断言落库记录带正确 trace_id；全局变量与 setter 已删除。

**出处**：`backend/tools.py:make_executors`

### P-006 架构对比实验缺 token 成本维度

**类型**：交付缺口
**严重度**：低（不影响结论方向，但 PRD 列了这一项）

**现象**
[iter-4 PRD](../../docs/prd-iter4-tooluse.md) 第 6 节列了五个对比维度，其中 **Token 成本**未实测——`run_architecture_compare.py` 只记录了通过率、耗时、写入/查询次数。

**为什么是问题**
「工具描述会进 prompt，成本上升多少」是判断该不该上工具调用的重要依据，尤其在高频调用场景。缺这一项，成本结论只能靠推测。

**当前状态：已修（2026-09-04）。**

**怎么修的**
`run_fixed` / `run_tools` 原先把 `Tracer(TRACE_PATH)` 内联在调用里，事件拿不到。改成持有 tracer 变量，再用 `eval/stability.py` 的 `collect_usages` 从 trace 事件收集 usage，两种架构同口径统计调用次数与 token。

与本条原先设想的补法有一处偏离，需记录：token **走 trace 事件，不透出到业务返回结构**。原因是返回结构受契约断言约束（字段集合必须精确匹配），往里塞可观测数据会让契约断言失去意义。

**怎么验证的**
`.venv/bin/python eval/run_architecture_compare.py --runs 2`，12 场景 × 2 轮真实模型。两轮 token 数字完全一致（温度 0 下 prompt 长度稳定），报告新增「成本」一节。事实源 `eval/results/arch-compare-20260904T015019Z.md`。

**修完之后推翻了本条自己的假设**

本条原文写的是「工具描述会进 prompt，成本上升多少」——预设工具调用更贵。实测相反：

| 架构 | 调用次数/请求 | token/请求 | 平均耗时 |
|---|---:|---:|---:|
| 固定链路 | 1.80 | 1304.5 | 2084ms |
| 工具调用 | 1.00 | 1187.2 | 1371ms |

工具调用每请求便宜 117 token（-9.0%）、快 713ms（-34%）。原因是固定链路每个请求要走**两次**模型（路由一次、抽取或规划再一次），两次调用的 prompt 累加超过了工具 schema 塞进单次 prompt 的开销。

这条推翻只在当前规模成立：3 个工具、schema 很短。工具数量增长后单次 prompt 会变长，交叉点会移动。**不能推广成「工具调用总是更省」。**

**出处**：`eval/run_architecture_compare.py`

## V5.0 · 稳定性与成本口径（2026-09-04）

### P-007 intent Runner 的退出码把 REVIEW 当失败，与四态纪律矛盾

**类型**：口径不一致 · 评测工具自身缺陷
**严重度**：中（不影响结论正确性，但让 CLAUDE.md 里的验证命令永远返回非零）

**现象**
四个 Runner 的退出码逻辑不一致：

```python
# run_tool / run_extract / run_query
return 0 if all(r["verdict"] in {"PASS", "REVIEW"} for r in all_results) else 1
# run_intent
return 0 if all(result["pass"] for result in all_results) else 1
```

`intent-dataset.jsonl` 里 `intent-rb-003`、`intent-rb-004` 是 observation tier，恒判 REVIEW，`pass` 为 False。因此 `run_intent_eval.py --views all --run-mode stub` **永远返回退出码 1**，即便 56 条全 PASS、0 条 FAIL。

**为什么是问题**
项目自己的四态纪律写的是「REVIEW = 规则尚未定义唯一 expected 的探索题，跑但不判分，不污染通过率」。退出码是给 CI 和自动化用的最终判定，把 REVIEW 计为失败等于在退出码这一层推翻了四态纪律。后果是这条验证命令的非零退出码变成噪音——真出现 FAIL 时反而分辨不出来。

**当前状态：已修（2026-09-04）**

主人启动 V5 关账后确认统一四态契约。`run_intent_eval.py` 新增 `exit_code_for_results()`，与另外三个 Runner 保持一致：`PASS / REVIEW` 返回 0，`FAIL / ERROR` 返回 1。

**验证方式**
```bash
.venv/bin/python eval/run_intent_eval.py --views all --run-mode stub --runs 2; echo "exit=$?"
# 修复后 exit=0，PASS 56 / FAIL 0 / REVIEW 2 / ERROR 0
```

新增 `test_exit_code_follows_four_state_contract` 5 组反证组合，分别覆盖纯 PASS、PASS+REVIEW、FAIL、ERROR 和混合失败。加上后续 P-008 用例后全量单测 `140 passed`，四套 Stub 回归全绿。

**溯源**：非本轮引入。`git show 9c0c534:eval/run_intent_eval.py` 显示 V4.0 关账版本即为此逻辑。

**出处**：`eval/run_intent_eval.py:exit_code_for_results`

### P-008 Tool Use 多轮评测重复使用 trace_id

**类型**：证据链缺陷
**严重度**：中（不影响业务判定，但跨轮无法精确定位单次 trial）

**现象**
`run_tool_eval.py` 原先使用 `t-{case_id}` 作为 trace_id。同一 Case 跑 3 轮时，报告三行指向同一个 ID，无法从持久化 Trace 中唯一区分轮次。

**怎么修的**
新增 `build_trace_id(case_id)`，在保留 Case ID 前缀的同时追加 UUID，保证每个 trial 唯一。

**怎么验证的**
`test_tool_eval_trace_id_is_unique_per_trial` 连续生成两次并断言 ID 不同；Tool Use Stub 两轮全绿；修复后重跑 Live 28 Case ×3 轮，84 条结果对应 84 个唯一 trace_id，业务结果仍为 84 PASS。

**出处**：`eval/run_tool_eval.py:build_trace_id`
