# V7 训练计划生成与可观测性迭代复盘

## 当前可观测能力盘点（2026-09-17）

当前定位：面向评测的本地链路可观测能力。可以从报告找到 Case，从 Case 找到过程证据，再核对问题、修复和复测；不是完整的线上监控平台。以下以训练计划链路为准，后续章节保留历史实验口径。

### 已经能查什么

| 排查问题 | 已有证据 | 使用边界 |
|---|---|---|
| 用户说了什么，系统怎么理解 | 原始输入、Planner 原始响应与解析出的肌群、难度、目标时长 | 解析合法不等于理解正确，需要对照 Case 预期 |
| 工具有没有调对 | 工具名称、实际参数、返回动作名称、数量及空结果原因 | 参数与预期比对，帮助区分理解错误与执行问题 |
| 生成模型实际拿到了什么 | `generate_request.payload.input` 保存拼装后的用户需求、解析结果、完整动作观察；Prompt 另有版本与 hash | 本次补齐的是 Generator 输入，不宣称所有链路都保存完整请求报文 |
| 模型到底输出了什么 | 模型原始响应、解析结果、最终计划 | 可以核对模型原文与解析后的结果，避免只看成功标志 |
| 问题出现在哪一步 | 同一 `trace_id` 关联事件；Viewer 展示执行异常和失败断言对应步骤 | 是定位线索，不是自动根因分析，也不等于能定位所有语义错误的最早起点 |
| Trace 自身是否完整 | 计划链路契约检查必需步骤顺序、字段存在性、部分字段值及 Trace ID 一致性 | 按子序列检查，允许额外事件；不代表所有日志内容都已验证 |
| 运行使用了什么版本 | 模型、Prompt 名称/版本/hash；计划报告保存数据集 hash、Git HEAD、dirty 状态、源码快照/hash | 未提交实现不能只靠 HEAD 复现；应保留运行快照 |
| 模型调用花了多少 | 模型调用耗时与 Token，评测报告汇总 | 不是完整的服务性能监控，也不是每个节点都有起止 Span |

计划链路的 Trace 契约、Viewer 和失败关联最完善，其他链路已有日志及各自评测检查，不宣称覆盖程度完全相同。

### 怎么使用

1. 从计划报告找到失败 Case、失败断言与 `trace_id`。
2. 用 Viewer 按执行顺序核对输入、解析、工具调用、观察和生成结果。
3. 对照 Case 预期及对应 Prompt 版本判断问题所在；修复后用同口径 Case 复测，分别保留新旧批次。

查看本次 `pl-004` 的命令：

```bash
/Users/wei/my/fit-agent/.venv/bin/python /Users/wei/my/fit-agent/eval/trace_view.py p-pl-004-361e1ab9-01bf-402e-ad5c-497035b3fd5d
```

也可传入 `--last` 查看最近一条 Trace。原始事件位于 `backend/logs/trace.jsonl`，自动报告、逐 Case 结果及源码快照位于 `eval/results/`；这些运行产物被 Git 忽略，需本地保留。Viewer 是终端文本工具，不是 Web 界面。

### 已经带来的实际价值

`pl-004` 的历史问题可以沿证据还原：用户要 40 分钟 → 工具只返回一个动作 → 生成模型收到该动作 → v2 声称“已补足 40 分钟” → 原断言只比较声明数字，因此漏检。

这让修复落在具体的生成规则与评测口径上，而不是笼统归因“模型不好”。当前 v3 保留目标时长、预计时长为 null，并说明无法保证满足目标；这修正了无依据的声明，没有实现时长估算。前后响应、测试结果与证据见 [时长一致性实施记录](../../docs/训练计划时长一致性-需求与评测场景初稿.md)。

### 尚未具备，暂不扩建

- 没有 Langfuse 依赖、父子 Span 树、跨服务追踪、在线告警或多用户检索界面。
- Trace 不自动证明业务正确；说明是否过度承诺仍需独立语义复核。Stub 验证检测器，Live 观察模型行为，单轮 Live 不证明稳定性。
- 暂不整批补齐 Observation 字段或建设平台。先用真实 Bad Case 走通“报告 → Trace → 原始输入输出 → 修复 → 复测”，出现具体排查缺口再补。

## 1. 为什么做

前四条链路（意图 / 抽取 / 查询 / 工具调用）都是**闭式任务**：输出空间有限，判分靠比对，黑盒校验基本够用。训练计划生成是第一条**开放式生成**链路，也是 L1 与 L2 的分界线——模型拿到工具返回后还要继续产出内容。

这一变化带来一个新的失败模式，前四条链路都没遇到过：

> 模型理解错了用户意图，但下游每一步都执行得很正确，最终输出**完全合法**。

「练腿」被听成「练胸」，模型就带着 `muscle=胸` 去查动作库，拿到的是货真价实的胸部动作，编排出的计划条条合规、时长合规、字段齐全。**所有只看输出的校验都会给它全绿。**

本轮只回答一个问题：

> 只看最终输出，能不能发现「理解错」？

## 2. 实现内容

- `backend/action_lib.py`：静态动作库（5 肌群 × 3 难度）+ 只读查询工具 `query_action_lib`；
- `backend/plan.py`：三段链路 `parse_need` → `call_action_tool` → `parse_workout`，全部 trace-first；
- `eval/trace_contract.py`：声明式契约，按**子序列**匹配（多记事件不算违约，声明里的一步都不能少）；
- `eval/trace_view.py`：给定 `trace_id` 还原因果链，含工具入参和最早失败步骤；
- `eval/run_plan_eval.py`：黑盒 4 条 + 白盒 5 条断言，核心指标 `blackbox_blind_spots`；
- `eval/datasets/plan-dataset.jsonl`：10 条 case，含 2 条陷阱 case 和 2 条 regression；
- `backend/prompts/workout_planner_v1.txt`、`workout_generator_v2.txt`：两个 Prompt 登记进 manifest。

**两处刻意的设计**：

1. **工具入参是一等断言对象**。白盒断言直接读 `tool_call.arguments`，不读工具实现、不读最终计划——错误在模型给出入参那一刻就已经确定，后面的正确执行只是把这个错误忠实地放大。
2. **两类错误必须可分**。「理解错」（肌群 / 难度听错）和「表达错」（JSON 字段非法）不能在同一个地方拦。`parse_need` 故意不校验「难度与水平是否匹配」——那一层只判表达合法，语义对错留给工具入参那一层。合并了，就再也说不清是模型没听懂还是输出格式坏了。

## 3. 实现中发现的问题

### 3.1 陷阱 case 在 live 下不会红，只在 stub 下红

pl-201（「给我一个 30 分钟练腿的计划，新手」，剧本改成 `muscle=胸`）在 live 下连续通过：真实模型解析正确，走的是 `muscle=下肢`，计划是徒手深蹲。

这不是断言失效，是**证据归属**问题：陷阱 case 用来证明「白盒断言在该红的时候确实会红」，它需要一个确定会犯错的被测对象。真实模型是否犯错不由我们控制，所以这个证明只能由 stub 提供——`stub_need` 按剧本演「理解错」，白盒必须红。

**结论**：白盒断言的有效性证据来自 stub；真实模型的解析能力证据来自 live。两者不能互相顶替，报告里必须分清。

### 3.2 黑盒 4 条 + 白盒 4 条，全绿，但链路里有一条真实缺陷

v1 生成器在 pl-004（背 / 中高，动作库该格子只有 1 条动作）上把同一条动作抄了 4 行：

```
单臂哑铃划船, 单臂哑铃划船, 单臂哑铃划船, 单臂哑铃划船
```

8 条断言一条都没红：动作名条条来自观察库、时长合规、字段齐全。**当时的断言集对「复制条目充数」完全盲。**

### 3.3 断言漏了，Prompt 也在鼓励这个行为

回溯 v1 Prompt 规则 4：

> 4. 动作数量按总时长铺：10 分钟给 2 个动作，30 分钟给 3 到 4 个，
>    40 分钟以上给 4 到 5 个。动作不够时，**宁可重复同一个动作的多组**，也不要引入库外动作。

一句「宁可重复同一个动作的多组」把违规写法写成了许可写法，而且写在了「不要引入库外动作」这个正当约束的同一句里——模型读到的是「重复是被鼓励的保守选择」。而动作库的设计是「一个格子一条动作」，这条规则等于在每个非空格子上都打开了复制开关。

**两处都要修**：断言侧补上「计划条数不得超过观察条数」，Prompt 侧改成「靠加大 sets 填时长，同一份计划里动作不允许重复」。

### 4.1 核心实证：黑盒全绿，白盒抓出「理解错」

stub 演 pl-201（脚本把「练腿」改成「练胸」），trace 里的因果链：

```text
[planner] request       {"text": "给我一个 30 分钟练腿的计划，新手"}
[planner] plan_response {"raw_text": "{\"muscle\": \"胸\", ...}"}
* [tool]  tool_call     {"tool": "query_action_lib", "arguments": {"muscle": "胸", "difficulty": "简单"}}
[tool]    tool_result   {"count": 1, "names": ["跪姿俯卧撑"], "reason": "ok"}
```

- **黑盒 4/4 全绿**：动作来自动作库、时长合规、字段齐全、计划该有就有；
- **白盒 4/5**：`tool_args_match_intent` 红，报出「期望 下肢/简单，实际 胸/简单」；
- 另有一条 pl-202 演「难度听错」（进阶被听成简单），白盒红 2 条（`tool_args_match_intent` + `need_difficulty_matches_level`）。

错误在 `tool_call` 那一行就已经确定，后面的 `跪姿俯卧撑` 只是把这个错误忠实地执行完。**这就是「只看输出」看不见的那一层。**

pl-001（不演戏的正常 case）黑盒白盒全绿，用来证明白盒断言不是「永远红」。

### 4.2 复制条目缺陷的前后对照

| 阶段 | 生成器版本 | Case 级 | 断言级 | `blackbox_blind_spots` |
|---|---|---:|---:|---|
| 补断言前 | v1 | 1.0000（7/0） | 1.0000（**77 / 77**） | **0 条** ← 断言集是瞎的 |
| 补断言后 | v1 | 0.8571（6/1） | 0.9881（83 / 84） | **1 条 -- pl-004** |
| 修 Prompt 后 | v2 | 1.0000（7/0） | 1.0000（**84 / 84**） | **0 条** ← 缺陷已消失 |

中间那一行是关键：**同一条 case、同一份计划，只因为加了一条断言，从 4/4 全绿变成 FAIL。** 断言 `plan_size_within_observation` 报出「观察 1 条，计划 4 条」。

模型在 v1 下自己写出的 note 直接复述了 Prompt 规则 4：

> 「动作库仅返回单臂哑铃划船一个动作，**为满足 40 分钟训练量，重复该动作多组编排**。」

v2 下的 note 换成了正确做法：

> 「动作库仅返回 1 个匹配动作，已通过**增加组数**将总时长填充至约 40 分钟。」

两段 note 是这次归因最硬的证据：不是模型随机发挥，是它照着 Prompt 写了被许可的那种「凑数」。计划内容从 `×4 条` 变成 `1 条 sets=4`，断言随之转绿。

## 6. 可迁移结论

1. **工具入参是白盒的第一落点**。链路中间的产物里，工具入参的信息密度最高——它同时是「模型理解的结论」和「下游全部行为的输入」。断言它，等于在错误扩散前设卡。
2. **黑盒全绿是一个必须被解释的现象，不是一个结论**。全绿要么因为没有缺陷，要么因为断言集是瞎的。区分这两者的唯一办法，是**造一条确定会犯错的 case，看断言红不红**。
3. **断言的红必须可归因到单一断言**。用 `failed == [...]` 而不是 `in`，是为了让「新断言真的抓到了」这件事无法被别的断言的噪音掩盖。
4. **同一条缺陷可能同时写在断言和 Prompt 里**。v1 的规则 4 把违规写法写成许可写法——这类缺陷靠加断言只能拦住症状，Prompt 不改就会换个形状再来。
5. **可在 AVIS 复用的最小集**：声明式 trace 契约（子序列匹配）+ 给定 `trace_id` 的链路还原 + 工具入参断言 + 「造错 case 验证断言会红」的反证纪律。这四件不依赖具体业务，也不依赖被测系统是否开源。
