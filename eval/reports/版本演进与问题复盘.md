## V1.0 — 意图识别闭环建立

**Git**：`1a61947`（2026-07-19 关账）

### 做了什么

一句自然语言 → `record / query / reject` 三分类。函数级 Router，无 HTTP、无下游业务。

```
输入 → ①入参防御 → ②调 LLM → ③严格 JSON 解析 → 统一判别结构
```

四个文件 248 行：`router.py`（决策）、`llm.py`（模型入口 + 测试替身）、`trace.py`（结构化日志）、`intent_router_v1.txt`（Prompt 单独成文件，可算哈希）。

配套评测：37 条分层数据集（34 分类 + 3 故障注入）、三视图（discovery / regression / locked）、评测 Runner、混淆矩阵与 macro-F1。

### 怎么测的

```bash
pytest -q                                              # 确定性单测
run_intent_eval.py --views all --run-mode stub         # 契约回归，零 token
run_intent_eval.py --views locked --run-mode live --runs 3   # 真实模型验收
```

### 结果

| 验证 | 结果 |
|---|---|
| 单元测试 | 24 passed |
| Stub 全量 | 37/37 |
| Live discovery ×3 | 30/30 |
| Live regression ×3 | 24/24 |
| Live locked ×3 | 48/48，macro-F1 1.0000 |

**当时的结论：全绿，迭代关账。**

### 当时已知的限制

- locked 在调优期被看过失败结果，不是独立盲测集，不宣称真实准确率 100%
- 全部合成数据，中文单轮短句

## V1.1 — 用断言方法论回扫，发现「全绿」是假绿

**触发**：先沉淀了 [断言方法论](../methodology/断言方法论.md)（四问 + 来源分类 + 四态 + 三级漏斗），然后拿这套东西回头扫 V1.0 自己的评测层。

**核心发现：V1.0 报告上的 37/37 全过是真的，但其中有一条断言根本不可能失败。**

### 怎么发现的

对着四问逐条比对 V1.0 的评测代码，问「这一问断了没有」：

| 四问 | V1.0 实际 |
|---|---|
| 一、系统承诺了什么 | **完全没断**——结构、错误码枚举、字段泄漏一条都没有 |
| 二、该发生的发生了吗 | 断了：`intent == expected` |
| 三、不该发生的没发生吗 | **断了一半**：有文件写入快照，但防御路径的断言是失效的 |
| 四、说的和做的一致吗 | 没断 |

第一问一比对就露馅了——评测从头到尾只取了 `actual["intent"]`，响应长什么样根本没人管。

### 问题 1：防御路径的断言是死的

**现象**：trace 事件比对用的是「包含」：

```python
expected_trace_events(actual).issubset(event_names)   # 旧
```

**为什么是问题**：`bad_request` 期望的事件是 `{input_received, result}`。如果程序有 bug、先调了模型才返回拒绝，实际事件变成 `{input_received, llm_request, result}`——**「包含」依然成立，判 PASS**。

这条断言的全部意义就是证明「防御时没调模型、没花钱」，而它恰恰证明不了。更讽刺的是单测里用的是精确比对（`==`），**评测层比单测松**。

**怎么改**：改成精确集合比对，多一个事件也算失败。

```python
expected_trace_events(actual) == event_names           # 新
```

**怎么验证**：加单测 `test_defense_path_rejects_extra_llm_call`，把旧写法的漏洞也写进断言留档——证明 `issubset(sneaky)` 为真、`== sneaky` 为假。

### 问题 2：`bad_request` 整条路径没进评测集

**现象**：37 条数据里没有一条防御类 Case。空输入、超长输入只在单测里覆盖。

**为什么是问题**：单测保证「代码没写错」，评测保证「行为没变坏」，两本账。防御是对外契约的一部分，只活在单测里意味着它不进任何一轮回归报告，也不会出现在给别人看的结果里。

**怎么改**：数据集加 3 条（空串、纯空白、501 字符），37 → **40 条**。这类 Case 不调模型，live 模式跑也不花钱。

**顺带发现**：stub 的剧本生成假设每条 Case 都有 `expected_intent`，防御 Case 一进来直接 `KeyError` 崩了。修成只在有 `expected_intent` 时生成剧本——防御 Case 剧本留空，**一旦真被调用就会落 parse_error 暴露出来**，比静默通过好。

### 问题 3：响应契约完全没断

**现象**：评测只看 `intent` 对不对，响应本身长什么样从来没人检查。

**为什么是问题**：意味着这些都能悄悄溜过——失败响应里还带着 `intent`（业务字段泄漏）、返回一个没定义过的 `error_code`、`confidence` 越界、多返回一个调试字段。

**怎么改**：新增 `assert_contract()`，覆盖第一问：

- 成功响应字段集合**精确**等于 `{ok, trace_id, intent, confidence, source}`
- 失败响应精确等于 `{ok, trace_id, error_code}`，且**不含 intent**
- `error_code` 必须在四个枚举内
- `confidence` 是 0~1 数字（排除 bool）
- `source` 恒为 `llm`

每条 Case 现在报三层结果：`semantic_pass`（分类）、`contract_pass`（契约）、`trace_pass`（痕迹），失败时列出具体挂在哪条契约上——对应方法论的**层序即归因序**。

**怎么验证**：5 个新单测分别构造泄漏 intent、未定义错误码、越界 confidence、多余字段的响应，断言它们**必须失败**。新断言不能是死的。

### V1.1 结果

| 验证 | V1.0 | V1.1 |
|---|---|---|
| 单元测试 | 24 passed | **30 passed** |
| Stub 全量 | 37/37 | **40/40** |
| 每条 Case 的断言层数 | 2 层 | **3 层** |

### 这一版真正学到的

> **测试通过 ≠ 测试有效。**

V1.0 的 37/37 是真实运行结果，没有造假；但其中一条断言在任何情况下都不会失败。一个永远为真的断言，和没有这条断言，信息量完全相同。

推论：**评测代码本身也需要被验证**。做法就是给每条新断言配一个「它应该失败」的用例——如果构造不出让它失败的场景，这条断言大概率是死的。

### 遗留

- 数据集 37 → 40，`README.md` 与外部文章中的条数表述需同步
- V1.1 改动尚未 commit

## V1.2 — 补齐结果口径：一致性、四态、双口径

**Git tag**：`v1.2`

延续 V1.1 的思路，继续按断言方法论补没做的部分。这一轮不是「发现 bug 再改」，而是**照着方法论把欠的补齐**。

### 做了什么

**1. 第四问 · 一致性断言**

新增 `assert_trace_consistency()`：执行痕迹里记录的结论，必须和返回值吻合。

- `result` 事件的 `ok` 与返回值一致
- 成功时 `intent` 一致，且 `parse_result` 里的 intent 也要对得上
- 失败时 `error_code` 一致

这一层防的是「日志说做了 A，实际返回 B」——排查时最误导人的情况。

**2. 四态 Verdict：把环境异常从业务失败里摘出来**

这一步做的时候撞上一个真实的设计问题：**`llm_timeout` 到底算什么？**

答案不唯一，取决于是不是预期内：

| 情况 | 判定 | 理由 |
|---|---|---|
| 故障注入 Case 期望超时，拿到超时 | **PASS** | 预期内，正是要测的 |
| 分类 Case 跑 live 撞上超时 | **ERROR** | 网络问题，不代表模型分错 |
| `llm_parse_error` | **FAIL** | 真实的 prompt / 模型问题，必须计入 |
| trace 写盘失败 | **ERROR** | 评测程序自身故障 |

连带一个改动：**ERROR 的 Case 不进混淆矩阵**。以前一条 record Case 因为超时失败，会被算成 record 的 false negative——等于把网络抖动记成了模型分类错误，指标失真。

**3. 双口径报告**

```
【核心结果】Case 级 1.0000（PASS 40 / FAIL 0）
【断言明细】断言级 1.0000（388 / 388）
【待复核】REVIEW 0
【执行异常】ERROR 0（不计入通过率）
```

Case 级给产品看影响面，断言级给开发估工作量。Badcase 表也加了 `verdict` 和**失败断言名**两列，挂了直接看出破的是哪条契约。

### 过程中的一个印证

改报告结构时，旧单测立刻失败了——因为它断言了报告里必须出现的字段。**这正是 V1.1 学到的那条在起作用**：断言要能失败才有意义。顺手给新加的四态和一致性断言也各配了「它应该失败」的用例。

### 结果

| 验证 | V1.1 | V1.2 |
|---|---|---|
| 单元测试 | 30 passed | **36 passed** |
| Stub 全量 | 40/40 | 40/40（**388 条断言**） |
| 结果状态 | 二态 | **四态** |
| 报告口径 | 单一数字 | **双口径 + 异常分账** |

### 这一版的判断

REVIEW 这一态目前恒为 0，因为意图分类是确定性任务，代码断言能覆盖全部判定。**LLM 裁判这一层在本项目暂不启用**，等出现自由文本输出（如知识问答意图）再说——留好结构，不提前启用。

## V1.3 — 数据集侧：来源、判定方式与鲁棒集

### 做了什么

**1. 每条 Case 补 `source`**——映射到 PRD 决策表的具体规则，如 `prd-iter1-intent#3.4-rule-3`。规则变化时知道该找谁确认、哪些 Case 要跟着改。

**2. 每条 Case 补 `assertion`，并让 Runner 真的按它判**

关键不是加字段，是把判定方式从代码搬到数据：

```python
ASSERTIONS = {"intent_equals": ..., "error_code_equals": ...}
assertion_pass = run_assertion(case, actual)
```

以前是代码里 `if "expected_error_code" in case` 隐式推断，换个执行器判定逻辑就丢了。同时加了加载期门禁：缺 `assertion` / `source`、或声明未知断言类型，直接报错退出。

**3. 两批更难的数据**：先补 8 条对抗样本（中英混合、错别字、超长噪声夹事实、JSON/Markdown 片段、咨询句塞满强关键词），再补 10 条鲁棒集（时态矛盾、复合意图、否定套否定、强关键词误导、训练对象边界）。数据集 40 → **58 条**。

### 结果：没打穿，但这不等于没收获

真实模型三轮跑下来：**29 PASS / 0 FAIL / 2 REVIEW，三轮完全一致。**

18 条新造的难题，除 2 条无法判分的之外，全部分对。**这不是「模型很强」的证据，是「题不够狠」的证据**——按 Anthropic 的说法这叫**评测饱和**：能力集全过就只剩回归信号，没有改进信号了。

### 唯一的真发现：复合意图没有稳定策略

两条句式几乎对称的复合句，模型给了相反的答案，三轮稳定复现：

| 输入 | 模型判定 |
|---|---|
| 「今天练了胸，**上次练胸是什么时候**」 | `query` |
| 「记一下今天跑了5公里，**顺便看看这周跑了几次**」 | `record` |

都是「先陈述已发生训练 + 再问历史记录」，模型一个取后半句、一个取前半句——**它没有稳定策略，是在猜**。

**但这不算模型缺陷**：PRD 规则 10 明确写了「单轮多意图不覆盖」，产品从没定义过该走哪条链路。责任在规则缺失，不在模型。

所以这两条标记为 `tier: observation`，判定为 **REVIEW**——跑、观察、留证据，但不判分、不进通过率。如果按普通 Case 硬判，会得到一个假的 FAIL，然后有人跑去改 prompt 迁就一条根本不存在的规则。

**副产品**：REVIEW 这一态在 V1.2 引入后一直恒为 0，这轮由真实需求驱动才用上。留结构、不提前启用，是对的。

### 为什么这个练习项目打不穿，真实项目会

这一点必须说清楚，否则容易把「我的评测没发现问题」误读成「我的系统质量高」。

**三个意图打不穿的原因：**

1. **意图空间太窄**——只有 `record / query / reject` 三类，语义距离远，不容易互相挤压
2. **边界被规则定死了**——PRD §3.0 那条「已发生 + 至少一个训练对象」把 record/reject 的分界写得极硬，模型照着规则走就不容易错
3. **单轮、无上下文**——没有历史状态、没有指代、没有账号信息干扰，输入分布干净
4. **句子是我自己造的**——合成数据天然落在我能想到的范围内，而模型也见过类似分布

**真实项目十几个意图时，会在这些地方裂开：**

- **相邻意图互相挤压**：意图一多，语义距离迅速缩短。「调整计划」和「重新生成计划」、「查询记录」和「查询计划」，人都要想一下，模型更容易滑过去
- **每对相邻意图都是一条边界**：3 个意图只有 3 对组合，15 个意图有 105 对——**边界数量按平方增长，而 Case 数量通常只按线性增长**，覆盖密度必然下降
- **上下文干扰**：多轮里的省略和指代（「那就改成周三吧」）本身不含意图关键词，全靠上下文，这是错分重灾区
- **真实表达比合成数据脏得多**：口语、错别字、多语言、一句话混三件事，分布远比 PRD 造出来的宽
- **意图之外还有闸门**：版本、灰度、白名单——意图分对了入口仍可能不通，失败会以「意图错」的表象呈现，归因难度高一个量级

**方法完全一样，只是难度不同。** 本项目验证的是流程能跑通：规则表 → 等价类 → 分层数据 → 分层断言 → 四态 → 回流。意图变成十几个时，要加的不是新方法，而是**更密的边界覆盖**和**更严的归因分层**。

### 结果

| 验证 | V1.2 | V1.3 |
|---|---|---|
| 数据集 | 40 条 | **58 条** |
| 单元测试 | 36 passed | 36 passed |
| Stub 全量 | 40/40 | **58/58** |
| Live discovery ×3 | — | **29 PASS / 0 FAIL / 2 REVIEW，三轮一致** |
| 数据 schema | 无来源、无判定声明 | **每条带 `source` + `assertion`** |

### 遗留

- 复合意图两条留在 `observation`，作为已知限制，**不回改 PRD**——规则该由产品定，测试不代劳
- 未继续加码造题：**不为了找 bug 而造 bug**，硬凑到打穿会造出真实用户不会说的句子，修了没价值还会把 prompt 带偏

## V2.0 — 迭代二：抽取与受控写入

**PRD**：[iter-2 专项 PRD](../../docs/prd-iter2-extract.md)

### 做了什么

本项目第一次产生**副作用**——真的往文件里写数据。

```
text → Router(iter-1) → intent=record → Extractor → 三态判定 → 受控写入 → 回执
```

新增四个文件：`storage.py`（Protocol + JsonlStorage + FakeStorage）、`extractor.py`（严格解析 + 三态）、`pipeline.py`（三层编排）、`extractor_v1.txt`（抽取 Prompt）。

**三态判定**：有动作 + 至少一个量化字段 = `complete`；有动作无量化 = `incomplete`；抽不出动作 = `invalid`。有氧的量化是时长或距离，不要求重量组数。

**写入规则**：`complete` 与 `incomplete` 都写并标记 `state`，`invalid` 不写；一句多动作拆成多条；每条记录带 `trace_id`，便于从脏数据反查调用。

### 关键设计：为什么抽取比意图识别更危险

意图判错，用户重说一遍即可；**抽取判错会往用户的训练记录里写一条假数据**，他明天翻记录看到自己卧推了 600kg，而且不会有人报 bug。

所以断言重心从「判得准不准」转向「**该不该写、写了几条**」，两条硬门禁写进退出标准：

- `invalid` / 被上游拦下的输入 → **零写入**
- 写入条数**精确匹配**，多写少写都算失败

### 本轮发现的两个问题，都在评测代码自己身上

**问题 1：评测集设计错了——用例根本走不到被测节点**

我造了「今天练得挺爽」「状态不错」当 `invalid` 用例，想测 extractor 的兜底。首轮 live 跑出 2 条 FAIL。

查下来：这些输入在完整链路里**压根到不了 extractor**——iter-1 的 Router 先判成 `reject` 拦掉了，返回里自然没有 `state` 字段。

**这不是缺陷，恰恰证明 iter-1 工作正常。** `invalid` 是 extractor 的防御性状态，该在单测层面测（已覆盖），不该拿自然语言在完整链路里测。

改法：这类 Case 的正确预期是「**Router 拦截 + 零写入**」，测的是两层协作而非单层兜底。

> **教训**：多节点链路里，写用例前要先确认「这条输入到底会走到哪一层」。用例走不到被测节点，测的就不是你以为的东西。

**问题 2：断言套错了形状**

改完预期后仍有 3 条 FAIL。原因是 `assert_contract` 仍拿抽取层的契约（`state` 枚举、`records` 数组）去校验被 Router 拦下的响应——那种响应根本没有这些字段，于是永远 FAIL。

**同一条链路的不同出口，响应形状不同，契约断言必须分支处理。**

顺带第三个：stub 剧本原本一律强制 Router 返回 `record`，期望被拦下的 Case 自然走不到拦截路径。**剧本要跟着 Case 的预期走。**

### 结果

三视图各连跑 3 轮，全部通过：

| 验证 | 结果 |
|---|---|
| 单元测试 | **61 passed**（36 + 25 新） |
| Stub 全量 | **28/28**，断言级 1.0000 |
| Live discovery ×3 | 21/21，断言级 1.0000 |
| Live regression ×3 | 2/2 |
| Live locked ×3 | 5/5 |
| **invalid 写入违规** | **0**（三视图三轮全部） |
| **写入条数错误** | **0**（三视图三轮全部） |

三态混淆矩阵对角线干净：`complete → complete` 15、`incomplete → incomplete` 4、`router_rejected → router_rejected` 2。

真实模型的抽取表现（三轮稳定）：

- 「明天练腿，今天刚游了40分钟」→ 只抽游泳，未来计划没混进来
- 「练了3年的卧推，今天做了5组」→ `sets=5`，「3年」没被误当组数
- 「体重70kg，今天卧推做了4组」→ 没把体重当训练重量
- 「硬拉100kg三组，然后划船做了四组」→ 拆两条，各自带字段

PRD 六条退出标准全部满足。

### 遗留与已知限制

按 PRD §5.2 明确不做，**不是遗漏**：不做幂等去重（同一句说两次写两条）、不做事务、不做删改、不引入数据库。企业里这四条都必须做且是测试重点，差异见 [存储选型与企业实践差异](../../docs/存储选型与企业实践差异.md)。

一个 PRD 未覆盖、实现时定的边界：**一句话里混合完整度**（一条 complete 一条 incomplete）时，每条记录各自带 `state` 落盘，整体状态取最保守的（报 `incomplete`）。

## V3.0 — 迭代三：查询与端到端

**PRD**：[iter-3 专项 PRD](../../docs/prd-iter3-query.md)

### 做了什么

数据能写进去了，但读不出来。这一轮补上查询，并让整条链路第一次能通过 HTTP 跑通。

```
一句话 → Router → ┬─ record → Extractor → 三态 → 写入
                  └─ query  → Planner(LLM) → Executor(纯代码) → 结果
```

新增：`clock.py`（时间注入）、`query.py`（Planner + Executor）、`app.py`（`POST /api/chat`）、查询 Prompt、22 条查询评测集与 Runner。

### 三个关键设计

**1. 把 LLM 和执行切开**

`QueryPlanner` 用 LLM 把自然语言翻译成结构化条件，`QueryExecutor` 用纯代码执行。

这样查错了能立刻分清是**没听懂用户**（改 Prompt）还是**查错了数据**（改代码）——责任完全不同。而且执行那半完全确定，可以用普通单测覆盖，不花 token。

**2. 时间必须可注入**

查询是本项目第一次遇到「答案会随时间变化」的场景。用例写「今天练了什么」，今天跑对了明天就错——**用例会自己烂掉**。

于是加了第三个统一入口，与前两个同样的形状：

```
LLMClient  →  LiveLLM      / StubLLM
Storage    →  JsonlStorage / FakeStorage
Clock      →  SystemClock  / FrozenClock     ← 本轮新增
```

每条 Case 自带 `now` 字段注入给 `FrozenClock`，所以「今天」永远是同一天，**明年跑还是同一个答案**。这条口子是 V1.2 时就写进架构约束的，到这一轮才真正用上。

**3. 口径先定死，再写代码**

「这周」从周一算还是往前推七天？「今天」跨不跨零点？查无结果算不算错误？这些不是技术问题，是**产品口径**——不定死，用例写不出唯一 expected。PRD §3 定了八条，其中「这周 = 周一起算」「查无结果返回空数组而非错误」是最容易分歧的两条。

### 本轮发现的问题

**日期格式漏洞（单测抓到，真 bug）**

`_is_date` 最初直接用 `datetime.strptime(value, "%Y-%m-%d")` 校验，测试用例给了 `2026-9-3`——**Python 的 strptime 接受非零填充**，于是这个格式通过了校验。

而范围过滤用的是**字符串比较**（`from <= date <= to`），非零填充的日期比较结果是错的：`"2026-9-3" > "2026-10-01"` 为真。模型只要哪次返回了非零填充日期，查询范围就会静默出错，而且**不会报错、不会崩，只是结果不对**。

修法：严格要求长度为 10 且分隔符位置固定。

> 这类 bug 的特征是**静默失真**——没有异常、没有崩溃，只有数字悄悄错了。**只有先写了「它应该失败」的用例才抓得到。**

**Self-review 发现的两处**

1. `data/` 没进 `.gitignore`——`JsonlStorage` 默认写 `data/records.jsonl`，那是用户数据，一旦有人跑起服务就会被提交进版本库
2. `app.py` 每个请求都新建 `LiveLLM()`，等于每次重建连接池；改为首次请求创建后复用

### 时间边界用例（本轮最有价值的一组）

这些用例**只有靠冻结时间才写得出来**：

| 场景 | 断言 |
|---|---|
| 记录在今天 00:00:00 | 属于今天（下边界含） |
| 记录在昨天 23:59:59 | 不属于今天（差一秒就排除） |
| 记录以 UTC 存储、本地已跨天 | 按本地时区归日，不错位 |
| 星期一问「这周」 | 只返回当天，不是往前七天 |

### 遗留与已知限制

- 动作名**精确匹配**，「卧推」查不到「杠铃卧推」——需要动作词典，属另一量级问题
- 只支持两类查询，部位聚合、趋势分析返回 `unsupported`
- HTTP 只有一个路由 + 异常兜底，**无鉴权、限流、并发、多用户**——本迭代验证的是链路能通，不是做可上线服务

## 历史待办（V1.3 已完成，保留原文备查）

### 原 V1.3 计划：数据集侧

代码侧按方法论已补齐，这一轮转向数据。

1. **补 `source` 字段**——每条 Case 标明来源（PRD 哪条规则 / 哪个历史 Bug），规则变化时知道找谁确认
2. **补 `assertion` 字段**——断言目前隐含在 Runner 代码里，数据本身不声明判定方式，换执行器就丢
3. **补对抗桶输入变体**——目前只覆盖提示注入，缺中英混合、错别字、超长噪声、非文本格式片段

前两件提升可维护性，第三件**最可能真发现新问题**。

**明确不做**：blind holdout。测试集在实际工作中常直接交给开发照着改，此时它是规格说明书而非统计工具，「被看过」不是污染。只有要对外宣称准确率数字时才需要盲测集——日常迭代不为它停工。
