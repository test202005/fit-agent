## V1.0 — 意图识别闭环建立

**Git**：`1a61947`（2026-07-19 关账）

### 做了什么

一句自然语言 → `record / query / reject` 三分类。函数级 Router，无 HTTP、无下游业务。

```
输入 → ①入参防御 → ②调 LLM → ③严格 JSON 解析 → 统一判别结构
```

四个文件 248 行：`router.py`（决策）、`llm.py`（模型入口 + 测试替身）、`trace.py`（结构化日志）、`intent_router_v1.txt`（Prompt 单独成文件，可算哈希）。

配套评测：37 条分层数据集（34 分类 + 3 故障注入）、三视图（discovery / regression / locked）、评测 Runner、混淆矩阵与 macro-F1。

### 怎么测的

```bash
pytest -q                                              # 确定性单测
run_intent_eval.py --views all --run-mode stub         # 契约回归，零 token
run_intent_eval.py --views locked --run-mode live --runs 3   # 真实模型验收
```

### 结果

| 验证 | 结果 |
|---|---|
| 单元测试 | 24 passed |
| Stub 全量 | 37/37 |
| Live discovery ×3 | 30/30 |
| Live regression ×3 | 24/24 |
| Live locked ×3 | 48/48，macro-F1 1.0000 |

**当时的结论：全绿，迭代关账。**

### 当时已知的限制

- locked 在调优期被看过失败结果，不是独立盲测集，不宣称真实准确率 100%
- 全部合成数据，中文单轮短句

## V1.1 — 用断言方法论回扫，发现「全绿」是假绿

**触发**：先沉淀了 [断言方法论](../methodology/断言方法论.md)（四问 + 来源分类 + 四态 + 三级漏斗），然后拿这套东西回头扫 V1.0 自己的评测层。

**核心发现：V1.0 报告上的 37/37 全过是真的，但其中有一条断言根本不可能失败。**

### 怎么发现的

对着四问逐条比对 V1.0 的评测代码，问「这一问断了没有」：

| 四问 | V1.0 实际 |
|---|---|
| 一、系统承诺了什么 | **完全没断**——结构、错误码枚举、字段泄漏一条都没有 |
| 二、该发生的发生了吗 | 断了：`intent == expected` |
| 三、不该发生的没发生吗 | **断了一半**：有文件写入快照，但防御路径的断言是失效的 |
| 四、说的和做的一致吗 | 没断 |

第一问一比对就露馅了——评测从头到尾只取了 `actual["intent"]`，响应长什么样根本没人管。

### 问题 1：防御路径的断言是死的

**现象**：trace 事件比对用的是「包含」：

```python
expected_trace_events(actual).issubset(event_names)   # 旧
```

**为什么是问题**：`bad_request` 期望的事件是 `{input_received, result}`。如果程序有 bug、先调了模型才返回拒绝，实际事件变成 `{input_received, llm_request, result}`——**「包含」依然成立，判 PASS**。

这条断言的全部意义就是证明「防御时没调模型、没花钱」，而它恰恰证明不了。更讽刺的是单测里用的是精确比对（`==`），**评测层比单测松**。

**怎么改**：改成精确集合比对，多一个事件也算失败。

```python
expected_trace_events(actual) == event_names           # 新
```

**怎么验证**：加单测 `test_defense_path_rejects_extra_llm_call`，把旧写法的漏洞也写进断言留档——证明 `issubset(sneaky)` 为真、`== sneaky` 为假。

### 问题 2：`bad_request` 整条路径没进评测集

**现象**：37 条数据里没有一条防御类 Case。空输入、超长输入只在单测里覆盖。

**为什么是问题**：单测保证「代码没写错」，评测保证「行为没变坏」，两本账。防御是对外契约的一部分，只活在单测里意味着它不进任何一轮回归报告，也不会出现在给别人看的结果里。

**怎么改**：数据集加 3 条（空串、纯空白、501 字符），37 → **40 条**。这类 Case 不调模型，live 模式跑也不花钱。

**顺带发现**：stub 的剧本生成假设每条 Case 都有 `expected_intent`，防御 Case 一进来直接 `KeyError` 崩了。修成只在有 `expected_intent` 时生成剧本——防御 Case 剧本留空，**一旦真被调用就会落 parse_error 暴露出来**，比静默通过好。

### 问题 3：响应契约完全没断

**现象**：评测只看 `intent` 对不对，响应本身长什么样从来没人检查。

**为什么是问题**：意味着这些都能悄悄溜过——失败响应里还带着 `intent`（业务字段泄漏）、返回一个没定义过的 `error_code`、`confidence` 越界、多返回一个调试字段。

**怎么改**：新增 `assert_contract()`，覆盖第一问：

- 成功响应字段集合**精确**等于 `{ok, trace_id, intent, confidence, source}`
- 失败响应精确等于 `{ok, trace_id, error_code}`，且**不含 intent**
- `error_code` 必须在四个枚举内
- `confidence` 是 0~1 数字（排除 bool）
- `source` 恒为 `llm`

每条 Case 现在报三层结果：`semantic_pass`（分类）、`contract_pass`（契约）、`trace_pass`（痕迹），失败时列出具体挂在哪条契约上——对应方法论的**层序即归因序**。

**怎么验证**：5 个新单测分别构造泄漏 intent、未定义错误码、越界 confidence、多余字段的响应，断言它们**必须失败**。新断言不能是死的。

### V1.1 结果

| 验证 | V1.0 | V1.1 |
|---|---|---|
| 单元测试 | 24 passed | **30 passed** |
| Stub 全量 | 37/37 | **40/40** |
| 每条 Case 的断言层数 | 2 层 | **3 层** |

### 这一版真正学到的

> **测试通过 ≠ 测试有效。**

V1.0 的 37/37 是真实运行结果，没有造假；但其中一条断言在任何情况下都不会失败。一个永远为真的断言，和没有这条断言，信息量完全相同。

推论：**评测代码本身也需要被验证**。做法就是给每条新断言配一个「它应该失败」的用例——如果构造不出让它失败的场景，这条断言大概率是死的。
