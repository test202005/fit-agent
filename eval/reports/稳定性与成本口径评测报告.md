> 状态：口径建成，首轮真实证据已取得，**未关账**
> 评测日期：2026-09-03 ~ 09-04（Asia/Shanghai）
> 模型：`deepseek-v4-flash`
> 覆盖：意图链路 discovery 3 轮（第 3~4 节）+ 架构对比 12 场景 2 轮（第 5 节）
> 口径自身的单测：`tests/test_stability_unit.py`，20 条，含三组「把口径改坏必须挂」的反证

> 口径提醒：本报告验证的是**评测口径本身能不能测出东西**，不是意图识别的质量结论。意图识别的质量结论见 [迭代一意图识别评测报告](迭代一意图识别评测报告.md)。

## 1. 这次要回答什么

在此之前，四个 Runner 只报单轮通过率。单轮通过率只能回答「它能不能做对」，回答不了两个问题：

- 同一条 Case 跑三轮，会不会三个结果？
- 跑一次要花多少钱？

本次新增两个口径回答这两个问题，并首次用真实模型取证。

### pass@k 与 pass^k

| 口径 | 定义 | 回答什么 | 出处 |
|---|---|---|---|
| pass@k | k 轮中至少一轮通过 | 峰值能力 | Chen et al., Codex, 2021 |
| pass^k | k 轮全部通过 | 稳定可用 | Yao et al., τ-bench, 2024 |

两者之差即 flaky 区间。只报 pass@k 会把偶然成功说成能力；只报 pass^k 会掩盖「其实做到过」。**两个都报，不合并。**

### 成本口径

每次模型调用的 prompt / completion / total token 从 SDK 响应读出，写入 trace 事件，不进业务返回结构——返回结构受契约断言约束（字段集合必须精确匹配），塞可观测数据会让契约断言失去意义。

## 4. 对照实验：验证波动检测本身

温度 0 下零波动是预期结果，**因此它不能证明波动检测有效**——一个永远返回「无波动」的坏实现也会给出同样的输出。必须制造真实波动，看检测能不能抓住。

方法：同一套 Case、同一个 Prompt、同一个数据集快照，只把温度从 0 升到 1.5，重跑 3 轮。

事实源：`eval/results/report-20260903T164354Z.md`（metadata 记录 `temperature: 1.5`）。

### 结果对照

| 口径 | 温度 0 | 温度 1.5 |
|---|---:|---:|
| pass@k | 1.0000 | 1.0000 |
| pass^k | 1.0000 | **0.8621** |
| flaky | 0 | **4** |
| 高风险轮轮通过 | ✅ | **❌** |
| 总 token | 53,704 | 53,821 |

**检测生效，且这组数据正好说明了为什么两个口径必须都报。**

温度 1.5 下 pass@k 仍是 1.0000——29 条可判 Case 每条都至少成功过一次。若只跑单轮只报通过率，看到的是 0.931 / 0.966 / 0.931，读起来像「偶尔抖一下」。pass^k 揭示真相：**四条 Case 根本不稳**。

```text
intent-adv-006    FAIL → PASS → FAIL
intent-query-003  FAIL → PASS → PASS
intent-rb-006     PASS → PASS → FAIL
intent-rb-010     PASS → FAIL → PASS
```

其中 `intent-adv-006`、`intent-rb-006`、`intent-rb-010` 标记为高风险，触发「高风险轮轮通过」判 ❌。关键安全行为不接受「三次里过两次」，这条纪律被真实数据触发了一次。

### 只有多轮才看得见的两个现象

1. **高风险错进 `record`**：`intent-adv-006`（原始 JSON 注入输入）在第 1、3 轮被判为 `record`，第 2 轮正确拦下。单轮运行有 1/3 概率完全看不到这个洞。
2. **偶发解析失败**：`intent-rb-006` 第 3 轮返回 `llm_parse_error`，另两轮为 0。单轮报告会把 parse error rate 记成 0。

两者都不是新 bug——是**旧口径根本观测不到的东西**。这是本次口径升级最直接的价值证明。

### 这个对照实验的边界

温度 1.5 是**为了制造波动而人为设定**的，不是生产配置。上述四条 flaky 和两个现象**不构成对当前线上质量的结论**，只证明检测逻辑在真实波动下工作正常。生产口径仍以温度 0 的那次运行为准。

## 5. 架构成本对比：一个被实测推翻的假设

成本口径接上 `run_architecture_compare.py` 后（问题清单 P-006 已修），第一次拿到两种架构的同口径成本。

运行：12 场景 × 2 轮真实模型，温度 0。事实源 `eval/results/arch-compare-20260904T015019Z.md`。

| 架构 | 通过率 | 调用次数/请求 | token/请求 | 平均耗时 |
|---|---:|---:|---:|---:|
| 固定链路 | 0.8333 | 1.80 | 1304.5 | 2084ms |
| 工具调用 | 1.0000 | 1.00 | 1187.2 | 1371ms |

P-006 原文的假设是「工具描述会进 prompt，成本上升多少」——预设工具调用更贵。**实测相反**：工具调用每请求便宜 117 token（-9.0%）、快 713ms（-34%）。

原因不在于工具调用便宜，而在于固定链路贵：它每个请求要走**两次**模型——先路由一次，再抽取或规划一次。两次调用的 prompt 累加，超过了工具 schema 塞进单次 prompt 的开销。

分场景看，复合请求上的差距更大：固定链路 2.00 次调用、1449.5 token、通过率 0；工具调用 1.00 次调用、1253.0 token、通过率 1.0。固定链路在复合请求上是**结构性做不到**，不是调得不够好。

**这条结论的边界**：只在当前规模成立——3 个工具、schema 很短。工具数量增长后单次 prompt 会变长，交叉点会移动。不能推广成「工具调用总是更省」。两轮 token 数字完全一致，说明温度 0 下 prompt 长度稳定，但两轮也不足以支撑成本的方差结论。

## 6. 这份证据能证明什么

- 两个稳定性口径和成本口径已经跑通真实链路，数字能取到、能落进报告；
- **波动检测在真实波动下有效**：温度 1.5 的对照运行抓出 4 条 flaky、点名 3 条高风险不稳、并让「高风险轮轮通过」正确判负；
- 在 discovery 集、temperature 0、该 Prompt 快照下，意图识别 3 轮零波动；
- 输入防御层在模型调用之前生效；
- 单条意图识别的成本量级约 640 token；
- 两种架构的同口径成本已取到，且推翻了「工具调用一定更贵」的原假设。

## 7. 这份证据不能证明什么

1. **不能证明系统整体稳定。** 只跑了意图识别一层，抽取、查询、工具调用三个 Runner 虽已接入同一口径，但只跑过 stub，无真实数据。
2. **不能证明泛化稳定。** discovery 集参与过 Prompt 调优，不是 blind holdout，存在选择偏差。零波动是这个集合上的结论。
3. **对照实验不构成质量结论。** 温度 1.5 是为制造波动人为设定的，不是生产配置。它证明的是检测器有效，不是线上有这些问题。
4. **成本口径未覆盖多步与多轮。** 已覆盖意图链路单次调用和两种架构的整请求成本，但当前工具调用是单轮的，ReAct 多步循环、多轮对话的累计成本没有链路可测。
5. **架构成本结论不可外推。** 3 个工具、短 schema 下工具调用更省，工具变多后结论会翻转，交叉点未测。
6. **不构成性能专项。** 只有端到端耗时和 token，没有节点级延迟拆分、尾部延迟（P95/P99）和并发下的表现。
7. **不代表真实用户分布下的准确率。** 沿用 iteration 1 的口径提醒。

## 8. 下一步

按优先级：

1. 抽取 / 查询 / 工具三个 Runner 各跑一次 live，取真实稳定性与成本；
2. blind holdout 建成后，在独立集上重跑稳定性口径；
3. `intent-adv-006` 在高温下会把原始 JSON 注入判成 `record`。温度 0 下未复现，**不作为缺陷登记**，但记为一个值得在 blind holdout 里专门覆盖的方向；
4. 性能专项（尾部延迟、节点拆分、并发）留到多步链路成型后再做——单轮链路上做一遍，上 ReAct 后量级全变，要重测。
