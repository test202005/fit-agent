# 37 条全过之后，我发现一条断言没有真正工作

> 《Agent 评测实战》迭代一·第 3 篇。本文记录一次真实的评测器缺陷：报告全部通过，但一条关键断言无法捕获它声称要防止的问题。

迭代一最初的结果很好看：24 条单元测试通过，Stub 全量 37/37，真实模型的验收集也连续三轮通过。

如果只看结果，这一轮已经可以结束。但后来我用自己整理的断言方法重新检查评测代码，问了一句：

> 如果防御路径偷偷调用了模型，这条断言真的会失败吗？

答案是否定的。

## 原来的断言错在哪里

项目要求空字符串、纯空白和超长输入直接返回 `bad_request`，而且必须在调用模型之前拦截。正常 Trace 只能包含：

```text
input_received → result
```

原来的代码这样判断：

```python
expected_trace_events(actual).issubset(event_names)
```

它只检查“应该出现的事件有没有出现”，没有检查“不应该出现的事件是否混进来了”。

假设真实 Trace 是：

```text
input_received → llm_request → result
```

`input_received` 和 `result` 仍然都在，因此 `issubset()` 返回 `True`。系统明明多调用了一次模型，Case 依然会被判为 PASS。

也就是说，37/37 是真实运行结果，但其中这条断言无论关键错误是否出现，都可能通过。它提供的信息量和没有这条断言几乎一样。

## 修复不是换一个函数这么简单

代码改动只有一行：

```python
# 旧：只检查缺没缺
expected_trace_events(actual).issubset(event_names)

# 新：缺少和多出都失败
expected_trace_events(actual) == event_names
```

真正重要的不是把 `issubset` 换成 `==`，而是给断言补了一条反例测试：

```python
honest = {"input_received", "result"}
sneaky = {"input_received", "llm_request", "result"}

assert expected_trace_events(result) == honest
assert expected_trace_events(result) != sneaky
```

这条测试不是证明系统当前能通过，而是证明当错误真的出现时，评测器能够失败。

从这次开始，我给新增断言加了一条要求：

> 不只准备它应该通过的例子，还要准备一个它必须失败的反例。

## 回扫还发现了另外两个缺口

同一轮检查又发现：

第一，`bad_request` 只存在于单元测试，没有进入评测数据集。单测能保证函数逻辑，但正式回归报告看不到这条对外契约。

第二，Runner 只看意图和错误码，没有严格检查响应结构。如果失败响应意外泄漏了 `intent`，或者成功响应多出调试字段，也可能被判为通过。

因此 V1.1 一共做了三件事：

1. Trace 事件从子集判断改为精确集合；
2. 增加响应结构、枚举、置信度范围和失败字段互斥断言；
3. 增加 3 条 `bad_request` Case，把数据集从 37 条扩展到 40 条。

修复后新增 6 组反证单测，结果变为：

```text
30 passed
Stub 40/40
```

这里不能说“40/40 比 37/37 更准确”。更准确的结论是：新版本检查了更多契约，而且关键断言已经证明自己能抓到对应错误。

## 为什么 AI 评测尤其需要测试评测器

普通自动化断言通常面对稳定结构，错误相对容易暴露。AI 评测经常同时包含语义判断、结构解析、Trace 检查、状态验证和指标聚合，评测器本身也会制造假 PASS、假 FAIL 和错误分母。

Anthropic 在 Agent Eval 实践中提醒，低分可能来自任务歧义、评分器缺陷或 Harness 限制，不能直接把分数当成模型能力；他们也建议检查 Transcript，确认失败是否公平。这个原则反过来也成立：高分同样不能直接相信，必须确认评分器真的检查了我们关心的问题。

我后来把断言检查总结成四个问题：

1. 系统明确承诺了什么？
2. 用户真正要求了什么？
3. 哪些事情绝对不应该发生？
4. 输出、Trace 和最终状态是否一致？

这次漏洞就属于第三问：我们检查了该出现的，却没有检查不该出现的。

## 从用户角度看，这篇最值得带走什么

如果你正在做自己的 AI 测试项目，不需要先建设复杂的评测平台。先挑最重要的一条断言，故意构造一个错误结果，看它会不会变红。

例如：

- 声称能防止错误写入，就故意让写入次数多一条；
- 声称失败不泄漏字段，就故意在失败响应里加入业务字段；
- 声称没有调用模型，就故意在 Trace 中加入 `llm_request`；
- 声称用户数据隔离，就故意让 B 用户读取 A 用户记录。

如果错误已经发生，报告仍然是 PASS，应该先修评测器，而不是继续扩充 Case。

## 能力沉淀

- **解决的问题**：评测报告全绿，但 Trace 断言无法捕获额外模型调用；
- **形成的能力**：断言反证、评测器自测、响应契约和负向副作用检查；
- **留下的证据**：漏洞复现单测、精确事件集合、3 条防御 Case、30 条单测和 40/40 Stub 回归；
- **不能证明的事**：断言能够抓住已知错误，不代表它已经覆盖所有未知失败模式。

这一轮给整个项目留下了一条长期纪律：**测试通过不等于测试有效，评测代码本身也必须被验证。**
