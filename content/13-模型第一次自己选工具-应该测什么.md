# 模型第一次自己选工具，应该测什么

做到 Tool Use 之前，`fit-agent` 的处理方式很像传统后端：先识别用户意图，再由代码决定走记录、查询还是统计。模型负责理解自然语言，但真正调用哪个函数，仍由 `if/else` 控制。

这种固定链路没有问题。对于路径明确、风险高、可以穷举的任务，代码路由反而更稳定。真正推动我增加 Tool Use 的，是下面这种复合请求：

> 帮我看看今天练了什么，再记录跑步 3 公里。

它同时包含查询和写入。继续扩展固定路由当然也能做，但每增加一种组合，都要新增一条编排分支。于是我做了一个受控改动：保留原来的业务函数，只把“选择哪个函数、生成什么参数”交给模型。

系统里一共只有三个工具：

```text
create_record   记录已经完成的训练
query_records   查询某一天的训练记录
count_exercise  统计某个具体动作在日期范围内练了几次
```

我原本以为，把三个 Python 函数包装成 Function Calling 的格式，模型能正确调用，Tool Use 就算完成了。后来才发现，工具调用不是给函数换一个名字，而是在确定性代码和不确定性模型之间建立一份新契约。

## Schema 不是接口文档，而是模型看到的操作说明

以 `count_exercise` 为例，它的 Schema 大致是：

```json
{
  "name": "count_exercise",
  "description": "统计某个具体动作在一段日期范围内练了几次。",
  "parameters": {
    "type": "object",
    "properties": {
      "exercise": {"type": "string"},
      "from": {"type": "string"},
      "to": {"type": "string"}
    },
    "required": ["exercise", "from", "to"],
    "additionalProperties": false
  }
}
```

对普通接口来说，调用方通常已经知道接口用途；对大模型来说，工具名、描述、参数名和示例本身就是上下文。模型要先从这段描述里判断“现在该不该用”，再生成参数。

所以工具设计至少要回答六个问题：

1. 它解决什么用户任务？
2. 什么情况下应该调用？
3. 什么情况下不能调用？
4. 完成任务最少需要哪些参数？
5. 成功和失败分别返回什么？
6. 它会不会写数据、发消息、产生费用或其他副作用？

Anthropic 在工具设计实践中也把 Tool 定义为确定性系统与非确定性 Agent 之间的契约，并强调工具应当职责清楚、减少重叠、参数命名明确，再通过真实任务评测模型能否理解这些工具。[Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

这解释了一个常见误区：后端接口有十个，不代表应该原样暴露十个 Tools。接口是按系统资源拆分的，工具应该按用户任务拆分。两个工具的描述连开发都分不清，模型只会更容易选错。

## 第一个真实问题：Schema 和 Validator 各说各话

第一轮实现后，28 条 Tool Use Case 在真实模型上连续三轮通过，工具选择、参数幻觉和错误写入都是 0。表面上看，这部分已经可以结束。

但我在整理工具契约时发现：三个 Validator 都会拒绝未知字段，Schema 却没有声明 `additionalProperties: false`。

也就是说，两层规则并不一致：

```text
模型看到的 Schema：没有明确说不能生成其他字段
服务端 Validator：一旦出现其他字段，立即报错
```

当前模型碰巧没有生成多余字段，所以真实评测全绿；但这不代表契约没有风险。换模型、修改描述或增加工具后，模型如果多传一个字段，错误才会突然暴露。

修复并不复杂：在三个 Schema 中明确禁止未知字段，再增加静态契约测试，锁定以下内容：

- 工具名不能重复；
- `required` 必须存在于 `properties`；
- Schema 字段和类型必须符合业务约定；
- 每个 Schema 必须存在对应 Executor；
- Schema 禁止的未知字段，Validator 也必须拒绝。

补完后，全项目 155 条单测通过。这里没有再次宣称模型能力提升，因为没有修改模型或 Prompt；这次验证证明的是工具契约和确定性保护层更一致。

## 为什么有 Schema，还要 Validator

如果模型接口支持严格 Schema，可以减少字段缺失、类型错误和额外参数。OpenAI 的 Function Calling 接口也提供 strict schema adherence，但只支持 JSON Schema 的一个子集。[OpenAI Function Calling API](https://platform.openai.com/docs/api-reference/chat/create)

严格 Schema 仍不能替代服务端校验。Schema 主要约束输出结构，Validator 还要处理业务事实，例如：

```text
sets = -3                    类型正确，业务非法
from = 2026-09-05
to   = 2026-09-01           格式正确，日期范围反了
exercise = ""               类型正确，但没有有效值
```

更重要的是，模型只负责提出调用意图，不能拥有最终执行权。真正写数据库之前，代码仍要检查字段、权限、状态、幂等和副作用。

我现在把一次工具调用拆成五个角色：

```text
模型：理解需求、选择工具、生成参数
Schema：告诉模型有哪些动作以及参数契约
Validator：拒绝非法、越界或无依据的参数
Executor：执行确定性业务逻辑
Guardrail：控制权限、副作用、幂等和调用上限
```

这样排查问题时，不会一看到工具调用失败就笼统归因成“模型不行”。可能是工具边界重叠，可能是参数描述模糊，也可能是 Validator 和 Schema 不一致。

## 这次沉淀出什么方法

我把工具设计收敛成一条可以直接执行的流程：

```text
先写用户任务
→ 判断固定路由还是 Tool Use
→ 按任务拆工具边界
→ 定义 Schema
→ 实现 Validator 与 Executor
→ 先做确定性契约测试
→ 再用真实模型测试工具选择
```

最关键的顺序是：先证明工具本身的契约一致，再测试模型会不会使用它。否则模型评测失败时，连问题在模型还是代码都说不清。

## 这份证据能证明什么、不能证明什么

当前证据能证明：在三个工具的规模下，`fit-agent` 已经形成 Schema、Validator、Executor 和静态契约测试；当前评测集也覆盖记录、查询、统计、复合请求和不调用工具的场景。

它不能证明工具增加到几十个以后，模型仍能稳定选择；也没有验证多轮 Agent 如何读取工具结果、失败后重试或切换工具。当前实现只是单轮 Tool Use，不把它包装成完整 ReAct Agent。
