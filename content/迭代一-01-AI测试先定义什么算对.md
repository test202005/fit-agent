# AI 测试的第一道门槛：先定义什么算对

> 《Agent 评测实战》迭代一·第 1 篇。本文只讨论一件事：面对自然语言输入，怎样先把“正确”定义清楚，再开始写评测 Case。

刚开始做 AI 测试时，我最自然的反应是先准备一批句子，然后统计模型答对了多少。真正动手以后，我很快碰到一个更基础的问题：**如果团队自己都说不清什么算对，准确率到底在统计什么？**

我用来验证这件事的项目叫 `fit-agent`，它接收一句自然语言，帮助用户记录或查询训练。迭代一没有急着做完整 Agent，只实现一个意图路由节点：

```text
用户输入 → record / query / reject
```

- `record`：用户明确说了一件已经发生的训练；
- `query`：用户要查询自己的训练记录；
- `reject`：咨询、闲聊、未来计划和其他不进入业务链路的内容。

看起来只有三类，真正困难的却不是写分类 Prompt，而是划清边界。

## 两句话，把问题暴露出来

下面两句话只差几个字：

```text
今天练了胸
今天训练了
```

第一句进入 `record`，第二句进入 `reject`。

原因不是“胸”这个关键词更像训练，而是我先定义了一条业务规则：

> 一条输入要进入 record，必须明确陈述已经发生的训练，并且至少包含一个可继续抽取或追问的训练对象。

训练对象可以是动作、肌群、训练类型、距离或时长。“今天练了胸”虽然没有重量和组数，但已经有可以继续处理的事实骨架；“今天训练了”只有训练语气，没有任何对象，后续既无法结构化，也不知道该追问什么。

如果没有这条规则，两个标注人可能给出两个答案，模型无论输出什么，都有人觉得合理。这样的 Case 不是困难，而是题目本身没有定义完整。

## 先写规则表，再扩充句子

我没有继续批量生成表达，而是先在 PRD 中写出意图决策表。比如：

| 输入特征 | expected |
|---|---|
| 已发生，并包含训练对象 | `record` |
| 纯否定，没有正向训练事实 | `reject` |
| 未来计划，没有已发生事实 | `reject` |
| 查询本人训练记录 | `query` |
| 咨询动作知识 | `reject` |

然后才围绕每条规则设计成对的边界 Case：

```text
今天没练卧推，改练深蹲5组 → record
今天没练卧推，改成休息     → reject

明天练腿，今天刚跑了5公里   → record
明天打算练腿                 → reject
```

这比把一句标准表达改写二十遍更有价值。前者覆盖不同的失败机制，后者很可能只是在重复同一道题。

迭代一最初的数据集一共 37 条：34 条分类 Case，加上 3 条故障注入 Case。这里的“37”不是一个值得追求的规模，它只是当时覆盖业务规则所需要的最小集合。OpenAI 将评测过程概括为“Specify → Measure → Improve”：先定义什么叫好，再测量和改进；Anthropic 也把 Eval Task 定义为具有明确输入与成功标准的测试。两者都指向同一个起点：**评测不是先跑模型，而是先明确成功。**

## 写不出唯一 expected，就先不收录

迭代一里还有一类输入：

```text
帮我记录今天的卧推，再查一下这周练了几次。
```

它同时包含记录和查询。系统当时只有单一路由，产品也没有定义执行顺序。我没有让模型“自己判断一个合理答案”，而是把它标成 Backlog，不进入正式数据集。

这是我后来一直保留的一条门禁：

> 写不出唯一 expected 的输入，不进入自动判分的数据集；先回到业务规则补决策。

否则评测很容易陷入一个循环：模型输出什么，测试人员就根据结果解释为什么它也可以。最后看起来每条都能评，实际上没有任何稳定标准。

## 从用户角度看，这一步值不值得做

如果你来自传统测试，这一步并不陌生。它仍然是在做等价类、边界值和需求澄清，只是边界从数字区间变成了自然语言语义。

真正需要补上的能力不是“会调用一个大模型”，而是把模糊语言重新变成可执行规则：

```text
业务目标
→ 决策规则
→ 语义等价类
→ 正反 Case
→ 稳定 expected
```

这也是我认为传统测试经验在 AI 时代仍然有价值的原因。工具变了，定义风险和验证边界的基本功没有失效。

## 能力沉淀

- **解决的问题**：意图分类没有统一正确标准，Case 数量无法代表覆盖质量；
- **形成的能力**：业务边界拆解、语义等价类设计、Golden Case 准入判断；
- **留下的证据**：意图决策表、37 条初始 Case、逐条 expected 和风险分类；
- **不能证明的事**：这批合成数据不能代表真实用户分布，也不能据此宣称模型泛化能力达到 100%。
