# 模型一换，为什么不同能力表现不一样

最近公司项目把底层模型从 DeepSeek V4 Flash 切换成千问 3.8 Flash，结果并不是所有能力一起变差。

意图识别的通过率从 90% 左右降到了 60% 左右，但记录运动和饮食的下降没有这么明显。

这个结果比“新模型整体不行”更值得分析。因为它说明：模型不是一个只影响总分的黑盒，不同业务能力对模型的敏感程度并不一样。

## 看起来只是换了模型

如果从普通接口的角度看，模型切换可能只改一行配置：

```text
model = deepseek-v4-flash
→
model = qwen-3.8-flash
```

但对 Agent 来说，模型参与了很多行为：

```text
理解用户输入
判断意图
提取参数
组织结构化输出
选择工具或后续链路
```

所以模型切换不是简单的配置替换，而是一次行为变更。

不过也不能因为意图识别下降，就得出“新模型所有能力都变差”的结论。当前项目的对比实验也出现过类似情况：两个模型在 Intent 和 Extract 上有差异，但 Query 和 Tool Use 基本持平。[两模型受控对比评测报告](../eval/reports/两模型受控对比评测报告.md)

## 为什么意图识别更容易受到影响

意图识别的标签很少，例如：

```text
record / query / reject
```

但真正难的不是记住这三个单词，而是判断边界：

```text
今天练了胸       → 已发生记录
明天练胸         → 未来计划
今天没练胸       → 不能直接当成训练记录
没练胸，改练深蹲 → 应该记录深蹲
今天动了动腿     → 信息不完整，但可能进入记录流程
```

模型对“已发生”“未来”“否定”和“修正”的理解稍有不同，标签就会变化。

而且意图通常在链路最前面：

```text
意图判断错误
→ 路由错误
→ 后面的记录、查询或计划逻辑没有机会执行
```

因此意图识别看起来只是一个分类问题，实际上是一个高杠杆的路由问题。它的错误会被后续链路放大。

## 为什么记录运动和饮食没有跌得那么多

记录类输入往往有更直接的业务线索：

```text
今天跑了 5 公里
午餐吃了两个鸡蛋
今天卧推 60 公斤，做了 4 组
```

这类任务更像：

```text
识别动作或食物
→ 提取数量和单位
→ 按固定字段输出
```

所以模型之间可能更容易保持一致。

但“下降较小”不等于“没有问题”。记录运动和饮食还要继续检查：

- 数量和单位有没有错；
- 未来计划有没有被当成已完成记录；
- 否定表达有没有被错误记录；
- 多条运动或多种食物有没有漏提；
- 不完整信息有没有被模型擅自补全。

意图错误通常马上表现为标签错分，记录和饮食错误则可能藏在字段、状态和最终数据里。只看意图通过率，无法代表整个 Agent 的质量。

## 这是模型问题，还是设计问题

模型对 Agent 影响很大，本身是正常现象。只要模型参与了语义判断，换模型就可能改变行为。

但如果系统默认“模型可以随便替换”，却没有做任何验证，那就是工程设计不完整。

我现在会把问题拆成两部分：

```text
模型依赖：模型能力不同，导致行为不同
系统设计：是否有机制发现、解释和控制这种差异
```

真正成熟的目标不是让所有模型表现完全一样，而是知道：

```text
哪个模型适合哪类任务
哪些能力对模型切换敏感
哪些错误绝对不能接受
成本下降是否值得质量损失
```

## 快速迭代阶段，怎么做最划算

现在不需要先做复杂的模型路由平台。每次切换模型，先固定四样东西：

```text
同一批 Case
同一份 Prompt
同一套断言
同一组关键参数
```

然后按业务能力看结果，而不是只看一个总通过率：

```text
意图识别：各意图和边界分别怎样
运动记录：字段、单位和写入是否正确
饮食记录：食物、数量和单位是否正确
结构化输出：解析和字段契约是否稳定
高风险行为：有没有错误写入或错误路由
```

第一轮只需要回答三个问题：

1. 新模型影响了哪些能力？
2. 哪些失败是稳定出现，哪些只是偶发？
3. 失败是模型语义问题，还是 Prompt、参数、解析和接口适配问题？

这比直接争论“哪个模型更强”更有用。

## 成本不能只看模型单价

如果新模型更便宜，但意图识别从 90% 掉到 60%，就不能只看每次调用少花了多少钱。

还要考虑：

```text
模型调用成本
+ 重试成本
+ 人工排查成本
+ 用户重新操作成本
+ 错误记录和数据修复成本
```

更实用的比较方式是：

```text
单位成功任务成本
= 总调用成本 / 成功完成的业务任务数
```

例如，一个便宜模型可以承担明确的运动和饮食记录；复杂意图、否定修正和高风险请求，再交给能力更强的模型。这个方向可以作为后续实验，但当前先通过数据确认哪些场景值得升级，不凭感觉拆复杂链路。

## 这次应该留下什么

这次模型切换至少应该沉淀四样东西：

```text
模型对比结果
按业务能力的差异表
真实失败输入和原始响应
模型切换后的回归 Case
```

以后再换模型，不需要从头猜，而是直接跑这套小型回归集。

Anthropic 也建议把任务、Trial、Grader 和 Assertion 分开记录，通过多轮运行观察模型行为波动；评测的价值之一，就是帮助团队更快判断模型升级是否真的适合当前 Agent。[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 这份经历能证明什么、不能证明什么

它能证明：模型切换会对不同业务能力产生不同影响，意图识别通常比线索明确的结构化记录更容易暴露边界差异；模型选型应该按任务能力和业务风险分析。

它不能证明千问模型整体不如 DeepSeek，也不能证明记录运动和饮食一定稳定。要得出模型结论，还需要在同一批输入、同一 Prompt、同一参数和同一断言下完成对比，并查看原始响应。

## 最后

快速迭代阶段，最实用的模型选型方法不是一开始就建设复杂平台，而是先保留一套小而重要的回归集：

```text
每次换模型
→ 跑同一批 Case
→ 按能力分类看变化
→ 先守住高风险行为
→ 再比较成本
→ 记录模型适用边界
```

模型可以替换，但质量证据不能省。真正值得留下的不是“这次换模型成功或失败”，而是知道它为什么影响意图、为什么没有同样影响记录，以及下一次应该用什么证据做决定。
