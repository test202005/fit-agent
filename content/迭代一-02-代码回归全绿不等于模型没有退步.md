# 代码回归全绿，为什么不能证明模型没有退步

> 《Agent 评测实战》迭代一·第 2 篇。本文拆开 AI 系统里经常被混在一起的两本账：确定性代码契约与真实模型质量。

迭代一刚把意图路由跑通时，我遇到一个很现实的问题：如果每次改代码都调用真实模型，回归测试既花 Token，又可能因为模型输出波动而不稳定；如果完全使用固定返回，测试虽然稳定，却测不到模型能力。

我最初想把两者放进同一套“通过率”，后来发现这是一个错误问题。一次 AI 请求里，本来就有两类性质完全不同的东西：

```text
模型有没有理解对             → 不确定，需要真实模型
解析、错误映射、Trace 是否正确 → 确定，可以稳定回归
```

既然测试对象不同，就不应该共用一个结论。

## 第一层：不用真实模型，验证代码契约

项目里的所有模型调用都通过 `LLMClient`：

```python
class LLMClient(Protocol):
    def complete(self, system_prompt: str, user_text: str) -> LLMResult: ...
```

线上使用 `LiveLLM`，测试时换成 `StubLLM`。Stub 可以固定返回合法 JSON，也可以主动制造超时、API 错误和坏 JSON：

```python
StubLLM(raw_text='{"intent":"record","confidence":0.9}')
StubLLM(fault="llm_timeout")
StubLLM(fault="llm_api_error")
StubLLM(raw_text="not-json")
```

这样可以稳定验证：

- 合法响应能否被正确解析；
- 非法字段和越界值是否被拒绝；
- 超时和 API 异常是否映射到明确错误码；
- 空输入是否在调用模型前被拦截；
- Trace 是否保留了必要事件；
- 路由阶段是否保持零业务写入。

这些都是真实代码路径，只是把不可控的模型替换成了可控依赖。

但 Stub 有一个必须主动写在报告里的限制：普通 Case 的返回值就是根据 `expected_intent` 构造的。注入 `record`，最后解析出 `record`，完全不能证明真实模型会分类。

因此我在报告中固定保留一句提醒：

> Stub 结果只验证代码与契约，不代表模型质量。

## 第二层：使用真实模型，验证行为质量

模型质量必须使用 `LiveLLM`。同一批输入真正发送给模型，再检查：

- `record / query / reject` 是否分类正确；
- 各类别 Precision、Recall 和 F1；
- 解析错误是否出现；
- 高风险输入是否被错误送进有副作用的 `record`；
- 同一个版本连续运行是否稳定。

迭代一最终留下了两组不同证据：

| 证据 | 当时结果 | 能证明什么 |
|---|---:|---|
| 单元测试 | 24 passed | 纯代码逻辑和边界行为通过 |
| Stub 全量 | 37/37 | Runner、解析、错误路径和 Trace 契约通过 |
| Live discovery ×3 | 30/30 | 调试集上的真实模型行为 |
| Live regression ×3 | 24/24 | 已修问题没有复发 |
| Live locked ×3 | 48/48 | 当时 16 条验收 Case 连续三轮通过 |

这些数字不能合并成一个“总通过率”。24 条单测和 48 次 Live Trial 的测试对象、分母与证据强度都不同。

## 为什么故障 Case 也不能混进分类准确率

数据集中还有 3 条故障注入 Case：超时、API 错误和解析错误。它们验证系统能否正确处理异常，不是在考模型属于哪个意图。

如果把这 3 条稳定通过的契约 Case 加进分类准确率，相当于用代码必过项给模型分数注水。因此报告把它们单列，不进入三分类混淆矩阵。

这件事后来影响了整个项目：环境 ERROR、业务 FAIL、规则待确认 REVIEW，都不能为了得到一个好看的数字而混在一起。

## 什么时候跑哪一本账

我最后采用的节奏很简单：

```text
每次代码修改
→ 单测 + Stub 全量

Prompt、模型或模型输入发生变化
→ 再跑真实模型评测

候选版本冻结
→ 固定 Case、Prompt、参数和版本，多轮验收
```

这让日常回归可以快速、免费、可复现；真正需要判断模型能力时，再付出 Live 评测成本。

OpenAI 的公开实践强调，评测需要持续维护，并用真实工作流中的错误推动改进；Anthropic 则明确区分能力评测与回归评测：前者寻找当前做不到的任务，后者保护已经做到的能力。项目里的“两本账”不是照搬工具，而是把同样的原则落实到一个可以运行的系统里。

## 从用户角度看，这一步有什么价值

准备进入 AI 测试的人很容易被工具和平台吓住，其实这一篇最值得迁移的不是某个框架，而是测试对象拆分：

```text
把确定部分做成免费、稳定的自动回归
把不确定部分放进受控的模型质量评测
不让一种证据替另一种证据作结论
```

传统测试中的依赖注入、Mock、错误路径和契约测试仍然有效。新增的工作，是识别哪些结果由模型决定，并为它建立独立的数据集、指标和运行快照。

## 能力沉淀

- **解决的问题**：真实模型回归昂贵且波动，固定响应又无法代表模型质量；
- **形成的能力**：LLM 可替换设计、故障注入、确定性回归与模型评测分账；
- **留下的证据**：`LiveLLM / StubLLM`、37 条契约运行结果、三组 Live 报告和版本快照；
- **不能证明的事**：Stub 全绿不代表模型准确，16 条验收集全绿也不代表真实用户分布下的准确率为 100%。
