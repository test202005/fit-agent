# 最终结果正确，为什么中间过程仍可能有问题

Tool Use 跑通以后，我最先看的也是最终结果：该记录的数据有没有写进去，该查询的结果有没有返回。

这当然重要，但不够。

假设用户说：

> 查一下今天练了什么，再记录跑步 3 公里。

最后数据库里确实多了一条“跑步 3 公里”，并不能证明整个任务正确。模型可能没有查询，可能多调用了一次写入，也可能先用错误参数写入，再用正确参数补写。只看最后一条数据，这些问题都会被隐藏。

工具让模型获得了行动能力以后，测试对象就从“一个回答”变成了“一段执行过程”。

## 一次 Tool Use，到底应该看哪几层

我最后把断言拆成五层：

```text
1. 工具选择：该不该调，选的是不是正确工具
2. 参数：字段、值、单位、时间，有没有参数幻觉
3. 调用过程：次数、顺序、多调、漏调、首个分歧
4. 执行结果：返回结果、最终状态和副作用
5. 追溯证据：Trace 是否与真实调用一致，版本能否还原
```

这五层不是为了把报告做复杂，而是让失败可以定位。

例如“这周卧推了几次”没有结果，至少存在四种完全不同的原因：

```text
模型没有调用工具
模型调用了 query_records，工具选错
模型调用 count_exercise，但日期参数错了
工具和参数都对，Executor 查询错了
```

如果报告只有 `expected=3, actual=0`，开发拿到后仍然不知道应该改 Prompt、Schema、日期处理还是数据库查询。

## 我用故障注入证明断言真的会失败

真实模型在当前 28 条 Case 上表现稳定，并没有自然产生足够多的错误。为了确认评测不是“无论怎样都全绿”，我用 Stub 主动注入四类失败：

```text
选错工具：查询请求却调用 create_record
该调不调：模型只返回文本，没有调用工具
未知工具：调用 delete_everything
参数错误：create_record 的 sets = -3
```

还注入了一条三步调用：

```text
第 1 步：正确记录卧推
第 2 步：exercise 为空，执行失败
第 3 步：调用未知工具
```

报告不能只说“有两步失败”，还必须指出第一个失败发生在第 2 步。因为后面的错误可能只是早期错误的级联结果，修复时应该优先处理第一个偏离点。

这也是 Trace 和 Trajectory 的区别：Trace 解决“发生了什么、能不能串起来”，Trajectory 进一步判断“模型选择的行动序列是否合理”。只有日志，不等于已经完成轨迹评测。

Anthropic 对 Agent eval 的定义同样强调，评测不仅包括最终输出，还包括工具调用、中间结果和环境状态组成的完整 transcript；同时应根据问题选择代码判分、模型判分或人工判断。[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

当前这些字段都能确定判断，所以我优先使用代码断言，没有引入大模型裁判。

## 最容易被忽略的是“不该发生什么”

传统接口测试经常验证“返回了什么”，Tool Use 还必须检查“有没有多做什么”。

在 `fit-agent` 中，我把三项设成硬门禁：

```text
参数幻觉 = 0
不该调用却调用工具 = 0
不该写却写入数据 = 0
```

原因很直接：一次错误回答通常还能被用户发现，一次静默写错可能长期污染数据。对于发消息、退款、下单、删除文件这类工具，副作用风险会更高。

因此测试“不支持的请求”并不是验证模型能否礼貌拒绝，而是验证 Executor 根本没有产生写入。回答看起来再合理，只要状态被错误修改，就应该失败。

## 工具序列是不是越精确越好

也不是。

当前项目是单轮、三个工具，而且复合请求只有一种明确合法路径，因此可以断言：

```text
query_records → create_record
```

但在更复杂的 Agent 中，同一个任务可能存在多条合法路径。如果测试强制要求唯一工具序列，模型用另一条同样正确、甚至更高效的路径，也会被误判失败。

所以断言粒度应该跟任务风险匹配：

```text
只有一种合法路径 → 可以精确断言工具与顺序
存在多种合法路径 → 重点断言必要工具、禁止行为和最终状态
自然语言质量 → 最后才考虑大模型裁判或人工复核
```

Anthropic 在工具评测实践中也提醒，可以指定期望工具来判断模型是否理解工具用途，但不应在存在多种有效策略时过度规定路径。[Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

## 最终报告不能只放一个通过率

当前 Tool Use 报告至少保留这些结果：

- Case 级通过率和断言级通过率；
- 工具选择混淆矩阵；
- 参数幻觉、不该调用和写入违规；
- 实际工具序列与首个分歧步骤；
- `pass@k`、`pass^k` 和波动情况；
- Token、模型、Prompt、数据集版本和 `trace_id`。

在一份受控对比报告中，DeepSeek Flash 和 Pro 分别对 28 条 Case 运行三轮，共 168 次 Case 执行，当前集合上全部通过，三项硬门禁均为 0。

这个结果说明两种模型在当时的三个工具、Prompt 和数据集快照上都能稳定完成任务；它不说明模型在更多工具、更长链路或真实用户流量下仍然是 100%。评测集已经参与开发，也不能包装成公开 Benchmark。

## 这次沉淀出什么方法

一次 Tool Use 评测可以按下面的顺序设计：

```text
从业务任务划分等价类
→ 给每条 Case 定义应调、不应调和副作用边界
→ 断言工具与参数
→ 断言次数、顺序和首个分歧
→ 检查执行结果与最终状态
→ 用 Trace 保存全过程
→ 用故障注入证明断言会失败
→ 再跑真实模型多轮评测
```

这里最有价值的不是增加了多少指标，而是每种失败都有明确归属：工具选错看模型和描述，参数错误看 Schema 与生成，执行错误看 Validator 和 Executor，状态错误看副作用保护，结果不可复现看 Trace 和版本证据。

## 这份证据能证明什么、不能证明什么

当前证据能证明：`fit-agent` 的单轮 Tool Use 已经覆盖工具选择、参数、调用过程、执行状态和 Trace 五层，并通过故障注入证明关键断言可以捕获错误。

它不能证明多轮 Agent 的重试、换工具、停止条件和错误恢复能力。当前系统也没有把工具结果再次回灌给模型，因此还不能把这部分经验扩大成完整 ReAct 轨迹评测。

## 能力沉淀

公开的 Agent 评测岗位会关注评测体系、自动化工具、结构化结果分析以及 Agent 能力边界；Tool Use、execution-based evaluation 和 trajectory 分析正好落在这条能力链上。[字节跳动大模型/Agent 评测工程师岗位](https://www.nowcoder.com/jobs/detail/429684)

这一轮能够展示的不是一个漂亮的 100%，而是：为什么最终结果不够、怎样把调用过程拆成可执行断言、怎样用故障注入反证评测有效，以及怎样明确说明结论只能覆盖当前系统边界。
