# fit-agent 能力地图

## 从一个 AI 功能，做到一套可评测的 AI 系统

`fit-agent` 不是为了展示“我做了一个 Agent”，而是持续建设一个**能被验证、能被追溯、能持续回归的 AI 系统**。

每增加一层 AI 能力，就同步回答四个问题：

```text
模型获得了什么新决策权？
新增了什么失败风险？
怎么观测和断言？
出错后如何归因、修复和防复发？
```

这条主线与 AI Agent 测试/评测岗位要求直接对应：模型与 Prompt 评测、数据集建设、Agent 过程验证、可观测性、质量归因和持续回归。

## 当前能力地图

| AI 系统能力 | 项目实现 | 质量保障方式 | 已沉淀的测试能力 |
|---|---|---|---|
| 意图识别 | `record / query / reject` 路由 | 等价类、对抗样本、混淆矩阵、风险 Case | 模型行为评测与边界覆盖 |
| 结构化抽取 | 自然语言 → 训练记录 | `complete / incomplete / invalid`、字段和写入门禁 | 结构化输出与副作用测试 |
| 查询执行 | Planner + Executor + HTTP | Frozen Clock、Fixture、查询零写入、时间边界 | 可测试架构与端到端验证 |
| Tool Use | 模型自主选择工具和参数 | 工具序列、参数、调用次数、写入行为、Trajectory | Agent 过程与工具调用评测 |
| 稳定性与成本 | 多轮、多模型、Token 统计 | `pass@k`、`pass^k`、flaky、Trace 聚合 | 稳定性、成本与模型对比 |

当前项目已从固定 Workflow 走到 **L1 Tool Use**：模型第一次拥有“选哪个工具、传什么参数、要不要执行动作”的决策权。尚未把未落地的 ReAct 多步、Memory、多 Agent 包装成现有能力。

## 评测闭环

```text
真实需求
  ↓
能力实现
  ↓
失败模式分析
  ↓
Case / Fixture / Prompt / 断言
  ↓
Stub 回归 + 真实模型多轮运行
  ↓
Trace 定位与分层归因
  ↓
修复、反证、回归
  ↓
方法论与证据边界
```

这里的重点不是把所有输出交给大模型裁判，而是先把能确定性验证的部分断死：字段、状态、工具、参数、次数、写入、副作用、Trace 和版本快照；只有代码无法判断的开放语义，才保留人工复核或后续引入裁判的空间。

## 企业级质量能力的最小落地

- **可追溯**：每次请求有 `trace_id`，能回到模型响应、工具调用和最终状态；
- **可测试**：LLM、Storage、Clock 都能替换，Stub 回归不花 Token；
- **可恢复**：区分业务 `FAIL`、待复核 `REVIEW` 和环境 `ERROR`，不把网络问题算成模型错误；
- **副作用受控**：`invalid` / 不支持的输入禁止写入，`incomplete` 按协议带状态受控落盘；
- **可比较**：冻结 Case、Prompt、代码、模型和采样参数，支持模型与架构受控对比；
- **可决策**：同时看任务成功率、执行过程、稳定性、Token 和证据边界。

## 已有证据

- 140 条确定性单元测试；
- Intent、Extract、Query、Tool Use 四套评测 Runner；
- Flash 与 Pro 在同一快照下各完成 399 次正式执行；
- 通过真实失败定位出：死断言、错误归因、日期静默失真、Trace 串线、工具调用错误和结构化输出截断；
- 当前默认模型保留 `deepseek-v4-flash`，因为 Pro 虽在 Query 和 Tool Use 上持平，但出现稳定意图错分和输出协议兼容问题。

## 一句话能力证明

> 我不是只验证 AI“答得像不像”，而是从模型决策、结构化结果、工具轨迹、状态变化、稳定性和成本多个层面，建立一条可观测、可断言、可归因、可回归的 AI 系统质量闭环。

## 当前边界

这是一个可复跑的项目型评测实践，不是外部 Benchmark，也不是完整评测平台。当前已验证固定 Workflow、Tool Use、稳定性、Token 成本和双模型对比；多步 Agent、Memory、完整费用核算、P95/P99、并发和生产级权限治理仍待真实需求驱动后继续建设。
