# 《Agent 评测实战》系列总纲

> 一句话：把真实 AI 测试工作和 `fit-agent` 迭代中验证过的方法、错误与证据，整理成一条可复现的 Agent 评测实践路径。
>
> 读者：想转 AI 测试的功能测试工程师；正在开发 Agent、但不知道怎么证明质量的开发工程师。
>
> 用途：既是内容系列大纲，也是 `fit-agent` 后续迭代的能力地图。先定义完整方向，再由真实迭代逐章解锁；文章是项目证据闭环后的沉淀，不反过来驱动项目凑内容。
>
> 写作定位、读者信任、市场价值与承诺边界，以[写作定位与商业锚点](写作定位与商业锚点.md)为准。

---

## 一、总框架

### 1. 两条主轴

**纵轴：Agent 能力形态**

```text
固定 workflow
→ Tool Use
→ ReAct 多步循环
→ Memory / Planning / Reflection
→ 多 Agent 协作
```

这是本系列采用的项目演进地图，不是行业统一等级。除“固定 workflow → 模型自主选择工具”这个关键分界外，不把后续能力包装成必须按顺序升级的 L0～L6 认证体系。

**横轴：质量维度**

每种 Agent 能力都从六个方面评测：

```text
功能正确性
过程与归因
稳定性与鲁棒性
性能与成本
安全与权限
体验与人工判断
```

能力纵轴回答“模型获得了什么新的决策权”，质量横轴回答“获得这些能力以后，系统可能怎样失败”。后续迭代由两条轴的空白共同决定。

### 2. 从总纲到项目迭代

```text
Agent 能力地图
→ 新增失败模式
→ 所需评测方法与可观测能力
→ 对照当前项目找缺口
→ 决定下一轮迭代
→ 产出代码、Case、原始结果和报告
→ 升级章节证据状态并沉淀文章
```

每个后续迭代必须回答五个问题：

1. 新增了哪种 Agent 能力或系统级质量维度？
2. 解锁了哪些以前不存在的失败模式？
3. 哪些失败可以确定性断言，哪些需要语义判断或人工复核？
4. 需要增加什么 Trace、环境、Fixture 或测试钩子？
5. 最后留下什么可复跑证据？

### 3. 证据状态

#### `已实战`

必须同时具备：

- 真实实现或真实被测链路；
- 可复跑 Case；
- 原始运行结果；
- 人工核对后的结论；
- 明确写出证据不能证明什么。

只有“写了代码”或“跑过一次”不能升级为已实战。

#### `已梳理`

已经完成概念边界、官方或行业依据、典型失败模式和初步评测方法，但尚未在 `fit-agent` 形成完整可复跑证据。

#### `待验证`

只有研究问题、风险假设和预期观测方式，不提前写结论。完成项目证据闭环后再升级状态。

### 4. 发布节奏

- **第一季：第 0～15 讲。**全部建立在 `fit-agent` 已完成实践上，从评测地基走到 Tool Use，构成可以独立交付的完整闭环。
- **第二季：第 16～18 讲。**随稳定性、性能和安全专项迭代解锁。
- **第三季：第 19～22 讲。**随 ReAct、LLM 裁判、Memory、Planning/Reflection 迭代解锁。
- **第四季：第 23～26 讲。**随多 Agent 与评测工程化实践解锁。

第 16 讲以后不设交付期限，不构成写作债务。项目坚持“一次只跨一个明确台阶，完成证据闭环再继续”。

### 5. 单讲写作约定

写作 Skill 内部使用七问检查：

```text
我原本以为：
结果哪里不对：
最后怎么归因：
沉淀出什么方法：
在项目里怎么验证：
这份证据不能证明什么：
读者能拿走什么：
```

前三问融入文章开篇叙事，不显示成模板字段。面向读者只固定三个显式小节：

1. 这次沉淀出什么方法
2. 这份证据能证明什么、不能证明什么
3. 你可以直接拿走什么

## 第 0 部分 · 先看清 Agent 到底难测在哪

### 第 0 讲：大模型为什么让传统测试变难

**证据状态**：`已实战`

**我原本以为**：接入大模型只是把原来的接口换成自然语言输入，等价类、断言和自动化回归可以原样搬过来。

**核心内容**：

- 大模型根据上下文生成内容，为什么同样输入可能得到不同输出；
- 模型、API、Prompt、Context 和结构化输出契约分别解决什么问题；当前“Prompt 约定 JSON + 严格解析”与模型 API 原生 Structured Outputs 有什么区别；
- 为什么“语义答对”仍可能因为 JSON、Schema 或截断而业务失败；
- 为什么接口成功不等于任务完成；
- 模型、Prompt、编排、工具、数据和环境如何共同影响结果；
- 为什么模型失败与测试环境失败必须分开；
- 被测系统、能力纵轴与质量横轴；
- 本系列当前做到哪里，哪些内容尚待验证。

**方法论题眼**：先理解模型的不确定性和系统补偿机制，再从接口测试转向 AI 系统评测。

**产出物**：被测系统链路图 + 能力—质量矩阵 + 最小评测闭环。

### 第 1 讲：什么时候不该上 Agent

**证据状态**：`已实战`｜**证据边界**：结论所依赖的受控实验在第 15 讲，本讲只给判断标准。

**我原本以为**：Agent 架构比固定流程更先进，所以应该优先使用。

**核心内容**：

- 固定 workflow 和 Agent 的区别；
- 决策空间能否被穷举；
- 模型自主性增加后，多出了哪些失败模式；
- 单一请求和复合请求分别适合什么架构；
- 怎样用受控实验代替架构争论；
- 为什么当前实验不能推出“所有场景都应该上 Agent”。

**方法论题眼**：架构复杂度必须由任务价值和评测结果共同证明。

**产出物**：Agent 架构准入检查表。

## 第 1 部分 · 所有 Agent 都要先有的评测地基

### 第 2 讲：为什么代码回归全绿，不代表模型没有退步

**证据状态**：`已实战`

**我原本以为**：Stub 回归全绿，就说明整个 Agent 没有退步。

**核心内容**：确定性回归与真实模型评测分别证明什么；什么变化只需要跑 Stub；什么变化必须跑真实模型；为什么两类结果不能合并成一个通过率。

**方法论题眼**：两本账——确定性回归与模型质量评测。

**产出物**：Stub 注入骨架 + 两本账报告模板。

### 第 3 讲：评测集先数边界，不要先数条数

**证据状态**：`已实战`

**我原本以为**：Case 越多，评测结果就越可信。

**核心内容**：从产品规则提取等价类；标准、边界、对抗、异常和真实 Bad Case；正向与负向覆盖；合成数据的价值与局限；为什么项目内 eval set 不能随便包装成 Benchmark。

**方法论题眼**：等价类覆盖优先于样本数量。

**产出物**：评测集样例 + 等价类覆盖矩阵。

### 第 4 讲：报告全绿以后，我发现一条断言永远不会失败

**证据状态**：`已实战`

**正文**：[37 条全过之后，我发现一条断言没有真正工作](迭代一-03-37条全过后我发现断言没有真正工作.md)

**我原本以为**：评测全绿，说明系统没有问题。

**核心内容**：断言四问；expected 从哪里来；不该发生的事情有没有被检查；一个永远为真的断言为什么等于没有断言；字段断言、业务规则和语义判断怎样随迭代升级；一条 Case 如何聚合为 PASS / FAIL / REVIEW / ERROR；怎样用反例证明断言有效。

**方法论题眼**：测试通过不等于测试有效，评测代码本身也要被验证。

**产出物**：断言四问清单 + “应该失败”用例模板。

### 第 5 讲：同样没通过，为什么不能都叫 FAIL

**证据状态**：`已实战`

**我原本以为**：一条 Case 没通过，统一记成 FAIL 就够了。

**核心内容**：PASS / FAIL / REVIEW / ERROR；业务失败、规则缺失、模型问题和执行异常；为什么 ERROR 不进入业务通过率；Case 级与断言级双口径；为什么不能只报一个总分。

**方法论题眼**：四态判定 + 双口径报告。

**产出物**：四态判定逻辑 + 标准报告结构。

### 第 6 讲：接口成功了，怎么知道是哪一步错了

**证据状态**：`已实战`

**我原本以为**：保存最终输入和输出，就足够定位问题。

**核心内容**：`traceId` 为什么必须贯穿全链路；模型、路由、工具、执行器和状态分别记录什么；事件完整性与结论一致性；为什么每个节点不能各生成一个 `traceId`；Trace 与 Trajectory 的边界。

**方法论题眼**：Trace-first 与分层归因。

**产出物**：Trace 结构定义 + 失败归因排查路径。

### 第 7 讲：改了一行 Prompt，怎么证明功能真的变好了

**证据状态**：`已实战`

**正文**：[改了一行 Prompt，怎么证明功能真的变好了](迭代一-04-改了一行Prompt怎么证明功能真的变好了.md)

**我原本以为**：出现 Bad Case，改到当前输入通过，再加入回归集就结束了。

**核心内容**：Prompt 如何承载业务规则、输出格式和安全边界；修改前保存 baseline；Prompt 文件、hash、Git commit、模型参数和数据集如何绑定；先判断是真失败还是规则、Prompt、模型、解析器、评测器或环境问题；修复 Case 如何进入 regression；为什么修改一条规则后必须检查相邻边界和稳定性。

**方法论题眼**：Prompt 是被测版本资产，修改必须进入“baseline → 变更 → 归因 → 回归 → 版本证据”闭环。

**产出物**：Prompt 变更记录模板 + 回流五步清单 + Golden Case 准入标准。

## 第 2 部分 · 固定 workflow 怎么测

### 第 8 讲：意图识别——第一步分错，后面全错

**证据状态**：`已实战`

**我原本以为**：意图分类只要看 Accuracy 就够了。

**核心内容**：意图边界和类别挤压；Precision、Recall、F1 与混淆矩阵；高风险错进写入链路；防御输入与故障注入；三个意图为什么容易饱和。

**方法论题眼**：路由能力评测与风险指标。

**产出物**：意图评测集 + 分类报告。

### 第 9 讲：模型答得像对的，为什么仍然不能写入

**证据状态**：`已实战`

**我原本以为**：字段抽出来了，就可以写数据。

**核心内容**：`complete / incomplete / invalid` 三态；该写、不该写和写错；多写、少写与重复写；副作用为什么比回答错误更危险；用户不会主动报告的静默脏数据。

**方法论题眼**：副作用断言与保护层。

**产出物**：三态协议 + 副作用断言清单。

### 第 10 讲：昨天通过的时间用例，为什么今天自己坏了

**证据状态**：`已实战`

**我原本以为**：日期变化造成的测试波动，重跑一次就行。

**核心内容**：Clock、Storage、LLM 三类不确定依赖；Frozen Clock、Fake Storage、Stub LLM；时间边界、时区与“这周”；测试环境为什么必须可替换、可恢复。

**方法论题眼**：测试确定性与依赖注入。

**产出物**：三个统一入口 + 时间边界用例集。

### 第 11 讲：查错了，到底是模型没听懂还是代码查错了

**证据状态**：`已实战`

**我原本以为**：查询结果错误，应该先调整 Prompt。

**核心内容**：Planner 与 Executor 分离；纯代码执行层怎样做普通单测；集合断言；日期格式造成的静默失真；测试怎样推动产品确定唯一口径。

**方法论题眼**：可测试性架构。

**产出物**：Planner/Executor 分离骨架 + 集合断言模板。

### 第 12 讲：我写的用例根本没走到被测节点

**证据状态**：`已实战`

**我原本以为**：为 Extractor 准备的输入，一定是在测试 Extractor。

**核心内容**：用例在上游被拦截；不同出口的响应契约；Stub 剧本与 Case 路径；防御逻辑应该在哪一层测试；测试系统为什么也会制造假失败。

**方法论题眼**：用例可达性与评测器验证。

**产出物**：用例可达性自检清单。

## 第 3 部分 · Tool Use：模型开始自主决定做什么

### 第 13 讲：模型第一次自己选工具，应该测什么

**证据状态**：`已实战`

**正文**：[模型第一次自己选工具，应该测什么](13-模型第一次自己选工具-应该测什么.md)

**我原本以为**：把原来的函数包装成 Tools，系统就自然变成 Agent。

**核心内容**：选错工具；参数幻觉；该调不调；不该调却调；工具报错后继续执行；不该写却写；为什么工具返回成功不代表任务完成。

**方法论题眼**：工具选择、参数与调用时机。

**产出物**：工具调用失败模式与硬门禁清单。

### 第 14 讲：最终结果正确，为什么中间过程仍然可能有问题

**证据状态**：`已实战`

**正文**：[最终结果正确，为什么中间过程仍可能有问题](14-最终结果正确-为什么中间过程仍可能有问题.md)

**我原本以为**：最终结果正确，中间调用过程不重要。

**核心内容**：早期错误的级联效应；第一个偏离步骤；工具序列、参数、错误结果和停止条件；合理替代路径与过度僵硬断言；Trace 何时真正进入 Trajectory 评测。

**方法论题眼**：首错归因与执行轨迹分析。

**产出物**：Trajectory 断言模板。

### 第 15 讲：固定链路和工具调用，哪种架构更合适

**证据状态**：`已实战`｜**证据边界**：成本结论只在 3 工具、短 schema 规模下成立，工具变多后交叉点会移动，未测。

**我原本以为**：Agent 架构必然比固定 workflow 更好。

**核心内容**：如何设计只改变编排方式的受控实验；单一意图与复合请求分账；正确率、耗时、调用次数和副作用；当前 12 个场景 × 2 轮实验能证明什么；为什么不能推广为所有场景的架构结论。

**方法论题眼**：用受控实验做架构决策。

**产出物**：架构对比实验设计 + 对比报告模板。

## 第 4 部分 · Agent 的系统级质量

这一部分不是新的 Agent 能力等级，而是所有能力形态都必须补齐的横向质量维度。

### 第 16 讲：Agent 稳定性——偶尔成功和稳定可用不是一回事

**证据状态**：`已实战`｜**证据边界**：只覆盖意图识别一层；discovery 集非 blind holdout，零波动是这个集合上的结论。

**我原本以为**：同一条 Case 跑通一次，就能说明能力存在。

**核心内容**：多次运行为什么必要；峰值能力与稳定成功；波动、超时和相关性失败；环境噪声与业务失败分离；关键安全行为为什么需要连续通过。

**方法论题眼**：多次运行与稳定性口径。

**产出物**：稳定性运行模板 + 波动报告。

### 第 17 讲：Agent 成本评测——Token 少，不一定更便宜

**证据状态**：成本 `已实战`、性能 `已梳理`｜**证据边界**：已实测 prompt/completion/总 Token、调用次数、架构和模型对比；费用、缓存、节点延迟、尾部延迟、并发与无效重试未测。正文见[第 17 讲](17-Agent成本评测-Token少不等于更便宜.md)。

**我原本以为**：统计一次模型响应里的 `total_tokens`，就完成了 Agent 成本评测。

**核心内容**：调用级 usage 如何沿 Trace 汇总成任务级成本；Token、费用与延迟的边界；多调用、零调用和输出截断；固定链路与 Tool Use、Flash 与 Pro 的受控对比；质量门禁与成本选择顺序。

**方法论题眼**：成本的最小统计单位是完整任务轨迹，且必须与任务成功一起衡量。

**产出物**：Token 采集与聚合口径 + 质量—成本对比报告。

### 第 18 讲：Agent 安全测试——模型有工具以后，风险变了什么

**证据状态**：`已梳理`｜已有副作用保护层，尚未形成完整安全专项。

**我原本以为**：安全测试就是在 Prompt 里要求模型“不要做危险操作”。

**核心内容**：越权工具调用；未确认就执行写入；用户未提供却被补出的敏感参数；Prompt Injection 与外部内容诱导；敏感数据进入日志、Trace 或输出；只读与写入权限隔离；高风险动作的人类确认。

**方法论题眼**：最小权限 + 副作用保护 + 攻击路径验证。

**产出物**：Agent 安全威胁清单 + 安全硬门禁。

## 第 5 部分 · 更高能力的单 Agent 怎么测

### 第 19 讲：ReAct 到底是什么，为什么不能只看最终答案

**证据状态**：`已梳理`

**我原本以为**：ReAct 就是让模型多思考几步。

**核心内容**：Reason → Act → Observe 循环；它与一次 Tool Call 的区别；模型如何决定下一步和停止；循环失控、提前停止、重复调用；错误观察如何污染后续判断；为什么不能强行规定唯一正确路径。

**方法论题眼**：多步决策循环评测。

**产出物**：ReAct 状态机 + 循环失败模式清单。

### 第 20 讲：代码判断不了时，才轮到大模型裁判

**证据状态**：`已梳理`｜已有方法和其他项目素材，尚未在 `fit-agent` 的 ReAct 链路落地。

**我原本以为**：代码断言覆盖不了的地方，交给另一个大模型评分即可。

**核心内容**：确定性断言 → LLM 裁判 → 人工；任务是否真正完成；推理与行动是否一致；裁判为什么要允许“不确定”；怎样用人工结果校准裁判；为什么修改 Judge Prompt 后不能直接比较分数。

**方法论题眼**：最小裁判与人工校准。

**产出物**：最小 Rubric + 裁判校准表。

### 第 21 讲：多轮与 Memory——该记住什么，也要知道该忘掉什么

**证据状态**：`已梳理`｜已有真实项目复盘，尚未在 `fit-agent` 复现。

**我原本以为**：把历史消息都传给模型，就拥有了 Memory。

**核心内容**：指代继承；缺失信息追问；跨轮状态一致性；旧信息污染新任务；用户修正后是否更新；该记不记、该忘不忘；Session 与单次 Trace 的区别。

**方法论题眼**：状态断言与上下文控制。

**产出物**：多轮 Case 模板 + 状态转移断言。

### 第 22 讲：Planning 与 Reflection——会规划、会反思，不代表会完成任务

**证据状态**：`待验证`

**我原本以为**：增加规划和反思步骤，就能自然提高成功率。

**核心内容**：计划是否完整、可执行；执行是否偏离计划；计划错误是否及时修正；该反思不反思；正确结果被过度反思推翻；反思后变得更错；多一步推理增加了多少成本。

**方法论题眼**：计划、执行与修正必须分层评估。

**产出物**：Planning / Reflection 失败模式矩阵。

## 第 6 部分 · 多 Agent 怎么测

### 第 23 讲：为什么用了多个 Agent，系统反而更难测

**证据状态**：`已梳理`

**我原本以为**：把任务拆给多个专业 Agent，质量自然会提升。

**核心内容**：什么时候需要多 Agent；单 Agent 能解决时为什么不要拆；Orchestrator、专业 Agent 和共享状态；多 Agent 新增了哪些不确定性；多一个 Agent 是否真的带来质量收益。

**方法论题眼**：多 Agent 是系统复杂度选择，不是能力勋章。

**产出物**：多 Agent 准入检查表。

### 第 24 讲：多 Agent 的核心不是分工，而是交接

**证据状态**：`已梳理`

**我原本以为**：每个子 Agent 各自输出正确，系统结果就会正确。

**核心内容**：任务分派准确性；Agent 间信息丢失率；共享状态一致性；冲突与回退；单个 Agent 的错误如何级联；谁应该为最终错误负责；编排效率与无效调用；多调用一次带来的质量提升是否值得成本。

**方法论题眼**：接口、交接、级联与系统级归因。

**产出物**：多 Agent 评测指标表 + 交接断言模板。

## 第 7 部分 · 把评测变成可持续工程能力

### 第 25 讲：什么时候手写，什么时候上框架和平台

**证据状态**：`已梳理`｜现有实战只覆盖手写命令行工具链，尚未发生向框架或平台换挡的真实场景。

**我原本以为**：专业评测必须先使用成熟框架或平台。

**核心内容**：Runner、评测框架、可观测平台和评测平台的区别；手写适合暴露什么问题；框架可能隐藏什么；什么时候接持续评测和 CI；什么时候需要多人平台；为什么命令行工具链不能包装成评测平台。

**方法论题眼**：工具服从评测目标。

**产出物**：评测工具链换挡条件清单。

### 第 26 讲：从项目到岗位——JD 是雷达，不是目录

**证据状态**：`已梳理`｜已有 JD 对照和项目证据整理，尚未形成完整求职验证。

**我原本以为**：把 JD 里的术语全部放进项目，就算完成能力对齐。

**核心内容**：怎样从 JD 提取高频能力；怎样判断自己是真做过还是只懂名词；项目证据、方法论和岗位表达的关系；如何讲一次真实失败归因；简历中怎样写能力、指标和可验证结果；为什么不能把 eval set 叫 Benchmark、把工具链叫平台。

**方法论题眼**：市场校准与证据化表达。

**产出物**：JD—能力—项目证据对照表 + 简历条目模板。

## 后续项目迭代路线

本节用于从能力地图倒推后续方向。正式实施顺序需要同步到 `docs/master-plan.md` 和 `当前进度.md` 后，才成为项目唯一有效计划。

```text
V5  Agent 性能与成本
    补 Token、节点耗时、工具次数、稳定性和质量—成本对比；
    多模型对比作为同一实验维度，不单独建设 leaderboard。

V6  SQLite 持久化与数据一致性
    补真实状态、用户隔离、事务、重复请求和重启恢复；保持一条命令可运行。

V7  Tool Use 安全
    补越权调用、Prompt Injection、敏感数据、危险参数和副作用保护。

V8  ReAct 多步循环
    补停止条件、循环失控、错误传播和任务完成度。

V9  LLM-as-a-Judge
    在 ReAct 实战中首次解决代码无法判断的过程质量，并完成人工校准。

V10 Memory / 多轮
    补追问、状态继承、指代、用户修正和上下文污染。

V11 Planning / Reflection
    补计划质量、执行偏离、修正有效性和额外成本。

V12 多 Agent
    补任务分派、信息交接、冲突、级联失败和编排效率。
```

评测平台不预设为固定迭代。只有当运行规模、数据规模或协作人数形成真实需求时，才从命令行工具链换挡。

## 总纲维护规则

1. 新概念先判断属于“Agent 能力纵轴”还是“质量横轴”，不随意新增等级。
2. 没有真实证据的内容只能标记为 `已梳理` 或 `待验证`。
3. 每完成一个项目迭代，只升级对应章节，不顺手包装其他尚未验证的能力。
4. 每章必须保留“这份证据不能证明什么”。
5. 项目路线变化时，先更新项目权威计划，再同步本总纲，避免两个事实源打架。
6. 第一季可以独立收口；后续章节按真实迭代生长，不为了补齐目录而制造项目。
