# 《从零给 Agent 搭一套评测体系》系列大纲

> 读者：以测试工程师为主，写 Agent 的开发也能看懂
> 主线：按能力走（意图识别 → 抽取写入 → 查询），每章挂一个方法论题眼
> 素材：全部来自 fit-agent 真实迭代，代码、数据、报告可复现
> 状态：目录草案，第 1 讲已成稿

---

## 全系列一句话

**用一个能跑的最小 Agent，示范怎么把「测不明白」变成「可复现地证明它没坏」。**

## 第 0 部分 · 开篇

### 第 0 讲：Agent 测试到底难在哪——三个传统测试用不上的地方

- 输出不确定：同样输入两次结果不同，怎么当回归
- 调用要花钱：跑一轮回归的成本
- 失败不可见：接口返回成功，但数据是错的
- 全系列会用到的那个最小 Agent 长什么样

**对应**：项目总览
**产出物**：一张链路图，一条命令跑通的仓库

## 第 1 部分 · 意图识别（iter-1，V1.0–V1.3）

### 第 1 讲：从 0 搭一套不花 token 的回归测试

- 意图识别是第一道关：它分错，后面全错
- 评测集不能只测好输入：分类 case + 故障注入 + 输入防御
- **不数条数，数意图等价类**：传统等价类划分怎么迁移到自然语言
- stub 怎么让回归零成本：契约回归与质量评测两本账
- 一条 case 挂了，trace 怎么定位到哪一步歪的
- 评测集为什么要分三层：调优的数据不能拿来验收

**方法论题眼**：等价类覆盖 · 两本账
**对应**：iter-1，V1.0
**产出物**：评测集样例 + stub 脚手架 + trace 结构
**状态**：✅ 已成稿

### 第 2 讲：我的评测报告全绿，然后我发现有一条断言永远不会失败

- 先有方法论，再拿它回头扫自己
- 断言的四问：承诺了什么 / 该发生的发生了吗 / 不该发生的没发生吗 / 说的和做的一致吗
- **测试通过 ≠ 测试有效**：一个永远为真的断言，等于没有断言
- 断多严看「这个值是谁规定的」
- 怎么证明一条断言是活的：给它配一个「它应该失败」的用例

**方法论题眼**：断言分层 · 断言自身的有效性
**对应**：V1.1
**产出物**：断言方法论（四问 + 来源分类）

### 第 3 讲：通过率不该只有一个数字——四态与双口径

- 同样是 FAIL，性质可能完全不同
- 超时算失败吗：把环境异常从业务失败里摘出来
- PASS / FAIL / REVIEW / ERROR 各自什么时候用
- 断言级 92% 和 Case 级 77%，该报哪个（答案是都报）
- 能力评测和回归评测的通过率目标本来就不一样

**方法论题眼**：结果口径 · 指标失真
**对应**：V1.2
**产出物**：四态判定逻辑 + 双口径报告模板

### 第 4 讲：数据集不是造完就完了——来源、判定声明与回流

- 每条数据要能回答「我为什么存在」：source 字段
- 把断言从代码搬到数据：assertion 字段
- 造更难的题：对抗样本与鲁棒集怎么设计
- **打不穿不等于系统好**：评测饱和是什么，怎么识别
- 为什么三个意图打不穿，十几个意图的真实项目会裂开
- Bad Case 回流的五步：先归因，再回流，还要更新覆盖矩阵

**方法论题眼**：数据集设计 · 覆盖矩阵 · 回流闭环
**对应**：V1.3
**产出物**：数据集方法论（六步 + Golden 准入 + 回流）

## 第 2 部分 · 抽取与写入（iter-2，V2.0）

### 第 5 讲：意图对了不代表入口通——双 LLM 串联怎么定位

- 第二个 LLM 节点带来的新问题：错在意图层还是抽取层
- trace_id 必须贯穿全链路，不能各层各生成一个
- 归因分层：层序即归因序
- 一个真实的例子：从「模型能力不行」到「prompt 格式约束不够死」

**方法论题眼**：可观测性 · 分层归因
**对应**：iter-2 链路设计

### 第 6 讲：Agent 开始写数据了，测试的重心要变

- 抽取判错比意图判错危险在哪：**用户不会报 bug 的那类错误**
- 三态判定：完整 / 缺字段 / 不可抽，各自怎么处理
- 断言重心从「判得准不准」转向「该不该写、写了几条」
- **不该写的没写，比该写的写了更容易漏**
- 副作用断言：从「有没有意外写入」到「精确断言写了什么」

**方法论题眼**：保护层断言 · 副作用验证
**对应**：V2.0

### 第 7 讲：用例走不到被测节点，你测的就不是你以为的东西

- 一个真实翻车：我造的用例被上游拦下了，根本没到被测层
- 同一条链路不同出口，响应形状不同，契约断言必须分支
- stub 剧本要跟着用例的预期走
- 多节点链路里写用例前，先问「这条输入会走到哪一层」

**方法论题眼**：测试自身的缺陷
**对应**：V2.0 的两个 Review 发现

## 第 3 部分 · 查询与端到端（iter-3，V3.0）

### 第 8 讲：让测试不再依赖「今天」——时间怎么注入

- 用例会自己烂掉：今天跑对了，明天就错
- Clock 注入：第三个统一入口
- 只有冻结时间才写得出来的边界用例：00:00:00、23:59:59、跨时区、周一问「这周」
- **任何让测试变慢、变贵、变不确定的依赖，都必须能被替换掉**

**方法论题眼**：测试确定性 · 依赖注入
**对应**：V3.0 Clock

### 第 9 讲：把 LLM 和执行切开——查询链路怎么设计才好测

- Planner 用 LLM，Executor 用纯代码
- 好处：查错了能分清是没听懂用户，还是查错了数据
- 纯代码那半可以普通单测覆盖，不花 token
- 集合断言：条数对不对、该在的在不在、**不该在的没混进来**

**方法论题眼**：可测试性架构
**对应**：V3.0 查询链路

### 第 10 讲：口径不定死，用例就写不出唯一答案

- 「这周」从周一算还是往前推七天
- 查无结果算不算错误
- 不完整的记录要不要计入统计
- **这些不是技术问题，是产品口径**——测试推动定义，而不是自己猜
- 写不出唯一 expected 的场景，标阻塞，不进用例设计

**方法论题眼**：可测试性门禁 · 测试左移
**对应**：iter-3 PRD §3 八条口径

### 第 11 讲：一个静默失真的 bug，和它为什么只能被单测抓到

- 日期校验接受了非零填充，范围过滤悄悄出错
- 不报错、不崩溃、只是数字不对——这类 bug 的特征
- 为什么端到端测不出来，只有边界单测抓得到
- 修法有几种，为什么选了最保守的那个

**方法论题眼**：静默失真类缺陷
**对应**：问题清单 P-001

## 第 4 部分 · 从练习到工程

### 第 12 讲：存储选型——为什么我不用数据库，以及企业里为什么必须用

- 需求只有「追加、读回」时，数据库是纯负担
- 留好 Protocol 口子，换实现不影响上层
- 企业里一次「写入」是跨系统的一组写入
- 由此带来的测试增量：一致性、幂等、并发、数据准备与清理
- **测试时间的大头会从「设计用例」转移到「准备和清理数据」**

**方法论题眼**：技术选型跟着测试需求走
**对应**：存储选型与企业实践差异

### 第 13 讲：大模型裁判要做浅——别把评测搞成没人维护的系统

- 三级漏斗：代码断言 → LLM 裁判 → 人工
- 裁判只输出三态，**不要评分、不要量表、不要权重**
- 裁判是观察员不是法官：结果不进正式通过率
- 为什么「改一下裁判 prompt 通过率从 72% 跳到 85%」的指标不能当门槛
- 什么时候才需要校准

**方法论题眼**：评测系统的成本控制
**对应**：断言方法论第 4 节

### 第 14 讲：真实数据进评测集之前——脱敏要做到什么程度

- 先判断需不需要：风险面 = 取了哪些字段 × 可能出现什么
- 按「给谁看」定投入，别一上来就套合规那套
- 最小可执行版三步
- 替换不删除：删字段会改变输入分布，评测就失真了
- **保留决策相关特征**：口语、错别字恰恰是模型会出错的地方
- 什么时候才需要升级到清单式和风险量化式

**方法论题眼**：数据合规与效用的平衡
**对应**：数据集方法论第 8 节

### 第 15 讲：小版本演进——怎么让「我做了个项目」变成「我解决了什么问题」

- V1.0 到 V3.0 每一版发现了什么、改了什么
- 为什么不一次性修完所有问题
- 问题清单怎么记：现象、为什么是问题、修法与没选的方案、验证方式
- 面试怎么讲：不是「我搭了个评测框架」，而是「方法论真的抓到了 bug」

**方法论题眼**：工程叙事 · 可展示的经验
**对应**：版本演进与问题复盘 + 问题清单
